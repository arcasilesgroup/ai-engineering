01The idea in plain words

Today the helper asks you many questions, waits for your yes, and stops again to show you the result before you merge. You want it to do the job when the job is clear, to pick the answer it recommends when something is unclear and nobody is there, and to write down every choice it made. You check the work in one place: the review that GitHub or Azure DevOps already asks for before a merge. The work is kept safe by locks that are always on, not by stop signs: the git hooks, the guard on every tool call, the scripts and tests, one AI review, and the review rule on your main branch. It always waits for you in one case: a feature that would use AI in a forbidden or high-risk way. First a practice job with hidden mistakes is run, so the numbers prove the cuts are faster and still catch every mistake.

Direction set by the owner on 2026-11-22: "by default, if it is clear, we continue and it gets implemented; in an autonomous process, assume the recommended option". Four independent adversarial reviewers (security, quality, simplicity, facts) checked the first version of this page. The owner accepted their changes on 2026-11-22.

02Why this matters

The product page (/why/, read on 2026-11-22) promises "no lifecycle to learn and no flow to migrate to", says "the guards screen the run; they do not script it", and claims "the work goes faster, on fewer tokens". The skills today add stops, nested loops and agent turns that the floor does not need. The base of the framework is the deterministic floor (git hooks, the guard chain, scripts, tests, the forge's review policy) plus AI validation where judgment is needed. A skill earns a step only when that step catches something the floor misses.

An earlier draft of this page added grant files, a launcher command and a session marker to allow unattended runs. The owner dropped it on 2026-11-22 as ceremony.

03Who it's for

  • The owner of a repository who wants clear work built without being asked, and who reviews in the forge before merge.
  • Every downstream project that installs ai-engineering: the skills, the guard and the AGENTS.md template ship to them.

05What success looks like

  • A clear request runs from brainstorm to a pushed feature branch with zero questions, on every lane.
  • With a person present and something unclear, the brainstorm asks at most one batch of questions, and only about choices that change the build: data model, public interface, a new runtime dependency, security, or the AI Act class.
  • With nobody present, each such choice takes the recommended answer and is listed under "Decided by the agent", so the reviewer sees it in the forge.
  • A plan write is refused when the brainstorm has no ai-act-class, when the class is prohibited, and when it is high-risk and the slug is not listed in config.toml.
  • A headless run always ends in a named state, and ai-eng work status <slug> exits 0 only when every checkpoint passed.
  • Against the A0 baseline of the reference feature, over 3 runs each: fewer agent dispatches per feature (splits included), and every planted defect is still caught.

06Decisions already made

Decided by the owner on 2026-11-22, unless a line says otherwise.

  • Autonomous by default. A clear request goes straight to the build. An unclear one, with nobody to answer, takes the recommended option and records it under "Decided by the agent". The read-back is always written into the page, and the run does not stop for it. "Clear" means the read-back leaves no gap in the five batch categories of section 05. This covers every lane: the spike "nod", the bounded "STOP", the HARD-GATE and the "too simple to need approval" section go.
  • The base is the deterministic floor plus AI validation. A skill adds no stop, step or agent turn unless it catches what the floor misses.
  • The forge's review policy is the human gate. That means GitHub branch protection or a ruleset with a required review, or an Azure DevOps branch policy with a minimum number of reviewers. ai-engineering does not block gh or az merge verbs. ai-eng doctor reports a base branch that has no required review. A headless run starts only when ai-eng doctor passes: the floor hooks are installed and the review policy is on. Without a forge, ai-eng worktree merge accepts a plan whose every checkpoint passed; the merge is local and can be undone. (The no-forge line is the recommended default, taken under the owner's rule.)
  • The app review leaves the lifecycle. Phase 4 becomes a report: routes to try, the checkpoint summary, the assumptions and the "Decided by the agent" list. The same change removes the app-review states, the reviewed-SHA pinning in Phase 3 and ai-eng worktree request-changes. A change request is a new run that resumes the slug.
  • The approval stamp shrinks. The guard keeps the slug match and the 14-day age, and drops the status-line equality check. The page carries no ai-approved-by field: "Decided by the agent" already says who chose.
  • AGENTS.md "never approve on your own initiative" becomes "approve when the request is clear; record what the agent decided". This applies to templates/AGENTS.md.tpl too.
  • EU AI Act, enforced by the guard. Every brainstorm carries <meta name="ai-act-class"> with one value: none, minimal, transparency (Art. 50), high-risk (Art. 6, Annex III) or prohibited (Art. 5) of Regulation 2024/1689. When in doubt, the class is high-risk. The guard refuses the plan write when the class is missing or prohibited. It also refuses high-risk unless the slug is listed in [work] ai_act_high_risk in config.toml, a file that self-protect already keeps from the agent, so only a person can list it. Art. 50 duties (tell people they deal with AI, mark generated content) become acceptance criteria that Gate 1 tests.
  • Untrusted input is scanned. The PostToolUse matcher adds mcp__.*, so issue text read through MCP passes the injection guard.
  • Headless runs end in a named state. When the Stop gate lets a turn end with open gates, it writes halted: {reason: "stopped with open gates"} itself. A wait for a person is halted: {reason: "needs-person: <why>"}. ai-eng work status <slug> prints the state and exits 0 when every checkpoint passed, 2 when halted and 3 when a person is needed. The CI job sets its own timeout and one concurrency group per clone. A fourth run while three lanes are active fails with the existing worktree new message.
  • A0 measures quality first, then cost. The reference feature under tests/fixtures/reference-feature/ (a labelled input, a button, an error state, a sticky header, run in a fresh ai-eng init repo in a temp folder) carries planted defects named before the baseline: at least one per gate, one security defect for Gate 3, and one piece of correct code that looks wrong, as false-positive bait. Each run records the gate and attempt that caught each defect. Cost is the count of agent dispatches per feature, splits included, timed from the Pre and Post receipts of the same tool_use_id. Both receipts gain an optional checkpoint field; the plan-write inference is dropped. Each comparison runs 3 times. The report is the receipts summary in ai-eng doctor (with --json), not a new command, and the baseline is committed as tests/fixtures/reference-feature/baseline.json, because receipts expire after 30 days. Timing is a measurement, never a gate.
  • Dropped: grant files, the grant guard, ai-eng work run, the session marker, the stop button, the parity test, ai-approved-by and ai-eng work time.
  • Everything follows public standards, with no company-specific rule.

Cuts

Each cut removes agent turns, stops or tokens and keeps every deterministic check. A cut that lets a planted defect through is reverted.

  1. Gate 3 is one critic pass per attempt. The next critic receives the stored findings and the fixer's ROOT CAUSE and FIX lines in the same prompt. The fixer may return DISPUTED F<n> <file:line>, and the next critic rules on it. The nested debate leaves the loop; /ai-adversarial-loop stays as a skill on request.
  2. Prototypes and the two UI reviewer agents run only when a design reference exists or the person asks. This cut ships with A3, because only then does Gate 2 run axe and audit.mjs as verify commands against a served build.
  3. checkpoint-planner writes the test plan in the same turn. The unhappy-path, why_ui and lowest-layer rules of ai-test-planner move into the planner, and the critic judges coverage against the brainstorm, not only against the planner's own acceptance.
  4. The viewer is opt-in, started only when a person is watching. The planner validates its JSON with bun, so the default path needs no python3.
  5. The brainstorm is one pass. It writes the sections into templates/brainstorm.html.tpl and never copies the CSS reference. It asks only under the batch rule and writes no PRD.html. The approval commit lands on the feature branch, never on main.
  6. Phase 4 is a report, as decided above.
  7. A LEARNINGS entry is written on a halt, or when the root cause differs from the finding. review-noise entries stay, because they are the only feedback on critic false positives.
  8. Gate 1 and the environment check run as scripts that report PASS or FAIL, not as subagent turns. One commit per passed checkpoint replaces one commit per gate result.

08Constraints and guardrails

  • No change removes or weakens a guard, a git hook, a script check or a test.
  • Never bypass a hook, never silence a linter, no secrets or machine paths.
  • No change adds an agent turn per checkpoint.
  • Wall-clock numbers are reported and never asserted (scripts/bench-chain.ts:3).

09Out of scope

  • Grant files, a launcher command, a scheduler or a daemon. A headless run uses the surface's own headless mode, and the schedule belongs to cron or CI.
  • A guard on forge merge verbs. The forge's review policy owns the merge.
  • Release or tag by an agent.
  • Removing any guard or git hook.
  • New skills.
  • The other steps of the plan (A2 to A8), queued in Handoff notes.
