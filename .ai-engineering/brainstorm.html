Producción lista para usar

Quieres que una persona pueda instalar ai-engineering desde cero en macOS, Linux o Windows, usar sus guardas con límites claros y recibir un paquete probado y atribuible.

01La idea en palabras simples

Una persona nueva debe poder instalar y ejecutar la herramienta sin ayuda. Antes de publicar una versión, el equipo debe probar el paquete que realmente se entrega, comprobarlo en los sistemas admitidos y saber de quién viene la versión. La herramienta también debe explicar claramente lo que no puede proteger.

02Por qué importa

La auditoría local de 2.6.0 encontró problemas en la instalación, pruebas que fallaron o no pudieron ejecutarse, controles incompletos antes de publicar y contenido con licencias sin resolver. Publicar sin cerrar o bloquear esas rutas dejaría al usuario con una promesa de seguridad que las pruebas no respaldan.

03Quién lo necesita

  • Personas que instalan ai-engineering desde cero en macOS, Linux o Windows.
  • Mantenedores que revisan cambios y publican versiones.
  • Equipos que necesitan entender cuándo una guarda falla abierta y cuándo hace falta aislamiento del sistema operativo.

04Qué existe hoy

  • package.json declara Bun como runtime y bin/ai-eng.js tiene shebang de Node. El informe probó un caso de enlace global Bun sin Node.
  • El código usa Bun.TOML; no encontramos una importación runtime de smol-toml. Esa afirmación del informe necesita corregirse, no añadir una dependencia a ciegas.
  • platforms.yml prueba init, doctor y uninstall en tres sistemas, pero no ejecuta la suite completa en cada uno.
  • El workflow de release crea el SBOM del repositorio completo y no ejecuta un smoke test del tarball instalado.
  • El hook de Copilot CLI conserva un fallback que puede permitir la llamada cuando el comando falla. Las guardas no aíslan programas opacos ni scripts preparados en llamadas anteriores.
  • El informe de licencias deja fuentes y permisos sin resolver. El tag 2.6.0 es ligero, no firmado.

05Cómo sabremos que funciona

  • El tarball real se instala y ejecuta en un consumidor limpio; el camino Bun-only funciona sin Node.
  • La suite completa produce resultados visibles en Linux, macOS y Windows; el timeout de retención queda resuelto y repetible.
  • La publicación verifica lint, typecheck y tests del SHA exacto, y produce un SBOM CycloneDX del paquete de runtime con licencias.
  • Los tags futuros son anotados y firmados por una clave configurada y verificada.
  • Los permisos de redistribución están documentados; si no se pueden probar, la publicación se detiene.
  • La documentación distingue las guardas de un sandbox del sistema operativo y explica el comportamiento fail-open de Copilot.

06Decisiones ya tomadas

  • No declarar smol-toml como dependencia directa mientras el runtime use Bun.TOML.
  • Probar el tarball empaquetado, no solo el árbol de trabajo.
  • Probar la suite en los tres sistemas soportados y ligar el release a verificaciones del SHA exacto.
  • Generar el SBOM desde la instalación de consumo, con licencias de sus dependencias runtime.
  • Bloquear releases mientras falten permisos verificables para el contenido incluido o una clave de firma permitida.
  • No reescribir el tag publicado 2.6.0, borrar contenido del producto ni inventar permisos o una identidad de firma.
  • No disparar workflows externos ni publicar como parte de esta tarea.

07Decisiones aún abiertas

No quedan decisiones de política abiertas. Las fuentes y licencias exactas de ciertos contenidos y la huella de la clave autorizada son hechos que hay que verificar. Hasta entonces, el release queda bloqueado; no se elimina contenido ni se acepta una licencia o firmante por suposición.

08Restricciones

  • Conservar el estado no rastreado existente, en especial .audit-2.6.0/ y los directorios de pruebas.
  • No hacer push, publicar, cambiar tags existentes ni lanzar workflows remotos sin autorización.
  • Usar las herramientas y pruebas Bun del repositorio; npm solo donde sea necesario probar el contrato npm.
  • Los resultados locales de macOS no sustituyen ejecuciones en runners Linux o Windows.

09Fuera de alcance

  • Crear un sandbox de sistema operativo dentro de ai-engineering.
  • Resolver por cuenta propia derechos legales, permisos de redistribución o la clave del firmante.
  • Modificar la publicación histórica 2.6.0, publicar una versión o cambiar configuración remota del repositorio.

10Preguntas de investigación

  1. ¿Qué contrato exacto aplica Bun al enlace global de un paquete con shebang Bun en macOS, Linux y Windows?
  2. ¿Qué tests de retención exceden el timeout en macOS y qué timeout mínimo permite una suite estable sin ocultar fallos reales?
  3. ¿Qué fuentes y licencias pueden demostrarse para ai-verify, ai-audit-design y el clasificador spoken-secret?
  4. ¿Qué huella de clave se autoriza para firmar los tags futuros?
  5. ¿Qué forma válida de respuesta y fallo aplica la versión soportada de Copilot CLI?

11Notas para la entrega

Dividir el trabajo en checkpoints: paquete y launcher; estabilidad y matriz de sistemas; gates de release, SBOM y firma; atribución y documentación de límites. Mantener el release bloqueado donde falten permisos o configuración humana.
