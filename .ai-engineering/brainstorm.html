01La idea en palabras llanas

Quieres una sola skill, ai-triage, para GitHub y Azure DevOps. Mira la URL que le das o el remote del repo para saber dónde buscar. Si no sabe cuál board usar, pregunta y recuerda la respuesta solo durante esa ejecución. El informe muestra todos los miembros del backlog elegido y los explica, como el informe de GitHub.

La skill solo lee Azure. Aquí se puede guardar el informe privado en el archivo normal, pero no se hace commit ni push con esos datos.

Ampliación aprobada: no basta con ordenar por Priority y Severity. Queremos saber qué cuenta el equipo en los comentarios, cuánto tiempo lleva abierto un elemento, qué importancia tiene su padre y si hay una fecha de entrega o un sprint definido. Cada recomendación debe decir por qué conviene actuar ahora y señalar los hechos que la apoyan.

02Por qué importa

La intención original era ofrecer una explicación útil del backlog en ambos proveedores. Azure ya tiene inventario y jerarquía, pero su orden solo toma Priority y Severity. Falta distinguir trabajo con compromiso próximo, bloqueos documentados y elementos antiguos que necesitan revisión, sin confundir actividad con urgencia.

03Para quién es

Para personas y equipos que usan ai-engineering con Azure DevOps en distintas organizaciones y proyectos. No debe depender de la empresa ni del tenant usado para probarla.

04Qué existe hoy

  • skills/ai-triage/SKILL.md define una única skill de solo lectura con procedimientos separados para GitHub y Azure DevOps.
  • La plantilla de brainstorm existente da el formato HTML para este documento.
  • En esta ampliación no se consulta Azure DevOps productivo. La ejecución de triage anterior se limita a evidencia del estado actual, no prueba la viabilidad de las nuevas APIs.
  • El usuario indicó que un proyecto de Azure DevOps puede tener varios boards y que el servicio de prueba es productivo y privado.
  • La implementación actual muestra padres e hijos como contexto, conserva el estado literal y no amplía el inventario con relaciones.
  • skills/ai-triage/references/azure-devops.md:52-61 documenta un ranking basado solo en Priority y Severity.
  • skills/ai-triage/scripts/collect-azure.mjs:9-13 limita los campos de contexto de padres e hijos a tipo, estado y título; no recoge su prioridad ni fechas.
  • skills/ai-triage/scripts/render-report.mjs:462-529 muestra prioridad, análisis, área, jerarquía y evidencia; no muestra señales temporales ni Why now.

05Cómo se ve el éxito

  1. Sin argumentos, un remote único identifica el proveedor y el destino. Si hay más de una opción posible, la skill pregunta antes de leer.
  2. La skill conserva la triage GitHub actual y añade Azure DevOps sin mezclar sus tipos de trabajo ni sus reglas de lectura.
  3. Con una URL, la skill limita la lectura al board indicado y muestra el destino que va a consultar.
  4. La salida de Azure DevOps presenta todos los elementos del board y sus detalles importantes con el mismo nivel de explicación que ai-github-triage.
  5. La ejecución no crea, edita, cierra, comenta ni borra work items.
  6. El informe de una ejecución real conserva los datos y explicaciones del backlog. En este repo público se permite generar localmente el informe de prueba, pero no hacer commit ni push de ese resultado privado.
  7. La skill funciona para organizaciones y proyectos distintos, sin nombres, URLs, credenciales ni reglas privadas codificadas.
  8. Ampliación aprobada: cada elemento muestra las señales verificadas y un Why now específico, o declara que no hay evidencia suficiente para justificar urgencia.
  9. Ampliación aprobada: un comentario que confirma un bloqueo importa por su contenido, no por aumentar un contador. El informe distingue los hechos del board de las inferencias del análisis.
  10. Ampliación aprobada: fechas e iteraciones ausentes, personalizadas o inaccesibles se identifican explícitamente; no se adivinan ni se sustituyen por el estado del workflow.

06Decisiones ya tomadas

Fijadas por el usuario

  • Habrá una única skill pública ai-triage, con un contrato común y procedimientos separados por proveedor.
  • ai-triage reemplaza a ai-github-triage; no habrá alias separado. El flujo GitHub existente debe conservar su comportamiento.
  • Una URL explícita decide proveedor y destino. Sin URL, la skill usa el remote del repo si identifica un único proveedor y destino; ante ambigüedad pregunta. No usa la cuenta activa de Azure CLI para adivinar.
  • El informe para el usuario debe contener y explicar el backlog completo del ámbito seleccionado, como ai-github-triage.
  • En Azure DevOps, cada ejecución cubre un solo board/nivel. Las relaciones con padres o hijos pueden mostrarse como contexto, pero no amplían el inventario; varios boards solo si se piden expresamente.
  • El Azure DevOps de prueba es productivo y privado. El informe puede guardarse localmente aquí, pero no se hace commit ni push de sus datos.
  • Si hay varios boards y no se indica uno, la skill pregunta en vez de adivinar. La elección solo vale para esa ejecución; no se añade un campo de triage a config.toml.
  • El diseño original pedía excluir estados terminales. La implementación actual conserva todos los miembros devueltos por el backlog. Esta ampliación no cambia esa política ni interpreta nombres de estado como urgencia.
  • La skill y todas sus pruebas son estrictamente de solo lectura respecto a Azure DevOps.
  • El usuario aprobó el 2026-10-08 evaluar comentarios, antigüedad, prioridad del padre, fechas de entrega, iteraciones o sprints y Why now mediante una recomendación razonada, separada de Priority y Severity originales, que permanecen visibles y no se reescriben.
  • Los compromisos vigentes y bloqueos explícitos pueden cambiar la recomendación de qué atender primero. Cada cambio de orden explica su evidencia y la acción sugerida; sin razones verificables se conserva el orden nativo actual. No hay score ponderado, pesos configurables ni urgencia por antigüedad o número de comentarios solos.
  • Los comentarios se analizan por contenido, secuencia y fechas. Una afirmación del equipo no se presenta como un hecho comprobado en código; una actualización posterior que resuelve un bloqueo sustituye la conclusión anterior.
  • La prioridad y el calendario del padre directo son contexto, sin herencia automática. Solo se afirma que un hijo bloquea la entrega del padre cuando existe evidencia explícita de esa dependencia.
  • Una fecha de entrega explícita representa un compromiso. El fin del sprint es contexto de planificación, no una fecha de entrega automática; una iteración sin fechas no aporta un plazo. Un compromiso próximo no rebaja por sí solo un riesgo crítico y los conflictos quedan visibles para decisión humana.
  • Una señal ausente, inaccesible o parcial se distingue con su motivo y próxima acción. La cobertura se describe como suficiente, limitada o no evaluable, nunca como confianza numérica. Una señal opcional inaccesible o parcial permite un informe de cobertura limitada si el inventario está completo; no permite afirmar ausencia de bloqueos ni urgencia sin evidencia.
  • La aprobación autoriza este diseño y su implementación local. No autoriza mutaciones remotas, nuevas lecturas productivas ni publicar datos privados. Las nuevas APIs siguen pendientes de investigación.

07Decisiones todavía abiertas

Decisiones de producto cerradas

El usuario aprobó el diseño y sus valores recomendados el 2026-10-08. Las reglas vinculantes están en la sección 6. No quedan decisiones de producto abiertas; la investigación técnica de la sección 10 es requisito previo a planificar las nuevas lecturas.

Alternativas consideradas y elección aprobada

  1. Aprobado: hechos más recomendación razonada. Recoger las señales verificables, mantener separada la prioridad del board y explicar en Why now por qué atender, aclarar, desbloquear o revisar el elemento. Los compromisos y bloqueos evidenciados influyen en la recomendación, sin score opaco. Las nuevas APIs requieren investigación antes de planificar su uso.
  2. Descartado: solo enriquecer la explicación. Mostrar las mismas señales conservando siempre el orden por Priority/Severity es menos invasivo, pero puede dejar enterrada una entrega próxima con compromiso vigente.
  3. Descartado: score ponderado configurable. Sumar pesos de edad, comentarios, padre y calendario crea falsa precisión, requiere calibración por equipo y puede premiar ruido o tickets abandonados.

Padre y calendario aprobados

Mostrar prioridad y fechas del padre directo sin herencia automática. Una relación padre-hijo no prueba que ese hijo bloquee toda la entrega. Una fecha de entrega explícita es un compromiso; el fin de una iteración solo es contexto de planificación, y una iteración sin fechas no aporta un plazo.

Evidencia insuficiente aprobada

Distinguir ausente, inaccesible y parcial, sin fabricar confianza numérica. Mostrar cobertura suficiente, limitada o no evaluable con el motivo y la próxima decisión concreta. Solo continuar con señales limitadas cuando el inventario esté completo y los guardarraíles de autenticación, ámbito y salida segura sigan satisfechos.

Escenarios de aceptación aprobados

  1. Un bug crítico y una tarea con entrega mañana: el calendario no rebaja automáticamente el riesgo crítico. Why now explica cada motivo y señala el conflicto para decisión humana.
  2. Un ticket antiguo con muchos comentarios, sin compromiso vigente: recomendar revisar relevancia o aclarar, no declarar urgencia solo por su edad o actividad.
  3. Un hijo de una Feature prioritaria: mostrar la prioridad del padre. Solo afirmar que bloquea esa Feature si hay evidencia explícita de esa dependencia.
  4. Un elemento asignado a un sprint vencido: señalar planificación desactualizada, no afirmar que incumplió una fecha de entrega que no existe.
  5. Un comentario antiguo dice bloqueado y uno posterior indica desbloqueado: analizar la secuencia y sus fechas; no mantener la conclusión antigua por contar menciones.

08Restricciones y guardarraíles

  • El HTML generado para un backlog privado puede existir localmente en el árbol de trabajo de este repo; nunca se incorpora al historial de ai-engineering mediante commit o push.
  • El informe que genera la skill en el proyecto de un usuario conserva el detalle completo del backlog; esa salida de usuario no es un fixture ni contenido fuente de ai-engineering.
  • El triage normal no crea, edita, asigna, comenta, cierra ni borra work items.
  • Un destino ambiguo, un error de autenticación o una lectura/paginación incompleta del inventario detiene el run y conserva el informe anterior. La cobertura limitada de señales opcionales se identifica por separado; no se amplía el ámbito ni se presenta como evidencia completa.
  • No inferir el proyecto a partir del usuario/tenant activo de Azure CLI cuando el repo o la URL no identifican uno.
  • Un fallo conserva el informe anterior. Los campos remotos se escapan como contenido no confiable antes de incluirlos en HTML; los enlaces solo se generan con URLs HTTPS validadas. La autenticación nunca aparece en el informe.
  • El entorno disponible es productivo. Usar fixtures sintéticos locales; cualquier nueva validación con lecturas reales requiere autorización específica y permanece estrictamente de solo lectura.
  • La salida real puede escribirse localmente en .ai-engineering/triage.html, pero no se hace commit ni push mientras contenga datos del Azure privado.
  • No modificar work items ni copiar datos reales del backlog a fixtures, logs, documentación o código fuente; el único artefacto de datos es el HTML local de triage.
  • Resolver y anunciar el ámbito antes de leer datos. No mezclar organizaciones, proyectos, equipos ni boards.
  • La implementación debe ser genérica y no asumir que el lector tiene permisos para crear, editar o borrar elementos.

09Fuera de alcance

No forma parte de esta idea

  • Crear, editar, asignar, comentar, cerrar o borrar work items como parte del triage normal.
  • Enviar datos del backlog a servicios externos o incorporarlos a ejemplos, tests, documentación o fixtures de ai-engineering.
  • Combinar varios boards en un mismo informe.
  • En esta ampliación, cambiar el comportamiento GitHub, crear un motor configurable de scoring o validar vulnerabilidades contra un repositorio que no se ha identificado.

10Preguntas para investigar

  1. Confirmar cómo Azure DevOps representa equipos, boards y niveles de backlog en sus URLs y APIs; importa para interpretar una URL sin ampliar el ámbito por error.
  2. Ver qué puede descubrirse de forma fiable desde un remote Git y cuándo hay que preguntar por varios equipos o boards.
  3. Comprobar qué comandos de Azure CLI están disponibles y qué permisos solicitan, sin imprimir ni guardar datos del tenant; importa para elegir una ruta de lectura segura.
  4. Preservar el contrato de inventario completo actual. No inventar paginación para membresía del backlog; comprobar la paginación únicamente en endpoints que la documenten.
  5. Verificar cómo preservar los campos y relaciones de Azure en el HTML sin permitir contenido activo ni enlaces inseguros, y que una lectura incompleta nunca se presenta como triage completo.
  6. Ampliación: comprobar las APIs de comentarios y su paginación, permisos y límites, y distinguir comentarios completos de una lectura parcial.
  7. Ampliación: verificar campos estándar de creación, actualización y entrega, y cómo reconocer campos personalizados sin reglas específicas de una organización.
  8. Ampliación: verificar cómo resolver las fechas de una iteración dentro del equipo seleccionado, sin asumir que una ruta de iteración implica un sprint activo.
  9. Ampliación: comprobar el coste y los límites de leer prioridad y calendario del padre directo; el padre sigue siendo contexto, no inventario adicional.

11Notas de handoff

Componentes y flujo aprobados

  1. Resolver e inventariar con los módulos existentes. Ampliar la allowlist solo después de verificar rutas de lectura documentadas y mantener el ámbito explícito.
  2. Enriquecer los miembros del inventario con comentarios, creación/actualización, calendario del elemento y contexto del padre directo. Resolver metadatos de una misma iteración una sola vez por ejecución; no recorrer ancestros o hermanos sin límite.
  3. Analizar cada elemento una vez con hasta cinco análisis en paralelo. La misma entrada de evidencia alimenta Analysis y Why now, pero no se duplica el texto. Cada conclusión cita su fuente y distingue una afirmación del equipo de un hecho comprobado en código.
  4. Renderizar señales, recomendación y datos originales en la fila existente. Validar inventario, análisis y enlaces antes de reemplazar el informe con el escritor atómico actual.

Errores y datos que faltan

Una lectura incompleta del inventario, un error de autenticación, un ámbito ambiguo o una salida insegura mantienen el informe anterior. Una señal opcional que no existe se muestra como ausente. Una denegación de permisos específica de una señal se muestra como inaccesible y una lectura incompleta como parcial; con inventario completo se puede continuar indicando cobertura limitada o no evaluable por elemento. No se afirma ausencia de bloqueos ni una conclusión completa a partir de esas lagunas. La investigación debe confirmar cómo identificar estos casos, no presentar las APIs nuevas como ya verificadas. Ningún fallo permite ampliar el ámbito o escribir en Azure.

Pruebas requeridas

Usar los tests existentes y fixtures sintéticos para los cinco escenarios de la sección 7, límites de paginación de comentarios, fechas/zonas horarias, metadatos ausentes, permisos, padres fuera del ámbito, HTML no confiable y conservación del informe anterior. Fijar el reloj en las pruebas de antigüedad/calendario. Mantener las pruebas de GitHub como regresión y comprobar que cada miembro aparece exactamente una vez.
