Un worktree por sesión, main como único destino local

Cada sesión que escribe código vive en su propio worktree con rama efímera; al terminar, su trabajo se fusiona en el main local y el worktree desaparece. Nadie empuja a origin: el PR lo abre el humano cuando decide, después, desde main local. Triage, research y auditorías no abren worktree. Se borran ai-pr-loop-fix y la vieja ai-git-cleanup, y nacen una ai-git-cleanup nueva y una skill ai-pr.

01La idea en palabras llanas

Cuando un agente va a cambiar el proyecto, no trabaja en tu carpeta: se hace una copia aparte con su propia rama y ahí dentro lo hace todo. Cuando termina, su trabajo se pega en el main de tu ordenador, la copia se borra y la rama se borra. Nada sale a internet. Cuando tú quieras, coges el main de tu ordenador y pides un pull request con todo lo que hay dentro, y ahí sí se ve en GitHub, se revisa y se fusiona. Y para la limpieza hay un solo comando que borra las copias y las ramas que ya no sirven, sin que tengas que apuntar nombres, y que nunca borra algo que no esté ya fusionado.

Las sesiones que solo miran (un triage, un research, una auditoría) no abren copia: miran el original y no lo tocan.

02Por qué importa

"Ahora mismo no está funcionando bien" tiene causas concretas y verificables, no una sola:

  • El árbol principal no está en main. git branch -vv hoy devuelve * feat/arcasiles-skills en /Users/soydachi/repos/ai-engineering, con main en 3986acbb. El modelo que pides exige el checkout principal en main; hoy no lo está, así que no hay destino local único al que fusionar.
  • El contrato citado no existe. skills/ai-orchestrator/SKILL.md:45 y :172 dicen "per the AGENTS.md git workflow", pero el AGENTS.md de este repo no tiene sección de workflow de git: solo tiene higiene de PR (título, lint y tests antes de commit). El agente busca un contrato que no está escrito.
  • La orquestación trabaja en el árbol compartido. ai-orchestrator Fase 0 hace git switch -c feat/<slug> en la carpeta principal (línea 45) y exige "stage explicit paths only ... because other sessions share this tree" (línea 46). Ese comentario es la prueba de que ya hubo dolor: sesiones peleándose por el mismo git add.
  • El cierre de sesión no es el que quieres. ai-orchestrator hace git merge --squash feat/<slug> contra la rama grabada en Fase 0 (línea 172), que no es main, y conserva la rama para siempre.
  • La limpieza no cubre worktrees. La ai-git-cleanup actual borra ramas locales; los worktrees aparecen solo como inventario y como bloqueo (WORKTREE_HELD). Con worktrees por sesión, eso se convierte en basura acumulada.
  • Dos skills no dan lo que quieres. ai-pr-loop-fix arregla CI sin crear PR ni fusionar (queda cojo), y ai-git-cleanup obliga a una pregunta interactiva y no gestiona worktrees.

03Para quién es

Para ti, soydachi, cuando lanzas una o varias sesiones de agente sobre este repo (o sobre un proyecto gobernado por ai-engineering) en paralelo o en secuencia. Tú eres el único que decide cuándo algo sale a origin, y el único que aprueba cada fusión a main local. El segundo destinatario es el agente de la siguiente sesión: necesita saber sin preguntar dónde trabajar y dónde fusionar.

05Cómo se ve el éxito

Cada criterio se comprueba con un comando o mirando un fichero. Sin adjetivos.

  1. ai-eng worktree new <slug> deja el árbol principal intacto, crea <repo>.worktrees/<slug> con la rama del slug, y esa rama queda con branch.<slug>.remote="." y merge=refs/heads/main. Se comprueba con git worktree list y git config --get branch.<slug>.merge.
  2. Al cerrar la sesión, el main local contiene el trabajo (un merge commit por sesión), y la rama y el worktree ya no aparecen en git worktree list ni en git branch.
  3. Ningún comando de la sesión empuja: git log origin/main..main muestra exactamente lo que faltará por subir, y origin/main no se mueve hasta que el humano lanza ai-pr.
  4. ai-git-cleanup en una pasada deja cero ramas fusionadas y cero worktrees muertos, y deja intactas las ramas sin fusionar: git branch --delete-merged refs/heads/main deja de encontrar candidatas.
  5. ai-pr termina con un PR fusionado y su número en el reporte, o con el PR abierto y el motivo de no fusionar.
  6. Los gates del repo pasan: bun test, bun run typecheck, bun run lint, y bun run arch sigue verde.
  7. La documentación queda al día y se comprueba por fichero: AGENTS.md con la sección de git, CONTRIBUTING.md con el flujo local, README.md nombrando el verbo nuevo, NOTICE.md y THIRD-PARTY-NOTICES.md sin la atribución que ya no se usa, y un changeset minor presente en .changeset/.

06Decisiones ya tomadas

Fijadas por el humano, el plan no las reabre

  • Sesión que escribe código = worktree con rama propia. Sesión que solo mira (triage, research, auditoría, brainstorm) = sin worktree.
  • Decisión A: una sola rama de largo recorrido, main local. Cada sesión fusiona ahí y su rama efímera desaparece. Cuando el humano decide, corta una rama nueva desde main local (sin worktree), la empuja y abre un PR que arrastra todo lo que main tenga por delante de origin/main, sea una sesión o cinco.
  • Decisión A′ (el worktree nace para construir, no para diseñar). El diseño se escribe en el árbol principal y se commitea a main local antes de cortar cualquier worktree; el worktree se corta de ese main y solo construye. Un worktree es uno por slug (una feature, una corrida de /ai-orchestrator), y esa corrida puede retomarse en varias sesiones de conversación sin abrir otro: /ai-orchestrator resume <slug> vuelve al mismo worktree, porque el estado vive en workflow/checkpoints/<slug>.json (skills/ai-orchestrator/SKILL.md:27) y la rama es feat/<slug> (:45, "or git switch feat/<slug> on resume"). El merge a main local es uno por slug, al cerrar la corrida. Y las cinco reglas de conflicto de §08: diseño secuencial fuera de los worktrees, artefactos de sesión con el slug en el nombre, compartidos escritos por el paso de merge, rebase dentro del worktree y luego merge --no-ff desde main, y aviso de solape al crear.
  • "Sesión" no es una pestaña. Una sesión de conversación puede retomar el mismo slug, o abrir el worktree de otro slug distinto. Lo que abre worktree es un slug que va a escribir código, no el acto de abrir una pestaña. Un feature que no cabe se parte en slugs (slices), y cada slice tiene su worktree: ahí sí hay varios en paralelo, si son independientes.
  • Verbo nuevo del CLI para gestionar worktrees (no código suelto dentro de la skill).
  • Los worktrees viven en <repo>.worktrees/<slug>, hermanos del repo (aquí: /Users/soydachi/repos/ai-engineering.worktrees/<slug>). Fuera del árbol de trabajo, un directorio por proyecto, sin nada que añadir a .gitignore.
  • ai-eng git no se renombra. El verbo de hooks conserva su nombre; el renombre a ai-eng hooks queda fuera (§09).
  • El destino de la fusión es el main local. Nunca origin.
  • El PR a origin lo decide y lo lanza el humano después, desde el main local, y puede agrupar 1..n sesiones de worktree.
  • La rama del PR a origin se crea sin worktree.
  • Se borran ai-pr-loop-fix y ai-git-cleanup. Se rehace ai-git-cleanup desde cero: una sola skill, worktrees + ramas, automática y segura.
  • ai-pr hace el ciclo completo, con la fusión desactivable: corta la rama desde main local sin worktree, empuja, abre el PR contra main, vigila CI y comentarios, arregla lo obvio en iteraciones acotadas y fusiona. El cuerpo del PR se arma con los merge commits de las sesiones incluidas, para que un PR que agrupa varias se lea.
  • La documentación se entrega con la feature, no después: la lista exacta de ficheros y qué cambia en cada uno está en §11, y es criterio de éxito en §05.
  • Nace una skill ai-pr para crear el pull request (adaptando work-with-pr al modelo de ai-engineering).
  • Revisar qué vale de tech-debt-audit y remove-deadcode para ai-audit-code, y de security-research para ai-security.

08Límites y guardarraíles

  • Git prohíbe la misma rama en dos worktrees. Es la razón de que cada sesión tenga rama propia; sin eso, el segundo worktree que apunte a main es un error, no una elección.
  • Nunca --no-verify, nunca silenciar un linter (AGENTS.md). Los hooks corren igual dentro del worktree.
  • Ningún push desde una sesión. Ahead/behind son solo lectura.
  • Solo se borra lo fusionado. Nada sin fusionar desaparece sin una confirmación explícita del humano.
  • El árbol principal no se toca mientras una sesión corre: el worktree existe justo para eso.
  • Gate verde antes de "hecho": typecheck, lint y tests con la salida a la vista.
  • El diseño se escribe antes, el recap llega con el merge. brainstorm.html, spec.html y plan.html se escriben y se commitean en el árbol principal antes de cortar cualquier worktree. recap.html nace en la rama de la feature, en el app review, y PRD.html lo actualiza solo el paso de merge.

Cómo se evita el conflicto

La regla no es de tiempo, es de dueño del fichero: cada ruta tiene un solo escritor. Donde el dueño es el paso de merge, la sesión paralela no escribe ese fichero nunca.

  • Diseño secuencial, en el árbol principal: brainstorm.html, spec.html y plan.html son los que se commitean antes de cortar cualquier worktree (PRE_WORKTREE_SLOTS, src/shared-worktree.ts:20); ningún worktree los escenifica. recap.html no entra ahí: se genera en la rama de la feature y llega con el merge.
  • Lo de la sesión lleva el slug en el nombre: workflow/checkpoints/<slug>.json, test-plans/<slug>.json, prototypes/<slug>*, reviews/<slug>-*.md. Ya es así.
  • El recap no lo escribe el merge: recap.html nace en la rama de la feature, en el app review, y el merge solo lo arrastra al árbol principal.
  • Los compartidos los escribe el merge, no la sesión: CHANGELOG.md, LEARNINGS.md, FILEMAP.md, PERMISSIONS.md y PRD.html se actualizan una vez, en el árbol principal, cuando la sesión ya está fusionada. El merge a main es forzosamente secuencial: un solo índice, un solo checkout de main.
  • El conflicto se resuelve en el sandbox, nunca en main: antes de fusionar, la sesión hace git rebase main dentro de su worktree (la rama es efímera, rebasar es gratis); con el rebase limpio, el merge a main es git merge --no-ff y no puede fallar.
  • La ruta del worktree se resuelve canónica: <repo>.worktrees/<slug> se calcula uniendo el directorio padre real del repo con <nombre>.worktrees, y se compara siempre en forma canónica (realpath). En macOS /tmp es un symlink a /private/tmp y git worktree list devuelve la forma canónica: comparar cadenas sin canonicalizar fue lo que apareció en las pruebas de hoy.
  • El directorio es un valor con escapatoria: por defecto <repo>.worktrees; si el padre del repo no es escribible (CI, checkout en la raíz de un volumen), config.toml puede apuntarlo a otro sitio. Es el único ajuste que necesita el "sirve para cualquier SO y cualquier proyecto".
  • Aviso de solape al crear: ai-eng worktree new compara las rutas declaradas por la sesión contra las de los worktrees ya abiertos y avisa. Dos sesiones sobre el mismo fichero es el único conflicto que git no puede resolver solo, y se evita antes de empezar.

09Fuera de alcance

No entra

  • Renombrar ai-eng git a ai-eng hooks: cosmético, toca los shims instalados (§04) y va como feature aparte si algún día se quiere.
  • Borrar ramas remotas. git push origin --delete no se usa, nunca.
  • Fusionar o cerrar PRs por iniciativa del agente sin que el humano lo haya pedido.
  • Sustituir el sistema de spec/plan/checkpoints por git: git es transporte, no proceso.
  • Reescribir ai-security o ai-audit-code enteros: solo piezas sueltas.
  • Rebase interactivo, historia reescrita, git gc.

10Preguntas para investigar

  1. resuelta ¿Existe --delete-merged? Sí, en git 2.56.0, pero no dispara sin upstream: la limpieza usa --merged + -d. Queda abierta la variante de abajo.
  2. ¿El framework puede exigir git ≥ 2.56, o tiene que funcionar con el git de Apple (2.50.1) que muchos tendrán? Importa porque decide si un verbo nuevo puede usar flags recientes o solo los de 2.25.
  3. ¿Los hooks de este repo (el "floor" de ai-eng) funcionan igual dentro de un worktree, o hay rutas absolutas que asumen el árbol principal? Importa porque el gate de commit correría distinto en la sesión.
  4. ¿Qué workflow de los siete es el gate real de un PR a main, y cuáles son informativos? Importa para que ai-pr espere Lo correcto.
  5. ¿El repo exige merge commit en origin (nada de squash) y branch protection con PR obligatorio? Importa para que ai-pr no emita un comando que origin rechace.
  6. ¿ai-eng spec close barre brainstorm.html y recap.html desde qué ruta (árbol principal o worktree), ahora que los artefactos pueden nacer en el worktree?

Dónde se revisa la documentación

En tres capas, y solo la primera obliga de verdad.

  1. Como gates ejecutables del plan de checkpoints. Cada checkpoint lleva verify (comandos) y acceptance, y el hook del checkpoint se niega a pasar un gate fuera de orden (skills/ai-orchestrator/SKILL.md:27). El precedente ya está en este repo: el plan de ai-git-cleanup verifica la documentación con comandos, no con prosa (.ai-engineering/workflow/test-plans/ai-git-cleanup.json:144 → rg -q 'ai-git-cleanup' NOTICE.md && rg -q 'CC BY-SA 4.0' NOTICE.md; y :193 → test -f .changeset/ai-git-cleanup.md && rg -q 'minor' .changeset/ai-git-cleanup.md). La tabla de §11 se traduce a una línea verify por fila, en el checkpoint que cambia la interfaz.
  2. En el paso de cierre del run. skills/ai-orchestrator/SKILL.md:153-155 ya escribe la entrada de CHANGELOG.md, revisa FILEMAP.md y actualiza PRD.html. Ahí cae también el changeset.
  3. En ai-pr, no revisando la doc, sino exponiéndola: arma el cuerpo del PR con la evidencia de lo que corrieron los gates. No es un revisor de documentación y no debería serlo.

CI no cubre documentación, y conviene saberlo

grep -rn changeset .github/workflows solo encuentra version.yml (changesets/action, que consume los changesets pendientes) y release.yml: ningún workflow falla por un changeset ausente. Y check.yml corre typecheck, lint, tests, arch, doctor, gitleaks, semgrep, trivy, bun audit, SonarCloud y Snyk: ninguno lee prosa. Por eso "documentación al día" tiene que ser gate de checkpoint, no confianza en el PR.

Decisiones de implementación ya fijadas

  • Esta feature no puede estrenar su propio flujo. El primer build ocurre en el árbol principal, porque el verbo y las skills que lo habilitan son justo lo que se va a construir. El árbol principal está hoy en feat/arcasiles-skills con trabajo sin commitear: la primera sesión de este feature aterriza donde el humano decida, y desde el segundo checkpoint en adelante ya puede usar el worktree.
  • Primitivo de limpieza: git branch --delete-merged refs/heads/main funciona si la rama efímera nace con branch.<x>.remote="." y merge=refs/heads/main: borra lo fusionado en main local y salta solo lo retenido por un worktree y lo sin fusionar. Reserva para ramas sin ese upstream: --merged main + -d.
  • Borrados y sus arrastres: se van skills/ai-pr-loop-fix/ y la vieja skills/ai-git-cleanup/ (esta última se rehace). Ninguna otra skill las nombra, pero sí las referencian src/assets.ts (regenerar), los tres tests/git-cleanup-*.spec.ts, y NOTICE.md más THIRD-PARTY-NOTICES.md.
  • Pieza de tech-debt-audit que sí vale: la disciplina de citar file:line y la sección "Looks bad but is fine"; la auditoría de 9 dimensiones no cabe en ai-audit-code, que es la escalera de pereza.
  • Pieza de remove-deadcode que sí vale: el guardarraíl anti-falsos-positivos y la verificación LSP antes de borrar (xd://lsp).
  • Pieza de security-research que sí vale: "no hay severidad sin camino de ataque" y el equipo cazador/PoC separado del validador; ai-security ya lo tiene, y ya tiene ledger findings.json: probablemente solo un par de frases.
