02Risk & parallelism

Jobs: steps 4, 5 and 6 all write src/commands/doctor.ts and src/spec/index.ts — they run in that order, never in parallel. Step 10 must be last before the suite: regenerating assets from a half-edited skills/ plants a tree that does not match the binary. Step 11 runs alone, after every gate has a receipt.

Steps 1, 2, 3, 7, 8, 9 are safe in parallel — disjoint files, except that step 1 must not write skills/ai-brainstorm/SKILL.md (step 3 owns it) or skills/ai-plan/SKILL.md (step 7), and step 2 owns tests/skills.spec.ts alone.

Risk: the canon test is the product's own floor. A G9-G14 that is loose makes the whole graph decorative. The rollback is one line per gate — revert the block, not the file.

Risk: twenty blocks written by hand drift from each other. The vocabulary is closed on purpose — three lane names, a fixed set of trigger ids, artifact paths taken from §21.1 — so the canon can reject an invention instead of reporting a typo as a design.

Risk: the trigger globs will be wrong the first time. They are declared by the node that owns them, so a wrong glob is a one-line fix in one skill; the evaluation code never hardcodes them.

Risk: spec close becoming stricter breaks existing repos mid-milestone. It only refuses on the artifact it already claims to check; a milestone with all gates evidenced is unaffected.
