Brainstorm · local worktree lifecycle

Un hub local, estados fiables

Un centro local reúne los worktrees de los proyectos configurados y muestra su estado con evidencia de Git y checkpoints; antes de crear un worktree, la aprobación se proyecta desde el brainstorm aprobado.

01

La idea en palabras llanas

Un hub local descubre proyectos bajo las carpetas elegidas en Settings. Muestra sus worktrees y estados. Al abrir una feature, presenta su viewer actual. Cada estado depende de evidencia local, no de una suposición.

02

Por qué importa

Un worktree queda como Unknown si Git o su checkpoint faltan, no coinciden o no se pueden validar. Es más seguro mostrar la incertidumbre que inferir actividad a partir de una rama o un proceso abierto.

03

Para quién es

Para quien coordina proyectos y sesiones de agentes en una máquina y necesita saber qué está activo, qué espera revisión y qué se cerró.

04

Qué existe hoy

  • El CLI del repositorio incluye ai-eng worktree list [slug] para revisar el estado y request-changes <slug> <sha> para devolver una revisión pendiente sin sobrescribir cambios concurrentes.
  • Los worktrees existentes se clasifican a partir de Git y de workflow/checkpoints/<slug>.json. Si falta evidencia válida o no coincide con el worktree, el estado es Unknown.
  • Antes de crear el worktree, la aprobación se proyecta en modo lectura desde el brainstorm exacto, reciente y aprobado; no se escribe un registro lifecycle previo.
  • La opción de archivos de worktree new guarda pistas de solapamiento en .ai-eng-worktrees.json, fuera del repositorio. Son advisory: no autorizan trabajo ni sustituyen el checkpoint.
  • El experimento anterior con .ai-eng-lifecycle se retiró durante la integración para evitar dos fuentes de estado.
05

Cómo se ve el éxito

  1. Una sola instancia local descubre las raíces elegidas y se reutiliza si ya responde.
  2. La lista identifica cada proyecto y agrupa sus worktrees por estado. La selección abre el viewer correspondiente.
  3. El checkpoint registra las transiciones del worktree; los cambios con revisión pendiente usan su SHA completo para evitar actualizaciones obsoletas.
  4. Un checkpoint ausente, ambiguo, obsoleto o incompatible se muestra como Unknown; las pistas de archivos nunca cambian esa decisión.
  5. La aprobación humana del brainstorm permite iniciar; la revisión humana final sigue siendo necesaria antes del merge y la limpieza.
06

Decisiones ya tomadas

Fuente de estado

Git y el checkpoint gobiernan los worktrees existentes. Antes de crear uno, el brainstorm aprobado es evidencia de inicio de solo lectura; no hay un registro lifecycle paralelo.

Aprobaciones

La aprobación humana del brainstorm permite iniciar. Las pistas de archivos no aprueban trabajo; merge y limpieza conservan su revisión humana final.

Independencia

Cada feature mantiene su brief en .ai-engineering/workflow/features/<slug>/brainstorm.html. Los cambios se hacen en su worktree.

Descubrimiento

El hub es local, consulta Git y respeta la raíz de worktrees configurada. No deduce actividad por la rama o un proceso abierto.

07

Decisiones todavía abiertas

  • El inventario se actualiza al iniciar y bajo demanda; no mantiene observación continua.
  • Settings ofrece selector nativo y permite rutas pegadas, ambas con validación visible.
  • Solo se abren documentos canónicos de una allowlist; no se abren prototipos ni archivos parciales.
08

Restricciones y guardarraíles

  • El hub escucha solo en loopback y no hace merge ni elimina worktrees.
  • Ni el checkpoint ni las pistas de archivos conceden aprobación; solo la aprobación humana del brainstorm permite iniciar.
  • Git y el checkpoint son autoridad para worktrees existentes. Las pistas opcionales quedan fuera del repositorio y solo advierten de solapamientos.
  • El hub no hace merge ni elimina worktrees. Los errores al actualizar estado se muestran explícitamente.
09

Fuera de alcance

Coordinación entre máquinas, inferir actividad por procesos o ramas, y controlar merge o limpieza desde el hub.

10

Investigar antes de cerrar

  1. Publicar y actualizar el CLI que incluye los comandos de worktree; verificar la versión instalada antes de depender de ellos.
  2. Probar el lector con raíz predeterminada y worktrees_dir personalizado, incluyendo worktrees prunables.
  3. Confirmar cómo se comparte el puerto del hub entre proyectos y cómo se recupera una instancia que no responde.
11

Handoff

El hub y los ajustes globales se implementan en este repositorio. Los checkpoints lifecycle sí se versionan; el registro paralelo se retiró. La integración y la limpieza siguen fuera del hub y requieren revisión humana.

Distribución: la versión publicada puede no incluir todavía los comandos de worktree; verificar y actualizar el CLI instalado antes de depender de ellos.
