## F1 · MINOR · fixed
**Where:** src/git/run.ts:90-95
**Critic (r1):** The commit identity is built only from `user.name`/`user.email`. Git's own `author.name`, `author.email`, `committer.name` and `committer.email` keys, and the `EMAIL` environment fallback, are ignored. Probe: with repo-local `author.email = repo-author@x`, the merge commit is authored as `local@x`, while plain git would use `repo-author@x`. With `EMAIL` set and no `user.email`, the verb refuses where git would commit. → Resolve each variable the way git does: `GIT_AUTHOR_*` env, then `author.*`, then `user.*`, then `EMAIL` for the email; committer likewise with `committer.*`. Add one test for local-over-global precedence and one for the missing-identity refusal (run.ts:97), which no test covers yet.
**Fixer (r1):** fixed — `commitIdentityEnv` no longer reads `user.*` itself; it asks git with `git var GIT_AUTHOR_IDENT` / `GIT_COMMITTER_IDENT` (normal config and env, repository-relocating variables still dropped) and passes the parsed name and email through, so git's own precedence applies: `GIT_*` env, `author.*`/`committer.*`, `user.*`, `EMAIL` (src/git/run.ts:71-99). Where `git var` fails, it refuses with git's reason and the `user.*` fix. Regressions: tests/worktree-command.spec.ts:4405 (two cases: repo-local `author.*` over global `user.*`; `EMAIL` with no configured email — both failed before the fix) and :4427 (missing-identity refusal under `user.useConfigOnly`, nothing changed). Note: setting `author.email` makes git stop falling back to `EMAIL` for the committer (git's own `ident_config_given` quirk); passing `git var` through reproduces that faithfully. · verify: `bun test tests/worktree-command.spec.ts tests/git-context.spec.ts tests/floor-hooks.spec.ts tests/floor-gates.spec.ts tests/arch.spec.ts` ✓ (267 pass / 16 skip / 0 fail), `bun run typecheck` ✓, `bun run lint` ✓, `bun test` ✓ (1685 pass / 16 skip / 0 fail)

## F2 · MINOR · fixed

**Critic (r1):** `worktree rm` catches every `namedBase` error, including an unparseable config.toml and an invalid `[git] base`, and reports "no base branch is detectable; set [git] base". R8 says a read failure is not absence. "no base branch is detectable" is now reserved for a base that is genuinely absent. ## F4 · MINOR · fixed
**Where:** src/git/context.ts:96 (consumed at src/floor/index.ts:171-176)
**Critic (r1):** This predates the checkpoint, but it is a way a base push still slips through. `[git] base = "origin/main"` passes `check-ref-format --branch`, so the guard protects `refs/heads/origin/main` while a push to `refs/heads/main` passes. The base is also read from the working tree's config.toml rather than HEAD, so an uncommitted edit to `[git] base` moves the guard. → Reject a configured base whose first path segment names a configured remote, telling the person to write `main`. **Fixer (r1):** fixed — `configuredBase` now normalises the value through `localBranchName` before validating it (src/git/context.ts:97, :100-119): `refs/heads/<b>` → `<b>`; `<remote>/<b>` and `refs/remotes/<remote>/<b>` → `<b>` when `<remote>` is a configured remote (longest match, since remote names may contain `/`); a `refs/remotes/` ref whose remote is not configured throws, so the guard denies (R8); anything else is kept, so a real local branch such as `release/2.6` is untouched. Every consumer (`resolveContext`, `namedBase`, the pre-push guard) reads the base through this one function, so src/floor/index.ts needed no change.
