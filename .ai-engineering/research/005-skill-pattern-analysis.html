02Patrones detectados

2.1 — El loop /ai-goal consume masivo de tokens

Frecuencia: 9/30 sesiones top (batch 1) + 5/27 sesiones (batch 3). Patrón dominante.

El usuario invoca /ai-goal con una lista de repos o un spec → el agente planifica sub-goals → el loop ejecuta. El planning consume la mayoría de tokens. En session #13 (508 msgs), el usuario documenta frustración: "el llm me esta engañando y no está implementando todo lo que en research, spec, plan y sobre todos me prometió en goal".[4]

Problema: El agente dice que va a hacer X pero no lo implementa completamente. No hay verificación post-loop que compare "claimed done" vs "actually changed".

Oportunidad de automatización

Pre-flight validation: verificar que el plan mapea a los gates del spec. Post-loop diff check: comparar deliverables declarados vs archivos realmente cambiados.

2.2 — Continuación de sesiones: "okay, seguimos así"

Frecuencia: 20/90 sesiones necesitan "continua" o "como vamos?" manual.

La mayoría de sesiones son continuaciones de trabajo previo, no starts frescos. El agente reconstruye el estado completo desde cero cada vez — re-lee specs, planes, contexto. Los thinking blocks muestran al agente redescubriendo cosas que ya debería saber.[5]

Problema: Cada continuación gasta 30-50 mensajes reconstruyendo estado. Session 0 (spec 010) consumió 7,702 mensajes solo para reportar el estado de un spec.[2]

2.3 — "Como vamos?" spam en sesiones largas

Frecuencia: 5+ veces en una sesión (session #2 con 731 msgs).

El usuario pregunta "como vamos?" repetidamente porque no hay progress reporting automático. La sesión más larga con 42 compactions (session #2, 930 msgs) muestra al usuario inyectando file paths mid-run para mantener al agente encarrilado.[3]

2.4 — Subagentes "Complete assignment thoroughly"

Frecuencia: 346 subagentes dispatchados con UNO solo prompt template a través de 53 parents.[6]

El patrón es siempre el mismo: una sesión madre lanza subagentes con instrucciones de tipo Complete assignment thoroughy: # Target ... # Files ... # Do NOT edit. Cada subagente hace su trabajo y entrega findings. Incluye: prose audits, comment audits, code audits, doc rewrites.

Problema: Esto es exactamente lo que debería hacer un skill automatizado, no cadenas manuales de subagentes.

2.5 — Skills desde ~/Downloads

Frecuencia: 3+ sesiones con Usa skill: /Users/soydachi/Downloads/X/SKILL.md.

El usuario tiene skills "en borrador" que nunca formaliza: unlazy, handshake, model-router. Cada vez que los quiere usar, los lee de ~/Downloads manualmente.[7]

2.6 — CI/CD loops manuales

Frecuencia: 5+ sesiones con fix → commit → push → PR → loop green → merge.

Sesión #6 (496 msgs) muestra 316 bash calls, con CI polling vía sleep 60/75/90; gh run… repetido decenas de veces. El release v2.0.0-rc.1 tuvo que hacer tag → prerelease → npm publish → GH environment release con required reviewers — todo manual.[8]

2.7 — Auditoría de docs manual

Frecuencia: 7/27 sesiones (batch 3) son audits de status/architecture.

El usuario pregunta "¿qué tiene este proyecto?", "audita", "verifica" repetidamente. Cada sesión lee los mismos 5-10 archivos core (CONSTITUTION.md, AGENTS.md, blueprint.html, justfile, chain/mod.ts). Session #6 (790 msgs) mapeó manualmente CLI output vs blueprint mockup — 29 tool calls, 45k tokens.[9]

2.8 — Porting inter-plataforma

Frecuencia: 3+ sesiones (Graft hooks to Pi, Graft statuline, secret classifier port).

El usuario evalúa constantemente si features de un platform funcionan en otro. Sesión #17 (478 msgs) instaló Graft globalmente across omp/pi/claude y creó PR. Sesión #28 (314 msgs) debugueó por qué Graft statuline no aparecía en omp.[10]

2.9 — Claimed-vs-done friction

Frecuencia: Múltiples sesiones.

"estas cosas los hiciste o lo estás proponiendo?" — el usuario no puede distinguir entre lo que el agente planeó vs lo que realmente implementó. Sesión #14 documenta esto explícitamente: el agente decía "hecho" pero los archivos no cambiaban.[4]

2.10 — Skill shopping cost

Frecuencia: 1 sesión con 10+ skills probados.

Sesión #8 (mega design, 363 msgs) usó impeccable, apple-design, ai-design, ai-design-audit, ai-visual-recap, shieldcn-badges, watch, ai-write… — 10+ skills en una sesión porque el router no elige bien en el primer intento.[11]

05Gaps críticos

Sin progress reporting

"como vamos?" spam (10+ veces en sesiones largas). El usuario no tiene visibilidad del progreso del agente. Solución: skill de status reporting automático.

Sin handoff entre sesiones

Conclusions se pierden. "okay, seguimos así" implica continuidad pero el agente no tiene acceso estructurado al estado previo. Solución: state-pull skill.

Sin claimed-vs-done distinction

El agente dice "hecho" pero los archivos no cambiaron. No hay verificación post-claim. Solución: diff-based proof skill.

Sin skill router óptimo

10+ skills probados en una sesión porque el router no elige bien. Solución: model-portfolio + router tuning.

Sin project health check unificado

Cada audit session re-invents la rueda. 7 sesiones lean los mismos 5 archivos core. Solución: ai-audit skill.

Sin skill lifecycle manager

Skills en ~/Downloads nunca se formalizan. No hay registry con lifecycle tracking (active/stale/dead). Solución: ai-skill-craft + registry.

06Direcciones

Dirección 1: Automatizar el overhead de sesiones

Los 3 candidatos de mayor ROI atacan el mismo problema: el usuario gasta tiempo en tareas repetitivas que el agente debería hacer automáticamente.

  • ai-session-inspector — automatiza este mismo análisis semanalmente
  • ai-release — elimina 7 pasos manuales de release
  • ai-cicp — elimina CI polling manual

Acción: Diseñar spec/plan de ai-release como primer candidato (mayor ROI inmediato, implementación media).

Dirección 2: Cerrar el gap claimed-vs-done

El problema #1 de satisfacción del usuario es que el agente "miente" sobre implementación. Esto erosiona confianza.

  • Pre-flight: verificar plan mapea a gates del spec
  • Post-loop: diff-based verification de deliverables declarados vs archivos cambiados
  • Progress reporting: updates automáticos sin que el usuario pregunte

Acción: Integrar verificación post-loop en ai-goal existente (no skill nuevo, mejora al skill actual).

Dirección 3: Formalizar el ecosistema de skills

Las skills en ~/Downloads nunca se formalizan. El ecosistema crece sin lifecycle tracking.

  • ai-skill-craft — scaffold automático de skills
  • ai-skills-lifecycle-manager — registry + lifecycle tracking
  • ai-init-verify — diagnostic post-install

Acción: Diseñar ai-skill-craft como segundo candidato (habilita la creación eficiente de los otros skills).

Resumen ejecutivo 
90 sesiones → 10 patrones → 10 skill candidates → 3 direcciones

ROI inmediato:
  1. ai-release          (7 pasos manuales → 1 comando)
  2. ai-goal improvement (claimed-vs-done verification)
  3. ai-skill-craft      (habilita creación de otros skills)

El gap más peligroso:
  El agente "miente" sobre implementación → erosiona confianza
  Solución: diff-based proof + progress reporting automático
