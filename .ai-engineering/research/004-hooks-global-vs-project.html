Can the hooks live on the machine
instead of in every repo?

Every surface ai-eng governs publishes a user-level hook location, so the per-project copy is a product decision, not a platform limit. What decides the question is blast radius, not capability: measured in this session, the guards already deny inside a repo they have never seen. Global placement moves the policy, not just the file.

00 · the decisionWhat changes depending on the answer

The question is not “can it be done” — it can, on seven of the eight targets. The question is which of two governance models ai-eng ships: declared governance (a repo opts in by carrying hook files, and git revert is the rollback) or ambient governance (the machine enforces policy in every repo the human opens, and the repo merely declares which surfaces apply).

Today: per projectMachine-level

Trust stepsper project (Codex hook review, Pi/OMP folder trust)once per machine for global extensions; Codex still reviews the hook once by hash

the short answer

Yes on the mechanism: Claude Code, Cursor, Codex CLI, OpenCode, Oh My Pi and Pi all document a user-level hook, plugin or extension location, and Copilot CLI already requires one (the repo has shipped a machine hook for it since §13). No on the current behaviour: the chain applies its policy whether or not the repo is governed, so a machine-level install today would police every repo on the machine. Global placement is therefore one small gate away — and that gate is a product decision, which is why it is not in the code.

02 · the measurementWhat actually decides it

Feasibility is not the constraint. Scope is. The guards do not ask whether the repo they are running in is governed — runChain resolves the repo, and then every guard in the table decides (src/chain/mod.ts:103, src/env.ts:27). Two probes, this session, in a repo with no .ai-engineering/ at all:

# /tmp/ungoverned — git init only, no ai-eng has ever run here
$ echo '{"tool_name":"Bash","tool_input":{"command":"git commit -n -m x"}, ...}' | ai-eng chain PreToolUse
[ai-eng] no-verify: git commit -n skips the git hooks, the floor every agent ... Run the command without it.
exit=2            # outside any repo at all: same deny, same exit 2

$ ai-eng git commit-msg /dev/null
the message does not follow the Conventional Commits convention: ""
exit=1            # and `ai-eng git pre-commit` exits 0 here only because there was nothing to check

So the hooks are not “this repo's hooks”. They are a policy that happens to be delivered per repo today. Install them on the machine and the same deny lands in the human's other repos — the ones they never governed, including someone else's clone with its own conventions:

consequence 1Deny everywhere

A machine hook that fails closed also denies on a broken machine: the binary off PATH turns every tool call in every repo into a hook failure. The repo already wrote that lesson down for the one machine hook that ships — “a machine-wide hook that fails closed with a missing binary denies every tool call in every repo”.

tests/surfaces.test.ts:224

consequence 2Conventions leak

Conventional Commits, the no-verify deny and the injection scan would apply in a repo whose team agreed to none of them. Today the per-repo copy is what makes “this repo is governed” true; on the machine, nothing does.

03 · intentWhat the repo already decided, and why

Per-project placement is not an accident of implementation; it is written down in three places and one test:

rule “only an explicit --global may write outside the repo”

The comment sits on installCanon itself. The machine side installs the canon and the mirrors because skills are machine-scoped; hooks were deliberately left out of it, with Copilot CLI as the single documented exception (its repo hook never fires).

src/surfaces/adapters.ts:81-85, :109-122

rule The ownership list puts settings per project

The blueprint's global/project split names .claude/settings.json, config.toml, overrides.toml, ai-eng.lock, arch.rules.json and the four contract files as per project, and “canon de skills, binario, caché de versión” as global.

docs/blueprint.html:696

rule core.hooksPath is actively unset

init writes the shims into .git/hooks and unsets any core.hooksPath it finds; uninstall reports reverting it. Redirecting git's hook directory was considered and refused — mostly for coexistence with husky, which does exactly that.

src/commands/init.ts:74-80 · §13.2

gap The one ambient hook is still unbuilt

§14.0a designs a machine-level SessionStart hook whose entire job is to detect an ungoverned repo and inject one line — the ambient hook, designed ambient-safe (an existence check, zero tokens when governed). No SessionStart exists anywhere in src/ today: the design that proves the pattern is unimplemented.

docs/blueprint.html:1138 · grep src/ for SessionStart → nothing

the counter-argument, in the repo's own words

Per-repo placement buys three things a machine install cannot: the hook is reviewable in a PR (it is governed code the team sees, not a local artefact), it is pinned to the repo (ai-eng.lock's sha256 + skills_min, which doctor checks), and git revert remains the rollback. A teammate who clones inherits nothing to install. Ambient governance loses all three silently, which is why “it is possible” and “it is right” are different questions.

04 · the git floorThe floor is a separate question with a native global answer

The git shims cannot be versioned — .git/hooks is not in the repository, so every clone starts without the floor and the repo's CI has to rebuild it (update --yes). That is the same class of gap the global mechanism closes natively, and git has had two ways to do it since 2.9: core.hooksPath in ~/.gitconfig points every repo at one hooks directory, and init.templateDir makes new clones be born with the shims already in .git/hooks [10][11].

cost 1A repo-local hooksPath wins

husky and pre-commit both set a repo-level core.hooksPath; repo config beats global config, so in those repos the machine hooks simply do not run. pre-commit needed an explicit --allow-global-hooks flag for the mirror-image problem [12].

cost 2hooksPath replaces, it does not add

When core.hooksPath is set, $GIT_DIR/hooks is ignored — the repo's own hand-written hooks stop running unless the global directory dispatches to them. That is a dispatcher to maintain, not a file to drop in.

cost 3Details that bite

Only executable files run; push-side hooks execute in $GIT_DIR, so a global pre-push must not assume the worktree is the cwd. --no-verify remains the universal bypass either way — which is why the no-verify guard exists at all.

Reading: for the git floor the global mechanism is the native one and the per-repo shim is the workaround; for the agent surfaces the per-repo file is equally native and the machine file is the addition. The two families should be decided separately, and today they are decided the same way by inertia.

06 · the designThe hybrid: one carrier on the machine, the declaration in the repo

The two models are not exclusive. The ergonomics of the machine hook and the semantics of the repo hook can coexist if the hook is machine-level and inert unless the repo declares itself — which is what .ai-engineering/config.toml already is, and what the chain does not yet check:

the gate, in one shape 
// before any guard decides anything (src/chain/mod.ts:103 area)
const root = repoRoot();
if (root === null || !existsSync(join(root, ".ai-engineering", "config.toml"))) {
  return allow;   // an ungoverned repo is not this tool's business — the same shape as the §14.0a nudge
}

With that gate, moving the seven surface hook files to their user-level locations becomes a placement change, not a policy change: config.toml still decides whether and on which surfaces a repo is governed, the lock still pins the version, and init stops writing hook files into the repo at all. The git floor stays the way it is (marker-managed shims, husky-compatible) until someone wants clones to be born governed, which is the init.templateDir question and a different trade.

direction 1Gate, then move

Add the governed-repo gate to chain, then install the surface hooks at the user-level locations in §01. Evidence it is viable: Codex loads user hooks even in untrusted projects, Pi/OMP global extensions skip the project-trust step, OpenCode loads the global plugin dir at startup [6][7][8][9].

src/chain/mod.ts:103 · src/env.ts:80-84

direction 2Ship the nudge first

Implement §14.0a's machine-level SessionStart hook — it is designed ambient-safe (existence check, one injected line, zero tokens when governed) and it is the smallest possible test of the whole ambient model: if a machine hook can be trusted to stay silent, the bigger move is defensible.

direction 3Decide the floor on purpose

Every clone today starts without the git floor (.github/workflows/check.yml:43 exists to fix that after the fact). Choose: keep per-repo shims, or set init.templateDir so clones are born governed — and record which, because “the global hooksPath wins” is false in any repo using husky [10][12].
