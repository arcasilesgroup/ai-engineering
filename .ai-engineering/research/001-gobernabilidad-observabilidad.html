Receipts are gitignored (.gitignore:7): the trail is machine-local, never shared, so a teammate's attack is nobody's signal but their doctor's.

02The gap, against the framework the market converged on

OWASP's Top 10 for Agentic Applications 2026 (published 2025-12-09 [1]) foregrounds exactly two design principles before any of its ten items: least agency and strong observability [2]. Their one-line verdict is the thesis of this report:

OWASP, first principles

"Least agency without observability is blind risk reduction…
Observability without least agency is just surveillance."

ai-engineering has the first half nearly complete and the second half as a counter. Cross-check of the ten ASI risks against what this repo actually does:

The pattern: every missing signal is a question that already has its raw data in .ai-engineering/receipts/ — guard name, tool, surface, ts, outcome. The framework doesn't need new sensors; it needs the sensors it already has to outlive the 30-day delete.

03External evidence — what the 2026 state of the art does

  • OWASP Agentic Top 10 (2025-12-09) [1][2]: least agency + observability as the two first principles; ASI06 defines memory poisoning as a cross-session detection problem, ASI10 rogue behaviour as a baseline-deviation problem. Detection language for defenders is explicit: "spike in API usage, unexpected tool chaining" = ASI02 [2].
  • The market moved from guardrails to ADR. Miggo launched "Agentic Observability, Detection and Response" as runtime defense [3]; Sweet Security sells "AI runtime monitoring: beyond APM and pre-deployment testing" [4]; Metoro monitors agents via eBPF at the syscall layer [5]. Note [5]: the observability community is abandoning content-pattern matching — the exact class injection.ts belongs to — for system-level signals, because patterns are the weakest rung. This is the case for ai-eng keeping its patterns but adding the behavioural layer beneath them.
  • Academia agrees the stopper alone is a losing game. CaMeL (arXiv:2503.18813, Google DeepMind) secures agents by system design — control/data-flow extraction plus capabilities at the tool-call boundary — because no input filter reliably catches injection [6]. LlamaFirewall (arXiv:2505.03574, Meta) is a layered runtime scanner (prompt/probing/alignment — the alignment monitor reads the agent's own reasoning trace, a behavioural signal) [7]. Neither paper suggests longer pattern lists.
  • OTel GenAI conventions [8]: third-party agent dashboards (the blueprint's own named outsources — AgentsView, Phoenix/Langfuse) consume gen_ai.* attribute names over OTLP. The conventions were being restructured into their own repo at time of check (ctx7 result was marked deprecated), i.e. still a moving target — see R3.

04Three directions worth taking — cited, small, invisible

R1 · Aggregate what gc throws away ~15 LOC · src/receipts.ts

Catches: ASI02, ASI10. Kills: blind risk reduction. Extend summarizeReceipts() (receipts.ts:58–86) from 4 numbers to the ones already in every receipt: per_guard_denies, per_tool, per_surface, and a 7-day day-by-day deny series. doctor --gc writes the richer summary into summary.json (doctor.ts:432–434) instead of the flat four — the aggregate outlives the raw files, so the baseline survives every 30-day sweep. Doctor's receipts check adds one deviation rule: 7-day deny series > 3× the prior mean → WARN naming the guard. The ceremony stays zero: all computation happens inside the gc pass the user already opted into; a quiet repo sees one unchanged line. Same pass fixes fact 1 above — count tool:"unknown" denies as their own bucket.

```mermaid flowchart LR A[runChain] -->|every call| B[receipts/*.json] B -->|doctor --gc today: 4 numbers| C[summary.json] B -->|R1: richer aggregate| C C -->|R2: fingerprint ledger
survives gc| D[(denies.json)] D -->|deny annotation| A C -->|R1 deviation WARN| E[doctor] C -.->|R3 opt-in shim| F[AgentsView / Phoenix] ```

R2 · A cross-session deny ledger, one file ~10 LOC net · src/chain/mod.ts

Catches: ASI01, ASI06, ASI08. Kills: the "across sessions" blind spot OWASP names for both. The fingerprint already exists (fingerprint(payload), chain/mod.ts:146) and the loop guard already counts denials per session (loop.ts:18). On every deny, add fp → count to .ai-engineering/receipts/denies.json (gitignored, gc-safe: it is the aggregate). When a fresh deny's fp has count > 0, the receipt gets "repeat": N and the human-facing message appends one clause: "this exact call has been denied N times before". It changes no verdict — pure signal, so it cannot break the loop its own guards govern (the failure mode the self-protect header at :1–13 warns about). A memory-poisoning campaign that retries the same exfiltration call from a new session is now visible for the first time.

R3 · Make the receipts readable by the tools the blueprint already points at ~40 LOC · optional

Catches: nothing new; buys the whole ADR ecosystem without owning it. The blueprint's "no observability of our own" stance (blueprint.html:452) stays intact — it just stops costing optionality. Bump schema: "urn:ai-eng:receipt:2" → 3 aliasing the field names to the OTel GenAI conventions (tool → gen_ai.tool.name, surface → gen_ai.agent.name) [8], plus one config.toml line: [observe] otlp_endpoint, off by default, ~20-line POST shim on the gc pass (batch, never hot path — the 50 ms ceiling is untouched). Users who never set it see nothing; users who did get their guard chain inside AgentsView or Phoenix for free. Caveat dated 2026-09-20: the GenAI conventions were mid-repo-move at check time, so alias now and verify against semantic-conventions-genai before shipping.

Honourable mention — the silent fold miss, ~6 LOC

injection.ts:35–40 matches only the ASCII-folded text and the file says a non-ASCII-alphabet homoglyph won't match. Cheap observability: when the raw text hits a pattern the folded text missed, log one line into the gc'd daily aggregate. Evasion attempts become visible as a trend without ever changing a verdict — the "see overreach, don't re-scan" move the eBPF crowd makes with far more machinery [5].

05Rejected — and the line that made it easy

The design brief: quality/security/governance that doesn't look like it's there. Test each rejected item: does it add a stopper the agent can collide with, a runtime dependency, or a UI? All three rejections fail that test:

  • OTel SDK as a dependency / full tracing exporter — ai-engineering is one binary, zero runtime deps (blueprint §"Sin dependencias de runtime"). R3's plain-JSON POST keeps the door open without walking through it. Revisit when someone actually pipes receipts to a dashboard and the shim chokes.
  • An LLM alignment monitor (LlamaFirewall-style, [7]) — a second model in the hot path breaks the 50 ms ceiling (doctor.ts:20) and the zero-deps rule, and the repo already routes judgment to a stronger model where judgment belongs: ai-verify, ai-security, the decide tier pin. The behavioral layer in this framework is the skills, not a service.
  • A new ai-eng observe verb / dashboards / a metrics server — anti-DRY and against the closed CLI-verb list; doctor is the only read surface by design. If R1+R2 signals ever outgrow a WARN line, the right move is ai-visual-recap drawing them, not a new command.

When this recommendation becomes wrong

If the dogfooded repo's deny rate stays flat at ~3% forever (103/3663 today), R1's deviation check is ceremony and the honest move is blueprint §10.2's own pre-committed cut: «si a los 3 meses los denies son 0, el producto es ceremonia» — shrink the guards, not the dashboard. Conversely, the moment ai-eng governs repos shared by many humans (the receipts become cross-org), gitignored local JSON stops being an audit trail and R3 stops being optional — ship the OTLP path then, with retention and redaction handled as a real data-policy question, not a shim.
