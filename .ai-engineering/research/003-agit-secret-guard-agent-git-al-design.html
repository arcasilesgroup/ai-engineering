¿qué entra en ai-engineering?

Adoptar (código): el clasificador de "secretos hablados" de agit-secret-guard, portado a TS como guard propio. gitleaks — que el floor ya ejecuta en pre-commit y pre-push [5] — ve sk_live_… y AKIA… pero no ve purple monkey dishwasher. El pack demuestra, con tests, que esa clase de secreto se detecta en el prompt del usuario antes de que la vuelta termine, y que ese timing es lo único que importa [1].

Adoptar (patrón, no código): los dos RFC de agent-git (docs/05 y docs/06) son el mejor escrito de threat-model + fail-closed que he leído en el dominio agéntico; calibran lo que ai-security ya exige ("nunca degradación silenciosa", src/floor/index.ts:64) con criterios concretos: sustitución antes de la formación del objeto, bóveda que falla cerrada, nunca un placeholder parcial [3][4].

Descartar: AL-Design. Nueve skills de diseño que chocan de frente con las ya instaladas (ai-design como router + stitch/high-end/impecable/hallmark/transitions…). Instalarlo crearía dos routers compitiendo por la misma ruta de trigger [9].

Condicional: agit como versionado de sesiones de agente. Es un producto serio (Rust, release pipeline CI-firmado, npm multiplataforma [2]), pero añade un hub externo, y su propio pack de guardia existe porque agit fuga secretos de baja entropía sin él [1]. Si algún día se quiere historia publicable de sesiones, se adopta junto con el guard, no solo.

03Fuente 1 — agit-secret-guard (pack local)

Qué es

Cuatro ficheros en ~/Downloads/agit-secret-guard: SKILL.md (6,3 KB, instrucción al modelo), scripts/secret_guard.py (17,1 KB — check · bootstrap · add · verify), hooks/agit_secret_hook.py (10,3 KB — hooks SessionStart + UserPromptSubmit de Claude Code) y tests/test_classify.py (unittest puro, sin tocar la bóveda) [1].

El problema que cierra: agit commit redacta valores registrados en la bóveda device-local en el momento del commit. Sus heurísticas encuentran claves con forma (sk_live_…, JWT) pero no una frase memorable. Registrar el valor en la misma vuelta en que aparece lo redacta; una vuelta tarde queda en los objetos git para siempre (agit revert borra de la vista, no del evidence log) [1].

Lo que está bien resuelto (y es transferible)

El clasificador, con tests que lo defienden

judge(key, value) decide qué par clave/valor es secreto; los tests fijan tanto los positivos (ADMIN_PASSWORD=purple monkey dishwasher se registra) como los negativos (changeme, ${VAR}, 6 bytes, anon keys públicas no) [1].

tests/test_classify.py:28-48 · scripts/secret_guard.py:192-215

Extracción del prompt, no del fichero

candidates(prompt) distingue valor citable exacto (auto-registra) de frase suelta (la pasa al agente como "primero registra esto"). Nunca imprime el valor ni lo pasa por argv.

hooks/agit_secret_hook.py:82-104 · tests:52-82

El timing como invariant

"Same turn, no exceptions. Never end a turn with an unregistered secret in it." El hook UserPromptSubmit corre antes de que empiece la vuelta del modelo: la protección no depende de que el modelo recuerde la skill.

SKILL.md:57-76 · README.md:22-25

verify contra objetos reales, no contra la vista

agit show hidrata placeholders en el dispositivo dueño, así que un leak y una sesión limpia se ven iguales ahí. verify grepea los objetos git con --text (los blobs de agit leen como binario a git grep -I).

README.md:70-76 · scripts/secret_guard.py:337-405

Lo que NO se puede adoptar tal cual

  • Todo el plumbing de bóveda es agit. register(), cmd_check, cmd_bootstrap, cmd_verify hablan con agit secrets … vía JSON [1]. Sin agit instalado (y aquí no está), el script no hace nada.
  • El hook está escrito para Claude Code. Escribe en .claude/settings.json con eventos SessionStart/UserPromptSubmit [1]. ai-engineering ya resuelve el multi-surface con su tabla de carriers [6] — el hook habría que reescribirlo sobre esa tabla, no instalarlo aparte.

La idea adoptable, destilada

Un guard de prompt propio: en el evento de prompt-submit (o pre-turn), correr un clasificador estilo candidates() sobre el texto del usuario y, si huele a credencial hablada, inyectar al contexto: "hay un posible secreto en este prompt — escríbelo en un fichero gitignored, no lo pegues en código ni en el commit". Eso funciona sin agit, protege repos git normales (donde el destino del secreto es el código, no el transcript), y cierra exactamente el hueco que gitleaks no ve. El clasificador es ~80 líneas de regex + stopwords: portar a TS es barato y los tests de test_classify.py se traducen casi 1:1 a bun test.

Leeído del README vía GitHub API [2]: binarios precompilados por os/cpu (Linux musl estático, matrix de contenedores antes de publicar), pipeline GitLab→mirror GitHub con tags inmutables y CI-creados, check-version.js que rechaza un bump sin sección de changelog. Es un proyecto con disciplina de release seria, no un weekend hack. No es evidencia de adopción masiva: 254★ es temprano, y el hub (agent-git.com) es un servicio externo cerrado (repo del servidor separado) [2][10].

Lo que vale para ai-engineering: los dos RFC

docs/05 — filtro global de secretos

Threat model explícito de lo que NO promete (proceso local comprometido, admin local, memoria de agitd); envelope encryption KEK/DEK con keystore OS o fichero 0600; Aho–Corasick en vez de regexes; "un vault que existe pero no se pudo abrir nunca es 'limpio'" — fail closed.

[3] docs/05_global_secret_filter.md §2-§7

docs/06 — placeholders reversibles por repo

La Joya: por qué la sustitución no puede esperar a git push — cambiar un blob justo antes del push reescribe cada OID (blob→tree→commit→tag) y rompe la identidad de versión. Por eso se sustituye antes de formar el primer objeto canónico, y push queda como backstop fail-closed. Placeholders versionados, sin SHA-256(secret) — "un digest determinista de un secreto de baja entropía es un oráculo de diccionario offline".

[4] docs/06_repository_secret_dictionary.md §2, §4

Qué transfiere a ai-engineering: no el código (Rust, otro dominio) sino el estándar de escritura: boundary primero, failure semantics por caso, "X no promete Y" antes de prometer nada. ai-security ya exige el principio ("never silent degradation", y el floor lo ejecuta: gitleaks ausente es HARD FAIL [5]); los RFC de agit son el mejor ejemplo de referencia que he visto de cómo se documenta eso cuando el control es de seguridad y outbound. Cita de calibración para el próximo ai-security run o para una entrada futura de DECISIONS.

Qué no transfiere: la arquitectura daemon (agitd como Secret Guard), el formato de vault, el hub. Son decisiones de su dominio (sesiones JSONL versionadas); ai-engineering no versiona sesiones, gobierna herramientas.

¿Adoptar agit como producto?

Solo condicional — y con el guard pegado

El caso de uso real para este repo sería historia compartible de sesiones (los receipts ya son un audit trail local gitignored [8]; agit añade versionado + share + resume). Pero:

  • dependencia nueva de un binario externo + servicio hub de terceros;
  • el propio pack existe porque agit fuga la clase de secreto más común (frases memorables) salvo registro same-turn [1];
  • ai-engineering es un framework que otros instalan — pedir agit a cada usuario del framework es un coste de instalación que el blueprint no contempla hoy.

Veredicto: vigilar. Si el framework algún día publica sesiones gobernadas, agit + guard es la pila candidata; hasta entonces, es peso muerto.

El hueco está dibujado con código real: dos puertas de gitleaks [5] que ven secretos con forma, y cero cobertura antes del commit para secretos hablados de baja entropía. El pack de agit demuestra que esa detección temprana es viable y testeable [1].

Encaje estructural: src/guards/ ya tiene el patrón (injection.ts compila regexes, policy.ts clasifica paths sensibles [5]); src/surfaces/surfaces.json ya documenta qué surface puede correr hooks a nivel prompt (Claude Code: settings machine-scope; omp: hooks/pre; codex/copilot: hooks.json) [6]. Un guard nuevo sería: clasificador TS en src/guards/spoken-secret.ts + tests en tests/ + wiring por carrier según la tabla. El work restante de investigación: confirmar qué evento recibe cada carrier (UserPromptSubmit de CC es seguro; omp pre-hooks se disparan por tool-call, habría que verificar si hay evento de prompt) verificar en PR.

Los tres cierres con dirección citada:

  1. Portar el clasificador same-turn — tests/test_classify.py:28-48 y secret_guard.py:192-215 [1] traducidos a TS; la prueba de que funciona es que los 10 negativos del test (changeme, anon key pública, 6 bytes) siguen sin disparar el guard en bun test.
  2. Verificar el evento de prompt en cada carrier antes de escribir wiring — Claude Code UserPromptSubmit documentado en el propio pack [1]; para omp/codex/copilot el evento correcto es una pregunta abierta que la tabla de carriers aún no responde [6] — mismo método que usó research/003/004: probe en vivo, fecha, evidencia.
  3. Si se evalúa agit de verdad, empezar por su threat model, no por su README — docs/05 §2 y docs/06 §7 [3][4] declaran lo que NO protege (backup de $AGIT_HOME, proceso local comprometido); cualquier adopción debe pasar ese filtro primero, igual que el guard local: "un vault que no se pudo abrir no es 'limpio'".

08Riesgos y desconocidos

  • Falsos positivos del clasificador son el riesgo real: registrar/avisar sobre una frase normal convierte cada mención futura en ruido. El pack lo acota con suelo de 8 bytes y stoplabels; el port debe mantener los tests negativos como contrato, no como decoración [1].
  • Ninguna afirmación de comportamiento de agit en vivo está verificada aquí — no hay binario en esta máquina. Todo lo dinámico (redacción same-turn, ~5 objetos por mención, dedup de bootstrap) proviene del README del pack, que declara su método de prueba [1].
  • agent-git 254★ = proyecto temprano [2]; su calidad de RFC no es evidencia de estabilidad de producto. El hub es closed-source por separado [2][10].
  • Cobertura parcial del guard propuesto: un prompt-submit hook solo ve el prompt del usuario; un secreto que el agente lee de un fichero y copia a otro sitio no pasa por ahí. Ese caso lo sigue cubriendo gitleaks en pre-commit — el guard es una capa antes, no un reemplazo.
