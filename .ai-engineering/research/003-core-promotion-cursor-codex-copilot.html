Can Cursor, Codex CLI and Copilot
become core surfaces?

The three tiers below core are not three flavours of the same gap. One of them is a bug in the allow path that the tier label was hiding, one is a one-time human trust step the vendor requires, and one is two different environments wearing one id. All three are closeable; only one of them needs the vendor to move first.

Tools used: local binaries + live probes (cursor-agent 2026.09.08, codex-cli 0.153.4, Copilot CLI 1.0.83, ai-eng 2.1.0) · web search + vendor docs (cursor.com, developers.openai.com, docs.github.com) · the repo's own tree
Tools absent: notebooklm (auth expired → deep tier skipped, no re-login attempted) · Codex end-to-end run (this machine's Codex account rejects every model id → documented, not measured)

00What changes depending on the answer

The decision behind this research: do we spend the next week promoting Cursor, Codex CLI and Copilot to core, or do we leave the labels alone and tell users what they actually get? The answer decides four things — whether init's picker stops warning, whether a surface may be offered without a caveat, whether the trust step becomes part of the install (and therefore part of doctor), and whether surfaces.json stays one entry per product or splits by execution environment.

Without that decision this would be reading, not research.

And the tier itself is only a label: tier is read in exactly one place — the picker grouping at src/commands/init-shared.ts:98 — and can.rewriteOut in exactly one place, the hint text at src/commands/init.ts:42-43. Nothing in the chain, the guards or doctor branches on either. So promoting a surface is not a code migration; it is a claim change that must be backed by a measurement, which is exactly how can.loopEvidence already works [9].

The honest reading of the current labels

“experimental — rewrite may be partial” and “best-effort — cloud FS” are statements about capability, and the capability fields beside them are already set: Cursor deny:true, rewriteOut:false, Codex deny:true, rewriteOut:"total-replacement", Copilot deny:true, rewriteOut:true. The label is the promise; the fields are the measurement. They are allowed to disagree — but not silently.

The Cursor finding, exactly

On allow, the chain prints nothing and exits 0 — chainMain calls runChain, writes the receipt, and process.exit(0) (src/chain/mod.ts:245-255); only the deny and rewrite paths write an envelope (src/chain/dialect.ts:35, :67). Cursor documents exit 0 with JSON output as the contract, and treats empty output as a failure on a hook whose failClosed is true [1] — which the shipped template sets (templates/settings.cursor.json.tpl). Measured: an allow-envelope-shaped hook passes, a silent one blocks, and the same silence blocks with failClosed unset (“a fail-closed hook that returned no output”).

the fix, verified end to end 
# stand-in for the one branch that would go into chainMain:
out=$(printf '%s' "$payload" | ai-eng chain PreToolUse --surface cursor 2>/dev/null)
if [ -z "$out" ]; then printf '{"permission":"allow"}'; else printf '%s' "$out"; fi

→ create-a-file prompt:  “Created `ok.txt` with the word `hi`.”   (was: blocked)
→ git commit -n -m x:    blocked, no-verify reason reached the model   (unchanged)

The Copilot hook-location finding, exactly

Probed twice at 1.0.83, headless (copilot -p … --allow-all-tools): a repository-level .github/hooks/*.json never fired, while a user-level hook under $COPILOT_HOME/hooks/ fired immediately. That matches the repo's own in-code note in src/surfaces/adapters.ts:109-117 and contradicts the published reference, which lists repository hook files as a CLI source [4]. This is a doc-vs-measurement disagreement, and the resolution below follows the measurement.

03Cursor — one envelope line away, and one vendor gap that is not ours

fixable here The allow path

Emit the allow envelope for the cursor dialect when the chain allows. Four lines in chainMain, no new abstraction: Cursor is the only host where silence is not permission (Copilot ran the tool through a silent hook in the probe above, and Codex documents “exit 0 with no output is treated as success” [3]; Claude's contract is exit 2 for a block, exit 0 for nothing to say).

vendor-side Output rewrite is MCP-only

postToolUse can rewrite a tool result only through updated_mcp_tool_output, documented “For MCP tools only”; for everything else there is additional_context (injection, not replacement) [1]. rewriteOut:false is therefore correct, and no amount of work on our side changes it.

cursor.com/docs/hooks — postToolUse output table

already true Deny, input rewrite, skills

preToolUse carries permission + updated_input + agent_message — which is what the chain's deny and wrap actually use — and failClosed is honoured per hook (measured). The tool-name alias Shell→Bash is already handled at src/chain/payload.ts:37-38.

cursor.com/docs/hooks — preToolUse output table

free upgrade It can read Claude's hooks

Cursor loads .claude/settings.json hooks with a documented mapping (PreToolUse→preToolUse, permissionDecision→permission, updatedInput→updated_input) [2]. Worth knowing: two templates for the same host is a maintenance choice, not a requirement. Not worth acting on while the native file already exists.

04Codex CLI — capable, but the vendor requires a human to say yes

Capability is not the problem. PreToolUse denies (permissionDecision) and rewrites input (updatedInput, allow-only); PostToolUse can replace the tool result with hook feedback (decision:"block" / continue:false) — which is why the registry says "total-replacement". updatedMCPToolOutput is documented as parsed-but-unsupported [3], so surgical output rewriting does not exist here either.

What blocks core is the trust gate: non-managed hooks are reviewed and trusted by hash through the interactive /hooks browser, and a project's .codex/ layer must itself be trusted. Untrusted or changed hooks are skipped with a warning. The escape hatches are --dangerously-bypass-hook-trust (present in the local 0.153.4 binary [6]) and enterprise-managed hooks in requirements.toml, which are trusted by policy and can be forced with allow_managed_hooks_only [3].

What this rules out

A zero-touch governed install on Codex is not available from the vendor for unmanaged hooks. Any promotion to core that pretends otherwise would be the false promise surfaceCanGovern() exists to refuse. The honest shape is “core, with one step a person performs once” — named in the picker, checked where it can be checked, never bypassed silently (the repo's own rules forbid --no-verify-class shortcuts).

05Copilot — one id holding two environments

Capability-wise the CLI clears the bar that Cursor misses: preToolUse allows/denies/modifiedArgs, and postToolUse.modifiedResult is honoured by command and HTTP config-file hooks — a real output rewrite [4]. Measured end to end above, receipts included.

The best-effort tier was earned by the cloud agent: an ephemeral Linux sandbox, destroyed per job, loading only .github/hooks/*.json from the clone, where ask collapses to deny and files written by hooks are discarded [4]. That is a different environment from the CLI on a developer's disk — and the registry currently gives both one id, one tier and one label.

split the id CLI vs cloud

Two entries, two truths: copilot (CLI, local FS, receipts survive) and copilot-cloud (ephemeral sandbox, config from the repo only, no receipts). Costs one template and one can block — cheaper than a label that has to be half-true twice.

re-probe per release The machine hook

installCopilotCliHook() exists because the CLI ignored repo hooks at 1.0.83. The published reference now claims otherwise [4]. Neither should be trusted blind: the probe is ~10 seconds and belongs beside the existing test that already measures this.

07What not to build

  • An output-rewrite emulation for Cursor. updated_mcp_tool_output is MCP-only [1]; anything we built would be a proxy that lies about what the model saw. YAGNI.
  • A second hook dialect per host. chain/dialect.ts already holds one envelope family per protocol; the Cursor fix is a branch inside an existing function, not a new file.
  • A chain bundle for Cursor/Codex/Copilot. Those three shell out to the binary; only the in-process hosts (OpenCode/OMP/Pi) need .chain-bundle. That split is already right.
  • Promoting a tier without evidence. D-009's rule — “nothing is promoted on optimism” — already exists; extend it rather than inventing a second mechanism.
  • Using Codex's bypass flag as the install path. --dangerously-bypass-hook-trust is for automation that vets its own hooks [3]; making it the default contradicts the repo's own SECURITY stance.

The GitHub reference lists repository-level .github/hooks/*.json as a Copilot CLI source [4]; the repo's note and today's probe both say the 1.0.83 CLI does not read it. I would act on the measurement — the doc may describe a newer release, the VS Code extension, or the cloud agent — and re-run the probe against each new CLI version rather than deleting the machine hook on the strength of a doc.

09Three directions worth taking

01 · fix
Allow envelope for Cursor
Emit {"permission":"allow"} from chainMain when the chain allows and the dialect is cursor. Verified today: allow passes, deny still blocks [6]. Without it, Cursor's guards are a wall, not a guard.
02 · split
copilot vs copilot-cloud
Two registry ids, two tiers, one probe per release for the repo-hook question [4][6]. This retires a label that is currently doing two jobs badly.
03 · evidence
generalise loopEvidence → can.evidence
The registry test already refuses a loop verdict with no measurement [9]; the same rule applied to deny/rewriteOut makes every future promotion a receipt instead of a mood. Codex then reads honestly as “core + one manual trust step”, which is the truth [3].

Order matters only for the first: the Cursor fix changes what users get today. The other two are claims, and a claim can wait for its measurement.
