Git-backed sessions:
¿podemos hacer lo que Agit?

Evaluación de si ai-engineering puede adoptar el modelo de sesiones versionadas en git de Agit (agent-git), o si una capa más ligera cubre los gaps reales sin añadir complejidad.

tools used: web search (agent-git docs, npm, GitHub) · codegraph (ai-engineering session model) · research 003 (prior Agit evaluation) · video transcript (AI Labs tutorial, nan whisper)
degraded-tool: notebooklm (no configurado)

01TL;DR

No adoptar el modelo completo de Agit. Agit es un producto de sesiones que gestiona conversationes como branches en un repo separado (~/.agit). ai-engineering es un framework de gobernanza que gestiona la cadena de guards, receipts y specs. Son productos diferentes con superficies de ataque diferentes.

Lo que SÍ vale la pena: receipts persistentes por sesión (ya existe), handoff entre sesiones (el gap más doloroso según research 005), y un ledger de denies que sobrevive entre sesiones (ya existe como denies.json).

Lo que NO vale la pena: repo separado de sesiones, fork/merge de conversaciones, cross-runtime portability, Hub de sharing.

02Qué hace Agit

Arquitectura 
~/.agit/                    ← repo separado de sesiones
├── agents/
│   └── alice/
│       └── my-project/     ← un repo por proyecto
│           ├── .git/      ← branches = sesiones
│           ├── main        ← memoria compartida
│           └── first-task  ← una sesión = una branch
└── credentials/

Cada turn = un git commit en la branch de la sesión
Cada sesión = una branch (owner/repo@branch)
Fork = crear branch desde un turn anterior
Merge = reconciliar sesiones divergentes

El modelo de datos [1][2][3]

  • Sesión = branch en un repo git separado (~/.agit), no en el repo del código
  • Turn = user message + agent response = un commit
  • Fork = crear una nueva branch desde un commit anterior (como git branch)
  • Merge = reconciliar sesiones divergentes (como git merge)
  • Memory = branch main del repo de sesiones, heredada por nuevas sesiones [6]
  • Import = traer una sesión de otro runtime (Claude Code → Codex) [4]

Lo que resuelve [5]

  • Continuidad entre sesiones — "resume desde donde dejaste" sin re-explicar
  • Sharing con teammates — push a Hub, otros clonan y continúan
  • Portabilidad cross-runtime — mover sesiones entre Claude Code, Codex, OpenCode
  • Historial versionado — cada turn es un commit, audit trail completo

03Qué tenemos nosotros

Modelo actual 
src/env.ts
SESSION_STATE = new Map()   ← en memoria, se pierde al cerrar
sessionId()                 ← de surface o minted: proc-{pid}-{ts}
adoptSession(id)           ← la surface inyecta el session id

src/receipts.ts
Receipt = {                 ← JSON en .ai-engineering/receipts/
  event, surface, tool,         un archivo por llamada a la cadena
  guards, latency_ms,           gc los limpia después de 90 días
  outcome                       (tracked by git = inmune al gc)
}

src/guards/loop.ts
stateFile() = ~/.ai-engineering/cache/loop/{hash}.json
← estado del loop guard por sesión, persiste entre llamadas

Lo que ya tenemos

✅ Receipts persistentes

Cada llamada a la cadena guarda un Receipt JSON en .ai-engineering/receipts/. Surviven entre sesiones. El gc los limpia después de 90 días (solo los que git ya tiene).

✅ Deny ledger cross-sesión

denies.json en receipts/ lleva un ledger de denies por clave. Sobrevive entre sesiones. doctor lo reporta.

✅ Loop state persistente

El loop guard guarda su estado en ~/.ai-engineering/cache/loop/. Una sesión puede ver los patrones de la anterior.

✅ Spec lifecycle persistente

spec.html, plan.html, brainstorm.html viven en .ai-engineering/. Sobreviven entre sesiones. El chain los protege con self-protect.

Lo que NO tenemos

❌ Handoff entre sesiones

research 005: "20/90 sesiones necesitan 'continua' o 'como vamos?' manual." Cada continuación gasta 30-50 mensajes reconstruyendo estado.

❌ Fork/merge de sesiones

No hay forma de bifurcar una sesión para explorar una alternativa y volver. No es un problema que tengamos hoy.

❌ Cross-runtime portability

No podemos mover sesiones entre omp, pi, claude. No es nuestro producto.

❌ Sharing con teammates

No tenemos Hub. No es nuestro producto.

05Lo que SÍ vale la pena

R1 — Session handoff briefing

Cuando una sesión empieza, auto-generar un briefing de estado: qué gates están verdes, qué paso del plan está en curso, qué denies recientes hubo. Esto es lo que research 005 llama "reconstruir estado desde cero" — y la solución NO es git, es un JSON que el chain ya podría generar.

R2 — Receipts con contexto de sesión

Los receipts ya tienen event, tool, outcome. Lo que falta: agruparlos por sesión y poder preguntar "¿qué pasó en la sesión X?". El sessionId() ya existe en src/env.ts:97 pero los receipts no lo llevan como campo. Agregarlo es un campo más en el JSON.

R3 — Research cache automático

research 005 propuso .ai-engineering/research-cache/. Ya existe como patrón en el skill pero no como infraestructura. El paso: crear el directorio y que ai-eng doctor lo reporte.

06Lo que NO vale la pena

Repo separado de sesiones

Agit guarda sesiones en ~/.agit (repo separado). ai-engineering ya guarda receipts en .ai-engineering/receipts/ (en el repo del proyecto). La diferencia: Agit necesita un repo separado porque sus sesiones contienen transcripts completos (MB). Nuestros receipts son JSONs de ~1KB. No necesitamos un repo separado.

Fork/merge de conversaciones

Agit permite bifurcar una sesión desde un turn anterior. Es útil para "¿qué pasaría si hubiera tomado otra dirección?" pero no es un problema que ai-engineering tenga: nuestro trabajo es gobernanza (¿está permitido esto?), no exploración de alternativas.

Cross-runtime portability

Agit convierte sesiones entre Claude Code, Codex, OpenCode. ai-engineering ya soporta múltiples surfaces (omp, pi, claude, cursor, opencode) pero no necesita mover sesiones entre ellas — cada surface tiene su propio modelo de sesión.

Hub de sharing

Agit tiene un Hub para publicar/clonar sesiones. ai-engineering no necesita sharing de sesiones — necesita sharing de specs y decisions (que ya hace vía git).

07Veredicto

Recomendación 
NO adoptar el modelo Agit. Adoptar tres mejoras concretas que cubren
los gaps reales sin añadir complejidad de repositorios separados:

R1  Session handoff briefing    → auto-generar estado al inicio de sesión
R2  Receipts con session_id     → agrupar receipts por sesión
R3  Research cache              → persistir hallazgos entre sesiones

Esto cierra el gap de "handoff entre sesiones" (research 005 #2)
sin añadir: repos separados, git branches para conversationes,
fork/merge, cross-runtime, ni Hub.

Por qué no el modelo completo

  1. Son productos diferentes. Agit gestiona conversaciones. ai-engineering gestiona gobernanza. Mezclarlos añade complejidad que ninguno de los dos necesita.
  2. El gap real es el handoff, no el historial. research 005 dice: "20/90 sesiones necesitan 'continua' manual." La solución es un briefing de estado, no un repo de commits.
  3. Los receipts ya son el ledger. Agit usa git commits. Nosotros usamos JSONs con receipt_id. El resultado es el mismo: un registro auditado de lo que pasó.
  4. El secret guard ya es mejor. Agit sustituye placeholders después del hecho. Nosotros bloqueamos en tiempo de prompt (spoken-secret guard). Nuestro enfoque es preventivo, el de Agit es reactivo.

Si en el futuro se necesitan sesiones versionadas

El camino sería: no un repo separado, sino un .ai-engineering/sessions/ con un JSON por sesión que incluya el transcript (messages + tool calls). Esto es lo que agentsview ya hace con su sessions.db — y research 005 lo usó para el análisis de patrones. La diferencia con Agit: nosotros lo guardaríamos en el repo del proyecto (con receipts), no en un repo separado.
