02Qué cambiaría según la respuesta

Si las capas de ai-engineering fueran un esqueleto válido para cualquier repo, init podría seguir copiándolas. No lo son. Si un agente pudiera editar arch.rules.json con la herramienta de escribir, la valla que existe para eso no serviría. Si user.name autenticara a la persona, bastaría leer git config. Git dice que ese campo es el nombre que quieres ver en el commit, y manda las credenciales a otra clave.

Lo que sí cambia el diseño: la plantilla de init, el último renglón del CLI, y una skill que solo arranca cuando la persona la nombra. La skill enseña el diff en una página de la casa, espera un sí hablado, y el binario escribe. self-protect no gana un agujero nuevo.

El cierre de init hoy nombra dos pasos: confiar el workspace y correr ai-eng doctor. No dice que hay que abrir el IDE y adaptar el proyecto. Ese renglón es el sitio del aviso.

04Qué se queda de AGENTS.md, y qué sale

La convención abierta no exige secciones: es markdown, el archivo más cercano gana, y se reescribe cuando el repo cambia. Cursor dice lo mismo y añade el corte: no copies una guía de estilo, usa el linter; no documentes comandos que el agente ya conoce; no dupliques lo que el código ya dice. ai-agents-md es más estricto que la convención, y es el contrato de este framework: una regla always nombra el mecanismo que la sostiene, y se para a proponer antes de escribir. Las dos fuentes no dicen lo mismo. Para este diseño mando el contrato local, y dejo la convención como el suelo (raíz, anidado solo si el paquete diverge, vivo).

05Cómo se escribe lo prohibido sin abrir la valla

self-protect niega Edit y Write sobre config.toml, overrides.toml, ai-eng.lock y arch.rules.json, y niega un comando de shell cuyo texto nombra esas rutas. El motivo que devuelve es el diseño: lo cambia una persona, en un diff. AGENTS.md y DECISIONS.md no están en esa lista. El blueprint todavía los pone dentro de la valla. Manda el código: la prosa se edita en sesión; la maquinaria, no.

El hueco que ya existe, y que hay que reutilizar, es ai-eng spec approve. El agente no escribe el lock con la herramienta de editar. Corre el binario. El comando no contiene la ruta ai-eng.lock, así que el guard de texto no lo ve, y el binario escribe el pin. La skill nueva hace lo mismo: la página de propuesta vive en .ai-engineering/config-proposal.html, que es material de la sesión (un hijo del directorio, no el directorio), y el sí hablado dispara un verbo del CLI que escribe los archivos y refresca los hashes del lock.

El recibo de la máquina dice quién aplicó el cambio aquí. La protección de rama dice si otra persona tiene que verlo antes del merge. Las dos caben.

06Quién lo ejecutó y quién lo aprobó

user.name y user.email son lo que Git mete en author y committer. Se pisan con GIT_AUTHOR_NAME y las variables hermanas. La misma página aparta la autenticación: si buscas credenciales, la clave es credential.username, no user.name. Git no tiene un campo de apellidos. El nombre es una sola cadena. Partirla en nombre y apellidos inventa estructura que la herramienta no guarda.

Una firma --gpg-sign es otra cosa: firma el commit con la identidad del committer, o con la clave que se pasa. commit.gpgSign lo hace en cada commit. Eso ata el commit a una clave. El trailer no. git interpret-trailers añade líneas tipo cabecera RFC 822 al final del mensaje — Signed-off-by, Reviewed-by, Acked-by — y puede rellenar un Signed-off-by con los datos del autor si no hay uno. La Developer Certificate of Origin 1.1 es el texto legal de esa línea: certificas el derecho a contribuir, y aceptas que el registro (incluido el sign-off) se conserva. No es una prueba criptográfica. Tratar user.email como prueba de identidad sería afirmar lo que Git niega.

Lo que el CLI graba

user.name tal cual, user.email, hora UTC, sha256 de la página aprobada, y un trailer Approved-by: en el commit del cambio. Si user.name o user.email están vacíos, no aplica.

Lo que el CLI dice en voz alta

Atribución, no autenticación. Si el repo firma commits, ese commit va firmado. Si no, el recibo dice unsigned. El commit pasa por el hook commit-msg. No usa --no-verify: esa excepción es solo el commit de install.

Ejecutor y aprobador, en este diseño, son la misma persona: la que invocó la skill y dijo el sí. El agente no tiene nombre en git config. Guardar la frase «el usuario dijo approve» no añade prueba. La prueba es que el verbo corrió, que el hash de la página coincide con lo que se mostró, y que el commit lleva el trailer. Si alguien cambia la página después del sí, el hash no coincide y el CLI no escribe.

07Tres direcciones

  1. Vaciar la plantilla y cambiar el último renglón de init. arch.rules.json.tpl sale con layers vacío, rules vacío y el bootstrap que ya existe, no con cli/guards/chain. El cierre de commitContract añade el tercer paso: abre el IDE y carga /ai-config-to-project para adaptar el proyecto. doctor deja de tratar «no hay src/ raíz» como «no hay código» cuando el árbol tiene otras raíces. Hecho eso, un init nuevo no repite el commit 013f77c6 de brand.
  2. Escribir la skill manual, no un agujero en self-protect. Frontmatter disable-model-invocation: true, más el pestillo en el texto. Entrevista el cwd, audita el AGENTS.md que ya esté, y escribe .ai-engineering/config-proposal.html con el shell de artifact (favicon, tokens, scroll-spy). Se detiene. El sí hablado corre un verbo nuevo del CLI, el mismo patrón que spec approve. Ese verbo es el único que escribe arch.rules.json, config.toml y overrides.toml, y actualiza los hashes. Una segunda invocación, cuando el proyecto cambie, parte de los archivos editados y vuelve a proponer. No restaura la plantilla del framework.
  3. Sellar atribución, y decir que no es identidad. Approved-by: con la cadena user.name y el email, más el sha256 de la propuesta, vía el mecanismo de trailers de Git. Firma GPG solo si el repo ya firma. overrides.toml sin until no se aplica. CODEOWNERS queda como la revisión de otra persona en GitHub; el trailer es el registro local. No partir el nombre en apellidos: Git no tiene ese campo.
