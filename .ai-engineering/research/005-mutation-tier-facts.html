00Why these three

The mutation tier gates a merge on a campaign whose results are restored from a cache. Three questions decided whether that gate is real: does a cached kill survive an edit to the test that produced it, does the invocation run Stryker on the runtime it requires, and who may write the cache. Each was answered from source, not from the README's summary, because the plugin's own README contradicts itself on the second one.

01An edited test invalidates its cached kills

The bun runner is at Stryker's "Full" test-reporting tier

Verdict: a test edit DOES invalidate the cached kill of the mutants that test covered. No extra configuration, no baseline file.

ClaimEvidence
The runner reports a file name and a line for every test it discovers.src/bun-test-runner.ts:744-782 at tag 1.3.8 — fileName from normalizeTestFilePath(testInfo.url), startPosition from testInfo.line, spread into every Failed/Skipped/Success TestResult returned in {status: Complete, tests, mutantCoverage}.
Stryker identifies a test by exactly those two fields plus its name.packages/core/src/mutants/incremental-differ.ts:591-601 — `${relativeFileName}@${line}:${column}\n${name}`.
A Killed mutant is reused only when its killing test is unchanged.Same file, :394-437 — reuse requires a killing-test key whose diff is same.
The report carries what the differ needs.packages/core/src/reporters/mutation-test-report-helper.ts:350-360 — test location plus the test file's source are written into stryker-incremental.json.
Stryker's public support table has no Bun row, so this could not be answered from the docs.stryker-mutator.io/docs/stryker-js/incremental lists Jest/Vitest/CucumberJS as Full, Mocha/Tap weaker, Command as Nothing.

Residual blind spots, and they are Stryker's, not the plugin's: changes to files that are neither mutated sources nor test files are invisible to the differ, and the no-inspector fallback path reports nothing. Neither is exercised by this repository's layout, where the mutated modules are imported directly by the tests that cover them.

02The invocation, and why the README looks self-contradictory

bunx stryker run, on Node ≥ 20, on an image that ships 22.23.2

Verdict: bunx stryker run is the correct CI line. No npx, no separate Node install.

The plugin README states "Stryker itself runs on Node (only the test children run on Bun)" and then shows bunx stryker run. Both are true: @stryker-mutator/core@9.6.1 declares bin.stryker → bin/stryker.js with a #!/usr/bin/env node shebang, and Bun's documentation states bunx honours shebangs by default, so the CLI executes under Node while the bun test children execute under Bun.

FactEvidence
Stryker 9 requires Node ≥ 20.engines.node in the registry metadata for @stryker-mutator/core@9.6.1.
The runner image already satisfies it.actions/runner-images Ubuntu2404-Readme.md — default Node 22.23.2 (image 20260907.300.1).
The plugin needs Bun ≥ 1.3.7 and core ^9.Registry metadata for @hughescr/stryker-bun-runner@1.3.8: engines.bun >= 1.3.7, peerDependencies["@stryker-mutator/core"] = "^9.0.0". The repository pins bun@1.4.2.

03The platform already isolates the cache

No cache key needs to name a branch

Verdict: one key, restore-keys by prefix. The per-ref key that was about to be added would have been ceremony.

FactEvidence
A pull-request run may restore a cache created by the base branch or the default branch — including from a fork.GitHub docs, dependency caching: "Restrictions for accessing a cache" and "Cache access for low-trust workflow triggers".
What a pull-request run saves is scoped to its own merge ref, so it is invisible to main and to sibling pull requests.Same page; actions/cache README, "Cache scopes".
Caches are immutable: the first write of a key wins, and a duplicate save does not fail the job.actions/toolkit packages/cache/src/cache.ts and actions/cache src/saveImpl.ts — the duplicate path is logged, not thrown.
Prefix search returns the most recently created match, current branch before default branch.GitHub docs, "Cache key matching".

Consequence for the contract: the only thing a cold cache changes is wall time, and the job timeout is what covers it — nothing about the verdict depends on the cache being warm.

04What this changed in the plan

One adjustment was deleted on the strength of section 03 (the per-ref cache key), one gate was added from section 01 (an edit to a single killing test must re-run its mutants), and one line was added from section 02 (node -v printed with the campaign). Nothing in this document decides a question the map leaves open.
