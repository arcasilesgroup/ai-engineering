El humano para dos veces: aprobar el plan, y probar la app. En medio, el orquestador decide. Si una puerta falla 3 veces, parte el paso. Si el paso partido también falla 3 veces, escribe halted y para. [2]

Cada paso que toca archivos hace commit en feat/<slug>, con mensajes fijos (plan, test, feat, gate, fix, docs, wip). Al aprobar, un squash a la rama base. No hace push. [2]

04Qué se congela y qué obliga el prefijo

El pedido cierra el texto, las fases, las puertas, el JSON, la tabla de commits y los nombres de agente. El prefijo ai- obliga a tocar solo las cuerdas que nombran el skill. Si esas cuerdas no cambian, el gancho de Stop no reconoce la sesión y el visor de rutas del skill no encuentra el archivo. [7]

El test del gancho fija esa cuerda. [7] [8]

Por qué la copia tiene que vivir en el proyecto

ai-engineering instala skills en el canon de la máquina y los espeja a ~/.claude/skills. El kit no. Sus skills se leen con ruta relativa al repo: .claude/skills/test-planner/SKILL.md y .claude/hooks/checkpoint-gate.py con CLAUDE_PROJECT_DIR. Si solo viven en el home, el orquestador abre un archivo que no está. El canon sirve para que ai-eng update tenga la fuente. El proyecto gobernado necesita además la copia en .claude/skills/ai-* y .claude/hooks/. [1] [9]

Los cinco agentes no llevan prefijo. Sus name: se quedan: checkpoint-planner, adversarial-reviewer, fixer, ui-visual-reviewer, ui-behavior-reviewer. [10]

05Dos casas de documentos, y no son la misma

.ai-engineering/*.html es el contrato de un hito. spec close lo barre. docs/ del kit es la verdad del producto, y sobrevive al hito. Meter PRD, permisos y aprendizajes en el slot HTML haría que un close borre el producto. [1] [11]

06Cada skill de ai-engineering contra el kit

El crítico del kit ataca reglas de arquitectura, seguridad de acceso (rol, IDOR, secretos), corrección, tests, consistencia, y en UI tokens más accesibilidad básica. No corre una auditoría WCAG 2.2, ni perf, ni el audit de seis fases de ai-security, ni mide píxeles sin prototipo. [13]

08Agentes

Hoy el binario no instala un catálogo de agentes. Algunos skills traen agents/openai.yaml, que es otra cosa. Los cinco markdown del kit son nuevos en el canon. [9]

Identidad por el campo name, no por la carpeta. Claude Code lo dice así, y desde v2.1.198 el comando /agents ya no abre un asistente: el archivo se edita a mano. [6]

El orquestador llama general-purpose para preflight, tests, implementación y la puerta de behavior. Esos no son archivos del kit. El host tiene que ofrecer ese subagente, o el texto que dice general-purpose no arranca. En Claude Code existe. En otros hosts hay que comprobar el nombre antes de prometer la Fase 0. [2] [6]

09Dos formas de escribir DESIGN.md

design-md-planner escribe docs/DESIGN.md en el formato de Google (frontmatter YAML de tokens más prosa), y no para hasta que npx @google/design.md lint queda limpio. Tiene dos modos: inventar un sistema, o extraer el que ya hay y juzgarlo. El modo extraer no copia el slop: lo nombra y propone un reemplazo. [18]

make-design-md hace otro trabajo. Lee el código que ya está, no diseña, no normaliza, no arregla en silencio, y escribe design/design.md. Cada valor tiene que salir del repo. [19]

No son intercambiables

Sustituir design-md-planner por make-design-md recorta el kit: se pierde la entrevista, el lint de Google, el catálogo anti-slop y la ruta docs/DESIGN.md que leen prototipo, review-ui y el crítico. Conservar los dos y cambiar solo la ruta de salida de make-design-md a docs/DESIGN.md cumple las dos frases del pedido: el workflow no se recorta, y para reflejar un sistema ya construido se usa make-design-md. Si los dos fueran a escribir el archivo a la vez, manda ai-design-md-planner, porque es el que el resto del kit nombra.

El sistema visual de los artefactos de ai-engineering no es el DESIGN.md del producto. El propio documento lo dice: una cosa es cómo habla el framework, otra cómo se ve el producto. [20]

10El visor

docs/checkpoints/viewer.html es cromo del framework que se copia al proyecto. El README deja cambiarle la paleta. El pedido de esta sesión fija esa paleta: la de los artefactos de ai-engineering. El comportamiento se queda. [1] [20] [21]

  • Se queda el script: poll cada 3 s, ?plan=, selector si hay varios JSON, drag-and-drop si se abre por file://, puntos de tamaño según xs…xl, puertas con las etiquetas Works / Looks right / Code review, assumptions, detalles técnicos, enlace al prototipo, unión con docs/test-plans/<slug>.json.
  • Se queda el copy en inglés. Es texto del workflow.
  • Se va la hoja de Google Fonts (Public Sans, IBM Plex Mono). El artefacto usa pilas de sistema para abrir offline.
  • Entran los tokens del artefacto, el favicon {ai}, y el scroll-spy del nav si el visor pasa a tener nav. La lógica de render no se reescribe para “limpiarla”.

11Desacuerdos

  1. ¿PreToolUse bloquea de verdad un Agent o un Task? La doc de Claude Code, consultada el 2026-09-25, dice que exit 2 en PreToolUse bloquea la tool call, y que exit 2 en Stop impide parar. Issues del tracker dicen que el resultado del hook para Agent/Task se mira después de que el subagente ya corrió, o que el deny no se aplica. No verifiqué si un release posterior los cerró. Actuaría por la doc como contrato, y no llamaría “impuesta” la puerta de subagentes hasta una sonda en la versión que corre aquí. La puerta de Write/Edit/Bash y el Stop siguen siendo el respaldo aunque el Agent se cuele. [4] [22]
  2. Formato de agentes en Codex. La doc de Cursor dice que lee markdown en .codex/agents/. Un handbook de terceros dice TOML. NotebookLM dice que Codex declara agentes en config.toml bajo [agents] o en AGENTS.md, no en una carpeta markdown. Pueden ser las dos cosas: el CLI guarda la config en TOML, y Cursor acepta markdown en esa carpeta por compatibilidad. No generaría TOML hasta abrir la doc de OpenAI o probar el CLI. [15] [23] [24]
  3. ¿El stop de Cursor obliga a seguir? NotebookLM dice que el stop de Cursor sirve para auditar y no tiene un exit 2 que devuelva al modelo al bucle. La página de hooks de Cursor, bajada en esta sesión, dice que followup_message en stop se envía como el siguiente mensaje del usuario. Actuaría por esa página: el adaptador de Cursor usa followup_message, no un exit 2. [5] [24]
  4. Dónde viven los agentes de Cursor. NotebookLM dice .cursor/subagents/. La doc de Cursor dice .cursor/agents/ y también .claude/agents/. Actuaría por la doc de Cursor. Una copia en .claude/agents/ sigue siendo la que cubre Claude y Cursor. [15] [24]
  5. Stop en Pi y OpenCode. NotebookLM marca los dos: la doc de Pi no trae un stop de turno, y OpenCode no trae un hook que rechace el cierre y obligue a seguir. Oh My Pi sí: turn_end puede inyectar un mensaje. No abrí esas páginas yo. La marca queda como síntesis, y la pregunta 3 del handshake sigue abierta hasta una lectura directa. [24]
  6. Research 009 y el prompt hook de Cursor. 009 no vio dispararse beforeSubmitPrompt, así que sigue sin cablear. La doc de hooks sí lista stop y preToolUse. Este informe usa esos dos, no el prompt hook. No contradice 009. [16] [5]
