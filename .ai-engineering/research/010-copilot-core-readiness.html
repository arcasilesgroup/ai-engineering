RESEARCH 010 / CONSULTA 2026-09-25 / DECISION: NO PROMOTE TO CORE

Copilot: sigue en best-effort

Pregunta: si el contrato de ai-engineering exige deny que el host obedece, rewrite de salida que el host aplica, prompt hook capaz de bloquear o reescribir, carrier realmente leído y receipts que sobreviven el turno, ¿puede Copilot subir a core?

Veredicto: no. El CLI sí cierra deny, rewrite de argumentos y lectura de ambos carriers. Pero la salida de userPromptSubmitted de un hook command/HTTP sigue descartada, el cloud agent descarta lo que escriben los hooks y la documentación consultada no atribuye este contrato a Copilot en VS Code. Una brecha abierta basta para mantener el tier en best-effort.

Brechas que deciden el tier

  1. Prompt hook: sigue abierta para CLI y cloud agent. Para cerrar la brecha, GitHub tendría que hacer que la salida del hook command/HTTP de userPromptSubmitted sea aplicada por el host, con una semántica documentada de bloqueo y/o sustitución de prompt. userPromptTransformed solo cubre reescritura model-facing y es mutation-only. [1]
  2. Carriers: cerrada solo dentro del CLI; no unifica los tres productos. El CLI ya combina repositorio y usuario. El cloud agent intencionalmente solo carga la copia del repo. Para una garantía común, VS Code necesitaría una superficie documentada y observable con el mismo carrier y contrato. [1][2]
  3. Persistencia cloud: sigue abierta. Un hook que escribe .ai-engineering/receipts o cualquier archivo del sandbox no deja un registro al acabar el job. Para cerrar la brecha hace falta una salida persistente que el host garantice, por ejemplo un mecanismo documentado de publicación/commit del output del hook; la referencia actual solo menciona HTTP para retenerlo. [1]

Tres direcciones

  1. CLI real: medir en una instalación vigente un hook de repo y otro de ~/.copilot/hooks que, por separado, denieguen, devuelvan modifiedArgs, escriban un receipt y prueben userPromptSubmitted. La doc ya afirma el contrato de deny/rewrite y la lectura combinada; la sonda debe comprobar la versión concreta y la durabilidad local. [1]
  2. VS Code: medir por separado el runtime de Copilot Chat con un hook de .github/hooks: carga, deny, rewrite de input, rewrite de output, prompt y receipt. La documentación primaria consultada no cubre esta superficie, así que no usar el resultado del CLI como proxy. [1][2]
  3. Dejar en best-effort: cloud agent y cualquier prompt guard basado en command/HTTP mientras GitHub no aplique modifiedPrompt y no haga persistente el output escrito por hooks. La recomendación está directamente limitada por esas dos capacidades documentadas como ausentes. [1]
