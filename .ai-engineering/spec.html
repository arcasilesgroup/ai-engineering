01Work points

Numbered sections: what must be done. Each point names the gates that prove it done.

01 · The planted pipeline can run at all

The workflow we plant installs the governor with bun add -g ai-engineering@2, a package that does not exist on npm (404, measured) — the check job is red at step 4 in any client repo. It also resolves a trivy action ref that does not exist (@0.33.1 vs the real v0.33.1/v0.36.0), and the bin it would install is TypeScript source, so a Python or Go client would need Bun only to run the governor. The template downloads the compiled binary from a pinned release asset instead, verifies its sha256 with the pattern we already use for gitleaks, and keeps the version in one place a human bumps deliberately.

Proves: G4, G5

02 · The planted gate fails when it should

Three of six steps in the planted check job end in || true (typecheck, lint, arch), so a client can merge with a failing typecheck. Every third-party action the template names is pinned by a mutable tag — the practice GitHub's own hardening guide refuses. Both stop being true: no step swallows a failure, and every uses: carries a full commit SHA.

Proves: G2, G3

03 · Every governed surface gets a merge gate, or none claims one

The workflow hangs off case "claude-code" alone: choosing OpenCode, OMP, Codex, Cursor, Copilot or Pi plants guards and adapters but no workflow, and nothing says so. The CI entry moves to planEntries where every surface passes, and a test proves each adapter-bearing surface receives it — so a future surface cannot be added without one.

Proves: G1

04 · Our own spec gate stops lying

check.yml runs bun dist/ai-eng spec run || echo in a job that never builds and whose dist/ is gitignored: measured, the command dies with Script not found and the echo turns it green. The job builds first and the step can fail. CI is expected to be red until this contract is approved — that redness is the feature, and it is why the approval is STOP 1.

Proves: G8

05 · The security job runs what we promise

§17 claims gitleaks + semgrep + trivy + npm audit in the merge gate; the repo runs gitleaks, discards npm audit with || true, and has no semgrep or trivy anywhere. All four run, every action is SHA-pinned, and the SBOM tool (cdxgen) is downloaded from releases/latest today — the same unpinned pattern we refuse for everyone else — so it gets the checksum treatment too. First runs may surface real findings; a finding is a finding, and it is reported rather than silenced.

Proves: G9, G10

06 · The canon is compared against the lock, in CI

§17 lists lockfile-vs-skills as a merge-gate tier; no job does it. ai-eng doctor already implements canon drift, so CI calls doctor instead of reimplementing the comparison — and the same step covers the lock version and the spec pin.

Proves: G11

07 · Mutation stops being a word we use loosely

The job named guards-mutation generates no mutant: it re-runs the adversarial suite that the check job already ran, and it is skipped on push. It is renamed to what it does and the blueprint stops claiming mutation runs today. Stryker — with the incremental scope and the 10-minute cap §17.1 describes — becomes its own milestone, because it is a dependency and a nightly budget, not a rename.

Proves: G12

08 · The release path is exercised before a client depends on it

v2 has never been released: the last release is v0.13.0 (2026-07-27, the v1 PyPI line). The release job uploads eight files all named ai-eng from dist-artifacts/**/* — expected to collide on unique asset names — so the binaries are named per target first. A prerelease (v2.0.0-rc.1) then runs the real path without claiming Latest, and a PR-time workflow proves the planted pipeline end to end against the freshly built binary. The ephemeral channel is ours; the client pins the stable one.

Proves: G6, G7, G13

09 · Publishing is a verb, not a memory

The release path has never run and the tag lives in a human's memory — the decision that always comes out the same, which AGENTS.md says belongs in code. The release job becomes dispatchable and creates the tag and the release itself, deriving --prerelease from the version's semver suffix (2.0.0-rc.1 → prerelease, 2.0.0 → latest). One workflow, not two: a tag pushed with GITHUB_TOKEN does not start another run, and workflow_dispatch always does (GitHub docs — GITHUB_TOKEN). The human keeps the press as a protected environment with required reviewers — one approval click, not a shell ritual, and the version decides the rest.

Proves: G14, G15

03Constraints & contracts

The client pins a stable artifact; we test with an ephemeral one. A gate pinned to a moving target is not a gate, so the template pins v2.0.0-rc.1 by version + sha256, and the PR-time proof uses an Actions artifact that dies with the run (needs a token to download — ours, never the client's).

G6 is a human dependency. It cannot pass until the prerelease is published; the milestone does not close on it without either the tag or an ABANDON line naming the reason.

Sending a prerelease to clients is deliberate and temporary. The version lives in one place in the template; promoting v2.0.0 to a real release is a one-line bump, and the plan carries it as the follow-up step.

CI is red on purpose until STOP 1. Fixing G8 means our own spec gate starts failing for real; it goes green when this contract is approved and its gates run.

Non-goals: no Stryker nor mutation budget (its own milestone, §17.1 stays as the design of record); no per-language CI generation (detectCommands reading the client's root instead of ours is the known adjacent defect, tracked in plan.html §04 — pull it in on request, one word); no change to release.yml's 8 targets or to the git floor.
