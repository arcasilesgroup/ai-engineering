{ai} PRD

Status: draft · Last updated 2026-10-27

Cumulative product scope. /ai-orchestrator settles ambiguity from this file, so business rules written here become the default answer to “what should happen when…”.

Problem

When someone installs ai-engineering and runs ai-eng init in a project that already has its own AGENTS.md, init keeps that file silently and never asks: the project ends up without the ai-engineering contract and no human decided anything (src/install.ts: "we never installed it: it is the user's"). On top of that, the authoring skill and the template carried none of the discipline long unattended runs need: verification floor, suite baseline before the first edit, hang-proof commands.

Floating core: the framework drifted from its promise "Not a platform. Nothing to sink." It imposes its own flow (one worktree per writing session, merges only into a local main, main and origin/main hard-coded in 77 places), runs its own local web hub and server, keeps four validators and two languages for one lifecycle state, and blocks agents on files unrelated to the operation. Real failures: orchestration refused to start because two design files were modified, merge refused on another feature's untracked artifacts (fixed in 55c87550), a stale folder looked like active work, resume became impossible on a dirty worktree, and ai-pr refused a PR because an unrelated branch was open and the Azure DevOps default branch was not main. The split between skills/ and packs/ also gives skills two source locations and makes installation harder to understand.

Goal

ai-eng init leaves every project with our AGENTS.md: written when missing, named and asked about when a foreign one exists (default: keep the user's), never replaced in silence. The ai-agents-md skill and templates/AGENTS.md.tpl carry the approved content: context-first explanation, the verification floor, the unattended-runs section, and the do-not-touch/context fill-ins, under the 120-line doctor ceiling.

Floating core: ai-engineering is a safety floor under the agent the person already uses. It works the same in the current checkout or in a worktree, detects the base branch instead of assuming main, and opens PRs from any branch with gh or az. Everything Git, the IDE, the harness and the forge already provide is used, not copied. The guard chain, receipts, contract, skills and token savings (wrap) stay. All skill sources and installable resources live under skills/<name>/, and every skill installs by default. Installation makes a skill available; it does not run it. Evaluation fixtures live under tests/fixtures/ and are not installed. Existing configuration is not rewritten; legacy [canon].packs values do not restrict installation. The ai-orchestrator ceremony stays core with its current behavior. Success: no resident process, no hard-coded base branch, one lifecycle validator, every refusal names the protected path and the next step, and a deterministic serial test suite under two minutes.

Features

Floating core: the floor stays, the platform goes

Feature floating-core, brainstorm revised and approved on 2026-10-29 (.ai-engineering/brainstorm.html). It supersedes the earlier "one worktree per feature, local main as the only destination" rules, the local project workspace hub, and the optional-pack installation decision.

  • Way of working: rhythm direct (bugfix, spike, one-sitting change: failing test first, fix, green, commit; no artifacts) or agreed (brainstorm approval, /ai-orchestrator checkpoints, app review). Work happens in the current checkout by default; a worktree is used when asked or when another feature is active in that checkout, preferring the harness's native worktree. Closing offers local merge, PR or keeping the branch; PR is recommended when a remote forge exists. .ai-engineering/recap.html is optional and never required for merge; it is created on the feature branch only when the user explicitly invokes /ai-visual-recap.
  • Base branch: explicit argument, then [git] base, then refs/remotes/<remote>/HEAD, then the forge default when opening a PR, otherwise ask once. Never a literal main. Pushes to the detected base fail closed: a direct push is denied, and so is any push when no base resolves.
  • Ceremony protected: every skill, agent, script and template that ai-orchestrator uses stays available and keeps its behavior (brainstorm, checkpoint-planner, ai-test-planner, ai-prototype, viewer, ai-review-ui with its reviewers, ai-adversarial-loop with its agents, ai-security and ai-write triggers, request-changes, merge). Every skill installs by default; a contract test fails if any required asset is missing.
  • State: the feature checkpoint JSON is the only state, validated by one TypeScript module. Phase names stay; reviewed_main becomes reviewed_base plus base_ref, read-compatible. approval-before-start and complete are dropped; "integrated" is derived from Git.
  • Checkpoint guard: a 1-to-1 TypeScript port of scripts/checkpoint-gate.py inside the chain (same gates, stages, halted and Stop rule), minus the "plan only inside a managed worktree" rule.
  • Removed: the workspace hub and its server, the lifecycle projection, dead sidecar/shadow/queue and circuit breaker, briefing, upgrade, spec, global git init.templateDir, worktree rebase|project-lifecycle, file-hint manifest, the pre-worktree pseudo row, auto-commits with --no-verify in init/update.
  • Kept: chain, guards, receipts, surfaces, per-repo Git hooks, wrap as token savings (only failing tests shown; full output saved locally), worktree new|list|merge|request-changes|rm with reviewed-SHA compare-and-swap merge from any checkout.
  • Token efficiency: every token ai-engineering puts in context earns its place. Re-measure skill frontmatter with every skill installed; keep the AGENTS.md template at most 1,200 tokens; hooks print nothing when green and at most 3 lines on deny; the pre-commit receipt recount (minutes over 239,991 receipts) is removed and receipt retention runs on its own. Filters never hide a failure and keep the exit code. The yardstick is beating rtk and caveman combined, measured in the follow-up feature token-economy.
  • Skills: every skill has one source under skills/ and installs by default. Evaluation fixtures stay under tests/fixtures/ and outside the installed skill payload. Existing [canon].packs values do not limit installation and user configuration is not rewritten.
  • Rules: block only what the operation will write; detect, never assume; one state, one validator; no resident server; never lose work (no automatic stash, reset, clean or delete); cleanup, install and uninstall touch only files proven ours by exact bytes, a recorded hash or the exact link written, and unproven files are never deleted; every refusal names the path and the next step; fewer tokens, never less truth (exit code kept, failures never hidden); ceremony behavior changes only through an explicit decision. Version 3.0.0 with a migration guide.

AGENTS.md contract on init

  • Init writes our AGENTS.md when the project has none, as before. When a foreign one exists, it names it and asks: overwrite with the contract file?
  • Rules: default (Enter) and --yes/non-TTY keep the existing file byte for byte; only a human yes replaces it. The prompt covers AGENTS.md only: existing DECISIONS.md and .gitignore are never asked about. An AGENTS.md not tracked by git gets one extra warning in the prompt before it can be lost. update, re-init and uninstall keep their current behaviour (they never touch the contract). Template and skill edits: 11-section order, Code style line carries the context clause, new Unattended runs section (no mid-run questions with assumptions recorded, full-suite baseline, hang-proof commands), verification floor and "noticed, not fixed" in Workflow, do-not-touch/context fill-ins in Project config, anti-second-map clause (name the memory the repo keeps, never add a PROGRESS.md beside it), doctor ceiling stated as 120 lines.

GitHub and Azure DevOps backlog triage (ai-triage)

Problem: teams need one complete, ranked backlog report from GitHub or Azure DevOps without losing useful provider-specific details or changing either service. Azure's current Priority/Severity ranking does not explain documented blockers, delivery commitments, item age, or parent and sprint context. Activity alone must not be mistaken for urgency.

Goal: one public ai-triage skill handles GitHub and Azure DevOps through separate provider procedures. Each run resolves one explicit scope, explains what to work on first, and writes a complete report. Azure recommendations include a specific Why now grounded in evidence, or state why urgency cannot be justified. Ambiguous scope stops for an answer before reads. No active Azure CLI account default may be used to guess scope.

Users & roles: people and teams using Azure DevOps across organizations and projects receive a complete report and decide what to act on. The triage agent reads only the selected scope and writes the local report; it cannot mutate remote work items or publish private backlog data.

Feature: Azure evidence signals and transparent recommendations, ai-triage-azure-signals. Design and recommended defaults approved on 2026-10-08. The approval covers design and local implementation, not remote mutations, new production reads, or publication of private data; new API capabilities remain unverified.

  • GitHub: preserve the complete open issue and pull-request inventories, pagination and counts, item analysis, ranking, evidence pinned to commits, report sections and fields, and read-only guarantees. Keep unassessed items visible; never omit items or claim a partial inventory is complete.
  • Azure DevOps: support Azure DevOps Services only. A URL determines provider and scope; otherwise use only an unambiguous repository remote and ask when provider, project, team, board, or backlog level is unclear. One run covers one selected board/backlog level; related parents and children are context, not extra inventory. Preserve every selected backlog member and literal state, including terminal states returned by the current collector; this extension does not change inventory policy.
  • Safety: Azure collection is read-only and limited to explicit, allowlisted reads. Ambiguity, authentication errors, unknown inventory completeness, or incomplete inventory pagination stop the run and preserve the previous report. Escape remote fields, validate HTTPS evidence links, and never include authentication data. Synthetic fixtures only; no private backlog data is committed to this repository or its history; the private report may exist locally without staging.
  • Recommendation rules: keep native Priority and Severity visible and unchanged. Evidenced current commitments and explicit blockers may change the separate recommendation of what to work on first; each change explains its source and proposed action. With no verified reason, preserve the existing native order. Do not use weighted scores or promote urgency from age or comment count alone.
  • Comment rules: analyze content, sequence, and dates, not counts. Distinguish team assertions from facts verified in code. Later evidence resolving a blocker replaces an earlier blocked conclusion.
  • Parent and calendar rules: direct-parent priority and dates are contextual, never automatically inherited. Claim a child blocks its parent's delivery only with explicit evidence. An explicit due date is a commitment; sprint end is planning context, and an iteration without dates supplies no deadline. A near commitment does not automatically demote critical risk; conflicting reasons remain visible for human judgment.
  • Coverage rules: distinguish absent, inaccessible, and partial optional signals, with a reason and next action. Describe evidence as sufficient, limited, or not assessable without numerical confidence. With a complete inventory, limited optional signals may produce a clearly labeled report, never proof that no blockers exist. Authentication failures, ambiguous scope, incomplete inventory, or unsafe output preserve the prior report. Research must verify how the new APIs expose each case before planning their use.
  • Approval boundary: preserve GitHub behavior, use synthetic fixtures and a fixed clock for calendar tests, and require separate authorization for new live production reads. No code or checkpoints are created by this design approval.

Out of scope: Azure DevOps Server, remote mutations, multiple boards in one report unless explicitly requested, persisted board configuration, guessing from Azure CLI defaults, changing GitHub behavior, configurable weighted scoring, automatic parent or sprint deadline inheritance, and committing, pushing, or sending private backlog data to external services.

Out of scope

  • External lifecycle sidecars or status consumers; Git and feature checkpoints remain canonical.
  • A semantic merge of two different AGENTS.md files: prose has no marker to merge on; the choice replaces or keeps the whole file.
  • Changing the 3-way diff of update, or uninstall's contract handling.
  • A CLAUDE.md shim, or a PROGRESS.md file (the memory slot belongs to plan.html; a second map is forbidden by ai-goal).
  • New CI or lint rules; the load-gating header ("do not load this file for short work"), since AGENTS.md always loads.
  • Floating core: changing guard security logic or adding guards (except the checkpoint port); any hosted service, telemetry or new own UI; coordinating work across clones or machines; deleting skills as part of the move (later removal requires evidence that a skill is not needed); redesigning the website (only its claims are corrected); external lifecycle consumers; changing the receipt format; PRs on forges other than GitHub and Azure DevOps; new token-saving filters for lint, typecheck or build (next feature); changing the orchestrator ceremony beyond working without a worktree and with a detected base.
  • Git flow:
    • Deleting remote branches: git push origin --delete is never used.
    • Renaming ai-eng git to ai-eng hooks: cosmetic, and the installed floor shims carry ai-eng git floor shim as their marker, so a renamed verb with old shims on disk denies every commit until ai-eng update runs in each repository.
    • Merging or closing a pull request on the agent's own initiative: ai-pr merges when the human asked for the PR, and the human can switch auto-merge off.
    • Rewriting history of the local main: no interactive rebase, no git gc, no forced deletes, no replacement of the spec/plan/checkpoint process.
    • Coordinating worktrees across separate clones or machines; the inventory is local. Merging a sibling branch that has not passed human review, or guessing through an ambiguous conflict, is never automatic.
    • Picking up the three attachments whole: only single pieces of tech-debt-audit, remove-deadcode and security-research enter ai-audit-code and ai-security.
