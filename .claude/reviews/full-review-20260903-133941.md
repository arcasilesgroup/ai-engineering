## Fix before merge

### 1. [CRITICAL] CONFIRMED — path traversal via lock asset keys: malicious `ai-eng.lock` deletes arbitrary files the hash matches
- **Where:** `src/commands/uninstall.ts:130` (`const absolute = join(root, rel)`) · vector enabled by `src/install.ts:138` `parseLock` (accepts any quoted key) · same pattern in `src/commands/doctor.ts` if it hashes lock assets
- **Trigger:** clone a repo whose committed `.ai-engineering/ai-eng.lock` contains `[assets] "\..\..\victim" = "<sha256 of victim>"` (or any relative path escaping `root`), run `ai-eng uninstall --project`, confirm.
- **Consequence (reproduced):** PoC — lock with key `"../../../Users/soydachi/victim-shared.txt"` + matching sha256 → sweep ran `unlinkSync` on `/Users/soydachi/victim-shared.txt`, **file deleted outside the repo**. `join()` normalizes `..` away, `settingsByPath`/`.git/hooks/` guards never see the escaped rel, and the hash gate is satisfiable by the attacker for any world-readable file. Same trust applies to install/update if they ever read asset paths from the lock (update only reads hashes: previous.assets values — safe there).
- **Fix:** validate every lock-declared rel before use: `const absolute = resolve(root, rel); if (absolute !== root && !absolute.startsWith(root + "/") || rel.startsWith("/") || rel.split("/").includes("..")) → skip + warn`. Apply at the single sweep loop in `uninstall.ts` (and to any other consumer of `parseLock().assets` keys: doctor, spec pin checks). Add an adversarial test: malicious lock → nothing outside root touched, lock deleted anyway.
- **Reviewer evidence:** quoted-key regex `src/toml.ts:27` `^(?:"([^"]+)"|...)\s*=` accepts the key; triage PoC confirmed end-to-end.

### 2. [MEDIUM] CONFIRMED (downgraded from reviewer's "low/medium") — recovery-state lock rebuild claims user-owned files
- **Where:** `src/commands/update.ts:166` (`buildLock(entries.filter(keep), VERSION)` when no prior lock)
- **Trigger:** repo in config-present/lock-missing state with a `.claude/settings.json` that is NOT ai-eng's template (user's own or older version). Reproduced: created `/tmp/f2` with `{"editor":"vim"}` settings, ran `update --yes` → lock recorded template hash for it although install() classified it untouched/user's.
- **Consequence (reproduced):** next `update` reports a false conflict ("2 files patched by you also changed") on a file ai-eng never owned; `uninstall` runs `stripAiEngHooks` on it. The user's file survived in the PoC (strip is conservative, deletes only ai-eng hook entries), so this is ownership-ledger corruption, not data loss — but it converts into real user-visible wrongness on every later update.
- **Fix:** in the no-prior-lock recovery path, build the lock only from files install() actually wrote or that byte-match ours: `const ownedNow = new Set([...report.written, ...report.untouched.filter(p => sha256(readFileSync(join(root,p)))===sha256-of-ours)])`. Simpler: `buildLock(entries.filter(e => report.written.includes(e.path) || plan.current.includes(e.path)), VERSION)`.
