# The block nobody could see

## Who this is for, and what it is worth to them

The person who is not at the keyboard. This repository was built to be run overnight —
"te dejo solo, que no estaré delante" — and specification 019 fixed the loop that made a
build spend four days on two specifications. It did not fix the other half. When a build
reaches something only a person can decide, the build stops and the person finds out by
reading a terminal transcript, if anybody kept one.

It happened while 019 was being built. Block H's header required written authority naming
two SHA-256 digests. The block was opened without it. Nothing stopped, and nothing said so
either — the requirement existed in a plan nobody was reading, and the only record that it
had been skipped was a sentence in a chat window. Both halves failed: the stop did not
happen, and the stop was not visible.

What changes: the page in `docs/` gains one section that answers "what is waiting for me".
A person opens one document, sees every item that needs them, and each one names what to
type. Nobody has to read a transcript to find out that work is parked.

## Context and problem

The repository already knows the answer and never says it. Counted on this tree today:

- `docs/requirements.toml` holds 14 verdicts of BLOCKED and 4 of CONTRADICTED.
- Ten specifications sit at `status: draft`. A draft is a document waiting for somebody
  to approve it, and which ten is not written anywhere a person looks.
- Four capability modes carry `human_gate = "before_network"` or `"before_write"`. Those
  are the designed stopping points and no surface lists them.
- The eight production-ready boxes are all INCOMPLETE, which the page does render.

`docs/solution-intent.html` has seven sections — `resumen`, `ciclo`, `intent`, `specs`,
`decisiones`, `produccion`, `superficie`. None of them is about what is stuck. Searching
the rendered page for "bloqueado", "pendiente" or "decisión" returns nothing.

There is a second gap under the first. Even with a collector, today's case would still be
invisible: nothing wrote it down. A skill that reaches a gate it cannot pass has no way to
record "I stopped here, and this is what would unblock me". The verdicts above are the
residue of checks that ran; a build that halts leaves no residue at all.

The constitution is not the problem and must not be relaxed. A model never grants itself
authority, and a gate that a model can talk its way past is not a gate. The defect is that
a stop is silent and idle, not that it exists.

## Options considered

1. **One section on the existing page.** The freshness check already byte-compares the
   rendered page against the tree on every `just check`, so a new section inherits a gate
   that fails closed. Costs: the page grows, and a section rendered from records that do
   not exist yet needs those records written first.
2. **A second page, a queue dashboard.** Cleaner separation, and it could refresh on a
   different cadence than the Intent. Costs: a second document to keep true, a second
   freshness check to write, and the person now has two places to look — which is the
   failure mode this specification exists to remove.
3. **Push it off the repository — an issue tracker, a notification, an email.** Reaches
   the person without them opening anything. Costs: a network dependency and a credential
   in the one path that must work when everything else is broken, and the record then
   lives somewhere the audit chain cannot verify.

## Decision

Option 1, with option 3 explicitly deferred rather than discarded.

One section, `bloqueos`, on `docs/solution-intent.html`, because the page is already the
document a person is told to read, already regenerated by `ai-eng report intent --html`,
and already gated by a byte comparison that cannot report fresh over a stale page. A
second surface is a second thing that can quietly stop being true, and this repository has
already paid for one of those.

Option 3 is a later specification and not a competitor: a notification is a pointer to
this section, and building the pointer before the thing it points at is the wrong order.

Two repairs, and the second is what makes the first cover the case that happened:

**Repair 1 — the section.** `solution_intent` gains a collector that reads what already
exists and renders one row per item: BLOCKED and CONTRADICTED verdicts, specifications at
`draft` that have a plan with tasks, accepted risks past their expiry, and the modes whose
`human_gate` is not `never`. Every row carries four fields and is refused without them:
what is waiting, since when, why it stopped, and the exact command that unblocks it. A row
whose fourth field would be "ask somebody" is not rendered, because a list of things a
person cannot act on is a list they stop opening.

**Repair 2 — a stop is a record.** A skill that reaches a gate it cannot pass writes a
governed fact before it halts, and the section renders those alongside the verdicts. This
is the half that would have caught Block H: the header's requirement was real, the skip
was real, and no file on disk knew either. The record is written by the run, never by a
model asserting a conclusion — it states the gate reached and the authority missing, and
grants nothing.

## Challenged once

The strongest case against: **a list of 113 items is not actionable, it is a bug tracker
with worse ergonomics.** Counting BLOCKED, CONTRADICTED, ten drafts and four gated modes
gives a page nobody reads past the first screen, and an unread list is exactly as useful
as no list — with the added harm that it looks like the problem is solved.

The case is right about the failure mode and wrong that it is unavoidable, so the decision
is kept with the scope cut. Three things answer it. The fourth field is mandatory: a row
that cannot name the command that clears it is not rendered at all, which removes most of
the INCOMPLETE and NO-EVIDENCE mass on its own. Rows are ordered by what is blocking work
now rather than by severity, because the person's question is "what unsticks the build",
not "what is worst". And the section states its own count against the total, so a reader
can see that 9 of 113 are shown and why the other 104 are not — a filtered list that hides
its filter is the thing that looks solved and is not.

What the case does defeat is any version of this that renders everything it can find. That
version is not built.

## Assumptions and unresolved risks

Assumed without proof: that a person reads the page. Nothing here measures whether the
section is opened, and specification 015 already records that this repository ships
without instruments. If the section turns out to be unread, the answer is option 3 and not
a louder section.

Assumed: that the four fields can be filled from records that exist for every class of row
listed in repair 1. Verdicts carry a cure; `human_gate` modes do not obviously carry one,
and if a class cannot fill the fourth field it does not ship — the row count drops rather
than the requirement.

Open risk: repair 2 adds a write to a path that runs when a build is already failing, and
a recorder that throws while recording a stop turns a halt into a crash. It must be the
kind of write that cannot fail the run it is describing.

Open risk, inherited: `solution_intent.read` opens live files in the working tree, and the
freshness assertion had to leave the concurrent suite because at least one test rewrites a
repository file transiently. A section fed by more inputs widens that surface. Recorded
here because it is a known ceiling on this design, not because this specification fixes it.

Not accepted, not assumed: none of the above is an accepted risk. `ai-eng accept` is the
only thing that accepts one, and nothing here has been through it.

## Examples somebody can check

**The success.** Given a repository where `docs/requirements.toml` holds a BLOCKED verdict
with a cure, When somebody runs `ai-eng report intent --html` and opens the page, Then the
`bloqueos` section contains one row for that verdict whose fourth column is the cure text,
and `just intent-page` prints `PASS  docs/solution-intent.html matches this tree at
<digest>`.

**The denial.** Given a candidate row whose source record carries no cure, When the page is
rendered, Then the row is absent from the section and the section's own count line reads
`N de M` with M larger than N — so the omission is visible rather than silent. Checked by
`uv run pytest -q tests/test_solution_intent.py -k blocked`, which fails if a row without
a fourth field is rendered.

**The case nobody can decide.** Given a build that halted at a gate and wrote a stop record
naming an authority it did not have, And the authority arrives later in a chat window and
nowhere else, When the page is rendered, Then the row is still present and still says the
authority is missing — because a model reading approval out of a conversation is the exact
thing the constitution forbids, and a surface that cleared itself on one would be worse
than no surface. Checked by `uv run pytest -q tests/test_solution_intent.py -k authority`.

## Production-ready

Nothing gets a URL until every box is ticked, and each one is ticked by a command.

- [ ] CI/CD — build, lint, test and security analysis on every push; deploy from the default branch
- [ ] Logs — structured JSON, one line per event, with level and service, to stdout
- [ ] Traces — only if this is our code and has more than one hop; no hop, no trace
- [ ] Errors — every uncaught exception leaves as a log with severity 17 and marks its span
- [ ] Health and data age — alive, age of the newest datum, and an independent recomputation
- [ ] External check — something outside the service verifies it and says what it could not check
- [ ] Second path — every published number recomputed by an independent route and compared
- [ ] Security — secrets sealed, no credential in a plain variable, SAST and dependency audit in CI
