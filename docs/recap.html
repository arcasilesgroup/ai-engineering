01Thesis

Generating code stopped being the bottleneck; verifying it is the bottleneck. ai-engineering is the governance floor under an AI coding agent: it writes no product code and never calls a model. It installs the contract the agent works against, runs the guards the surface routes to it, and requires a receipt for every claim of done. The floor is one binary, ai-eng, and it does three things: install, guard, prove.

install The contract lands in your repo

ai-eng init writes AGENTS.md, DECISIONS.md, .ai-engineering/{config.toml, overrides.toml, arch.rules.json, ai-eng.lock}, the CI workflow and the git-hook shims, plus the adapter of every surface you pick. ai-eng init --global installs the skill canon once per machine. ai-eng update re-installs this binary's own assets with zero network; ai-eng uninstall reverts ours and keeps yours.

guard Five guards on every tool call

ai-eng chain <event> runs self-protect, no-verify, injection, wrap and loop in one dispatcher and answers in the surface's own denial dialect. ai-eng git <hook> runs the same floor at commit time, outside any agent session. ai-eng wrap reruns a test command and prints failures only.

prove Receipts, not promises

ai-eng spec run executes the milestone's gates and writes a receipt per run; a check that cannot execute is red, never absent. ai-eng doctor runs its twelve checks plus one real adversarial payload, and reports the chain's p50 and p95 latency. Every decision, rewrite and gate run lands in .ai-engineering/receipts/.

Five design rules

  • Proof beats promise. The agent shows an executed output, or the task stays pending. A decision that always comes out the same is not delegated to judgement.
  • Governance informs; a security or quality failure blocks. Everything passes → one line. Something merely annoying → not mentioned. A secret, a layer violation or a broken spec gate stops the step: it blocks instead of reporting. See §09.
  • Guards ship inside the binary. Deleting a markdown section turns off no protection. Turning a guard off costs an entry in .ai-engineering/overrides.toml with a written reason and an until date; that reason travels to the receipt, the commit-msg hook requires it, and doctor warns until it expires.
  • Your governance is yours. The contract, config, rules and hooks live in your repo and version with your code; the canon installs once per machine under ~/.ai-engineering/skills and is mirrored by symlink into each surface's discovery path. Nothing is fetched at run time — update reads the assets embedded in the binary.
  • A decision that always comes out the same is code, not a prompt. The model does not decide whether there are secrets — gitleaks does.

What the floor deliberately does not do

No metrics product and no dashboard: the local receipts are the whole telemetry. No model call: the [models] pin in config.toml is a line injected into the surfaces, never a request from ai-eng. No third-party binary installed on your behalf: adopted tools are offered as the exact command for a human to run.

Fail-open, said once

A hook timeout is fail-open on every surface: a hung hook blocks nothing, so guards are written to finish inside the hook's own budget — 5s on Claude Code, 10s on Cursor — and doctor measures the chain receipts' p95 against a 50 ms ceiling. A crash does not block either, except where the surface allows it: Cursor ships failClosed:true, and OpenCode, Oh My Pi and Pi run the chain in-process, where a guard that throws denies. Copilot CLI's machine hook fails open when ai-eng is off the PATH, on purpose — a missing binary must not deny every tool call on the machine.

2.1 · The autonomous loop: what it does, where it stops, how it reports

A human calls one skill after another as needed. An autonomous agent has no such judgement, so the loop is a skill — ai-goal — and it does not implement the loop: it contracts it. A surface that declares a native goal mode (loop: "native" in the surfaces registry) runs the loop; a surface that declares none runs in facilitator mode, where the skill walks plan.html one step at a time and the human is the clock. Either way ai-goal fixes what the loop must consume (.ai-engineering/plan.html), which gates it must close (ai-eng spec run, receipt attached), and the three stops it may not cross. Guards cannot be skipped from inside the loop because they live below it, in the tool layer.

The rule that governs the whole loop is KISS/YAGNI: the smallest thing that closes the gate. An agent under this harness can work for hours unattended; it cannot widen its own permission, rewrite spec.html once its sha256 is pinned in the lock, or declare done without a receipt. Final responsibility stays with whoever started it.

Why the init list is short

Every candidate passes three filters: it must complement ai-eng rather than duplicate a live source of truth, its license must be verifiable, and it must not widen the attack surface without a guard covering the new ground. Anything failing a filter is documented and left unoffered.

The rule that decides every future case: ai-eng offers, it never installs third-party binaries. It prints the exact command with the pinned version and the license, and a human runs it. A package manager that executes someone else's code under this project's credibility is curl | sh with a better face. The canon holds twenty ai-* skills; the tools that stay outside it — caveman, engram, impeccable, hallmark, shadcn, astryx, emil-design-eng, ui-ux-pro-max, tasteskill, tavily, exa, context7, mantis, skill-map — are named as install commands only.

04The repository, file by file

One repository holds the CLI, the skill canon and the templates that init writes into client projects. It is dogfooded: it carries its own AGENTS.md, DECISIONS.md, .ai-engineering/ and surface wiring, and its own skills govern work on it.

The binary is the payload. skills/ and templates/ are embedded into the compiled executable by scripts/gen-assets.ts, so init, update and doctor read every asset from inside the binary — never from disk, never from the network.

The line ai-eng does not cross: your remote is yours

No command of ai-eng pushes, pulls, clones or rewrites a remote. init runs git init -q when a folder has no repository and there is permission, and commits the contract it installed; everything else stays inside the working tree. The model is two clean channels: the binary, and with it the skill canon, arrives through bun or npm, where the registry signs it — your work arrives through your git, where you read the diff. Neither can stand in for the other.

05Your project after ai-eng init

It works on a bare folder. With no repository present, init offers git init -q itself (confirmation, or --yes) and closes by committing the contract — chore(ai-eng): install governance with the version, no hooks and no signature. That commit is what gives the lockfile and the Receipt-Id trailer a baseline.

Two phases, one command. The machine side runs first and always: the canon is installed or repaired, and the status line prints whether it was already intact. The project side runs only inside a repository. In a repository that is already governed, init offers update, config or exit instead of scaffolding again.

Nothing you edited is overwritten. A file byte-identical to ours is a no-op; a file that is exactly our previous version is a safe update; a file you edited that also changed on our side is reported as a conflict and left alone for a 3-way diff. AGENTS.md, DECISIONS.md and the scaffolded .gitignore are written once and are never rewritten by update.

One canon per machine

A skill is instruction, not a dependency of your code: duplicated per repository it becomes as many copies as repositories. Health is measured, not assumed — init and doctor byte-compare every canon file against the binary's payload, so a deleted or stale skill is reported instead of passing an existence check. ai-eng.lock records the sha256 the repository expects, and doctor reports drift between the lock and the canon.

Mirrors: symlink where it works, copy where it does not

macOS and Linux get a symlink — one inode, no drift. Windows gets a junction, and a copy verified by sha256 where the filesystem refuses one. CLAUDE.md follows the same rule against AGENTS.md: a symlink, or a one-line import. One truth, two mechanisms, chosen by the OS at install time and checked by doctor.

What is per project

The hooks in .git/hooks/, the surface settings, the CI workflow, config.toml, overrides.toml, arch.rules.json, ai-eng.lock, the receipts, and the four contract files: AGENTS.md, DECISIONS.md, spec.html, plan.html. Everything the tool executes lives in .ai-engineering/; everything a team reads lives at the root and survives uninstall.

What init writes once, and what arrives later

Written once by init

AGENTS.md and DECISIONS.md are rendered from their templates with the version, the detected stack commands and the date. update rewrites hooks, settings and the CI workflow and never touches these two. CLAUDE.md is created only when it is absent.

Written later, by the verb that owns it

spec.html and plan.html come from ai-eng spec open, which refuses to open a second contract while one is live and records the commit the milestone starts from. brainstorm.md and recap.html belong to the same slot, and ai-eng spec close deletes all four from the tree — git keeps the history. receipts/ fills as guards run. research/, design/, security/ and reports/ exist once their verb has been used; doctor --gc applies the growth caps in config.toml and aggregates or deletes what no document cites.

Bootstrap: with no src/ yet, the architecture rules hold off rather than fail on an empty tree — doctor activates them when the directory appears. The next move after init is the one it cannot make for you: trust the workspace in your surface, so the hooks run at all, then ai-eng doctor to prove the chain answers. The layout the CLI installs into a client repository is the payload described in 04.

Deleting the "Architecture layers" section does not switch the arch-test off — that guard reads arch.rules.json, not markdown. The only thing you can switch off is a guard, through one mechanism, with a visible cost:

[[guard.off]]
name   = "loop"
reason = "batch migration: 400 identical failures expected this week"
until  = "2026-09-05"          # every exception expires — there is no infinite date

The reason travels to the receipt, the commit-msg hook writes it into the commit as an Override-Reason: trailer, and doctor reports the override as WARN until it expires. An entry with no usable until never expires, so doctor names it as a finding rather than a neutral value. Real opt-out, not silent disappearance.

6.2 · DECISIONS.md — one real block

## D-001 · ai-engineering governs this repo ({{date}})
**Decision:** {ai} Engineering {{version}} installed (init), global skill canon, local receipts.
**Reason:** proof > promise — a decision that always comes out the same is code, not a prompt.

The template is templates/DECISIONS.md.tpl: a heading ## D-NNN · <title> (date), then Decision — the standing rule, present tense — and Reason — why it holds, present tense. One entry is one standing decision, ≤6 lines, not a post-mortem. The trigger is deliberately small: a 20-second note gets written, an 80-line ADR does not.

6.3 · spec.html + plan.html — executable WHAT and ordered HOW

One pair per milestone, in .ai-engineering/, from templates/spec.html.tpl and templates/plan.html.tpl. They are HTML because a visual surface needs no separate renderer, and they never restate each other.

spec.html says WHAT and WHY. Requirements, constraints, data contracts and acceptance gates. The gates live inside <pre id="gates"> in the format owned by skills/ai-proof/references/gates.md: a line - [ ] G1: <outcome>, indented CHECK: and EXPECT: lines, an EVIDENCE: line that starts at pending, ABANDON: G1 <reason> as the honest exit, and an optional Jobs: <n> capping concurrency for checks that are not parallel-safe. Maximum 30 gates per milestone. It is stable: it changes only when the scope changes, and CI executes it.

ai-eng spec approve pins the spec's sha256 into .ai-engineering/ai-eng.lock; from then on the self-protect guard denies agent writes to it, and ai-eng spec run refuses a spec whose hash does not match. Running the gates ticks the boxes and rewrites the EVIDENCE: lines in that same file, so both are normalized away before the comparison — the act of running never revokes the authorization that allowed the run.

plan.html says HOW, WHEN and IN WHAT ORDER. Steps that close gates (step 3 closes G2+G4), their dependencies, the Jobs: that must never run in parallel and the risk points. It is dynamic: the loop marks it every iteration, and CI never executes it. Its derived truth is the receipts of spec.html — a step marked done with no receipt behind its gate is a claim.

Generation

ai-plan writes both files when the milestone opens: spec.html with the acceptance gates and plan.html with the ordered steps. Two files, one truth each — never one file mixing requirements with a schedule.

Review

The initial review surface is spec.html itself; ai-visual-recap — a skill, not a CLI — writes recap.html when the milestone closes.

Execution

ai-eng spec run executes every CHECK of spec.html through skills/ai-proof/scripts/gate-check.mjs (never reimplemented), writes a receipt and exits non-zero when a check could not run: a check that does not run is red, never green by absence of an executor. No gates at all — the run refuses.

The machine verb has four steps: ai-eng spec run, spec open <milestone> (claims the slot and records the commit the milestone starts from, the base every conditional node is judged against), spec approve, and spec close — the only exit: it requires evidence or an honest ABANDON per gate, checks the contract was not edited after approval, refuses when a fired trigger left no artifact, then archives the pair to git and frees the slot. spec.html and plan.html are two of the four slot files, alongside brainstorm.md and recap.html.

6.4 · The model pin

# .ai-engineering/config.toml
[models]
decide  = "claude-fable-5"   # architecture, judgment, security review — expensive is fine
execute = "gpt-5.6-sol"      # end-to-end implementation, mechanical reviews
verify  = "gpt-5.6-luna"     # binary PASS/FAIL checks — cheap

One tier name per kind of work, and the asymmetry is the point: cheap to verify, expensive to judge. The node that decides whether the gauntlet passed is not economized on; the node that runs a binary check is. The values are whatever the installed surfaces resolve natively, and ai-eng never calls or proxies a model — it only reads the pin, and the skills consult it: a verdict on why something broke belongs to decide, a mechanical pass/fail to verify. ai-eng config rewrites only the surfaces key of the file, in place, so the [models], [guards] and [gc] blocks and their comments survive.

07The five guards

The guards are compiled into the binary and dispatched by src/chain/mod.ts. Its TABLE maps event and tool matcher to guards, and it is the only way a hook runs: adding an entry point means adding a row, so there is no way to add a hook without instrumentation. A guard that crashes is a DENY, not a pass — a guard that cannot decide cannot say the action is safe. self-protect

The protected literals are derived at run time, never copied from a list that could fall behind the wiring: .ai-engineering and its fixed governing children (config.toml, overrides.toml, ai-eng.lock, arch.rules.json), .git/hooks, the surface settings this install wrote (.claude/settings.json, .opencode/plugins/ai-eng.ts, .agents/hooks/ai-eng.ts), the global canon under ~/.ai-engineering/** and the home skill mirrors. The four milestone slots are the one thing inside that directory the session owns, and the guard matches them by exact name, never by prefix. Of those, spec.html joins the protected list only once its sha256 is in the lock — reopening an approved contract costs a human. The prose contracts the user owns (AGENTS.md, CLAUDE.md, DECISIONS.md) are not protected, and neither are the agent's workbench files plan.html, brainstorm.md and recap.html.

no-verify

It also decides core.hooksPath by value, never by verb: a value that resolves to nothing, or to a path outside the repo root, denies — because a hooksPath pointing at a directory that does not exist stops every hook and says nothing. The relative value this install writes resolves to an existing path and passes. The linter half has one narrow exception built into the regex: eslint-disable-next-line prettier is formatting and passes; silencing a quality or security check does not.

injection

One regex per catalogue entry, matched only against text the agent is about to consume — never text it wrote — and folded to ASCII first with NFKD decomposition, so a fullwidth letterform matches the word it imitates while a homoglyph from another alphabet does not. On a read it pre-reads the target and denies before the model sees anything: prevention. On a fetched page the read already happened, so the block stops the payload being acted on: containment, and the denial says so.

loop

Window 6, repeats 3, failures 5, overridable in the [guards] block of config.toml; state is per session. It reads only authoritative failure fields from the tool response, never the word "error" in output, so a passing suite that prints one does not fire it. The only way through is a written override — never a recipe printed to the model, which may be obeying injected text.

wrap rewrites a test command to ai-eng wrap test -- <command> before it runs, and the painters in src/wrap/paint.ts print failure blocks only — one shape per runner, grouped by file, with no I/O in the painters (§12).

Real code from src/guards/no-verify.ts. The command-side patterns:

const SKIPS: Skip[] = [
  { pattern: /\bgit\b[^|;&]*\b(commit|push|merge|rebase|am)\b[^|;&]*--no-verify/, label: "--no-verify" },
  { pattern: /\bgit\b[^|;&]*\bcommit\b[^|;&]*(?<![\w-])-[a-zA-Z]*n/, label: "git commit -n" },
  { pattern: /\bHUSKY=0\b|\bPRE_COMMIT_ALLOW_NO_VERIFY\b|\bSKIP_HOOKS\b/, label: "an environment flag" },
  { pattern: /\brm\b[^|;&]*\.git\/hooks/, label: "deleting .git/hooks" },
];

And the file-content patterns, the same rule in the other vocabulary:

const SILENCES: RegExp[] = [
  /\/\/\s*eslint-disable(?!-next-line\s+prettier)/,

SKIPS runs over the command of a Bash call; SILENCES runs over the content being written by an edit. The dispatch is a tool-name branch, and the denial is the guard's own words:

export function runNoVerify(payload: Payload, repoRoot: string | null): GuardResult {
  if (payload.tool_name === "Bash" || payload.tool_name === "PowerShell") {
    const command = payload.tool_input["command"];
    if (typeof command === "string" && command.length > 0) return checkBash(command, repoRoot);
    return undefined;
  }
  // Edit|Write|MultiEdit|NotebookEdit judge the content being written.
  const newString = payload.tool_input["new_string"] ?? payload.tool_input["content"] ?? "";
  if (typeof newString === "string" && newString.length > 0) return checkContent(newString);
  return undefined;
}

A denial is not printed by the guard. The chain translates one outcome into the host's dialect (src/chain/dialect.ts): exit 2 plus stderr for Claude Code; stdout {"hookSpecificOutput":{...,"permissionDecision":"deny"}} with exit 0 for Codex; stdout {"permission":"deny"} with exit 0 for Cursor; stdout {"permissionDecision":"deny","permissionDecisionReason"} with exit 0 for Copilot. 7.2 · The receipt — one signal, zero telemetry

The chain writes one append-only JSON per governed call under .ai-engineering/receipts/, named <timestamp>-<event>-<operation_id>.json. The fields are the type in src/receipts.ts:

// .ai-engineering/receipts/2026-08-30T09-14-02-118Z-PreToolUse-7f3a1b2c.json
{ "schema": "urn:ai-eng:receipt:2", "operation_id": "7f3a1b2c", "event": "PreToolUse",
  "surface": "claude-code", "tool": "Bash",
  "guards": { "ran": ["self-protect", "no-verify"], "denied_by": "no-verify" },
  "latency_ms": 38, "outcome": "deny", "ts": "2026-08-30T09:14:02.118Z" }

An allowed call writes the same record with "outcome": "allow" and "denied_by": null; a rewrite writes "outcome": "allow" too, because the command was not blocked. A second delivery of the same physical call is answered from the verdict cache: an allowed call writes nothing new, a denied one is re-issued in the guard's own words. There is no envelope, no HMAC and no hash-chain: the real signature is the Receipt-Id trailer — the first 8 hex characters of sha256(ts:operation_id) — which the commit-msg hook appends to the commit, so git already is the chain. When an override is active, the same hook appends Override-Reason: beside it.

doctor aggregates the folder with summarizeReceipts: total runs, denies, p50 and p95 latency, against a 50 ms ceiling applied only to chain receipts — git-floor (git-*, commit-msg) and spec-runner (spec-*) receipts carry their own budgets, and folding them in would make the chain look slow when it is not. Without the aggregate you do not know whether the chain runs at all; a long stretch with zero denies means the product is ceremony, not a guardrail.

08The skill canon

The canon is twenty skills. They install flat — one directory each, no nesting, no bundles — into ~/.ai-engineering/skills/ during the global phase of ai-eng init. Every installed file is byte-compared against the binary's embedded payload on the next ai-eng doctor: drift, missing and stale entries are named, and a directory that is not ours is reported and left alone.

One level, one naming rule

Every skill in the canon is called ai-<name>. There are no provenance suffixes, no version suffixes and no numbered siblings: a canon skill has exactly one name, and that is the name every surface and every other skill uses. A skill either belongs to the canon or it does not; once it does, it is ai-engineering's. Lineage — which upstream a method came from — is maintenance information: it lives in attribution and in the skill's own Source: line, never in the name or the path.

Every rule below is binary and runs as a gate in tests/skills.spec.ts, so bun test in CI turns a canon violation into a red build. A load-breaking rule means the skill is invisible: a surface whose loader cannot parse the file never sees it.

The seam that unites them: one format, one executor, one pin

Three contracts are shared by all twenty skills, and nothing more:

  • one format — the gates format (CHECK / EXPECT / EVIDENCE / ABANDON:). ai-plan writes it into spec.html; the CI consumes it; a gate nobody can execute is a failure, not a pass.
  • one executor — ai-eng spec run, which wraps skills/ai-proof/scripts/gate-check.mjs. One runner for the milestone's gates, in the developer's terminal and in CI, exiting non-zero when a check could not run.
  • one pin — [models] in .ai-engineering/config.toml: decide, execute, verify. Every skill reads the same table; ai-eng never calls a model, it injects the line and the surface resolves the names natively.
ai-brainstorm ──▶ ai-plan ──writes──▶ spec.html + plan.html (gates: CHECK / EXPECT / EVIDENCE / ABANDON) ai-architect ──proposes──▶ arch.rules.json (a diff in a pull request; a human approves — never auto-written) config.toml [models] ──read by──▶ every skill (decide / execute / verify — one pin for the twenty) spec.html ──executed by──▶ gate-check.mjs (ai-proof) ──▶ exit 0 / ≠ 0 + receipt · CI ai-verify evals ──test──▶ ai-verify (apply-pack.ts applies known bugs · score.ts measures recall + precision)

Every run leaves a receipt, and the receipt is the fourth shared thing without being a contract: it is how a gate proves it ran.

The duty of grounding

ai-brainstorm, ai-research, ai-architect and ai-plan cannot cite a file, an API or a library that ai-explore (code) or ai-read-docs (documentation) has not opened in this session. A requirement in the spec or the plan carries a file:line or the URL of documentation that was actually read. 09Governance

The framework improves the process underneath the work; it does not add ceremony on top of it. But informing is the default posture, not the universal rule. Something that can break you is blocked; something that cannot is a line or silence. A security or quality failure does not inform — it stops the step.

The two classes, separated

BLOCKS security and quality

The git floor. gitleaks on the staged diff at pre-commit and over the whole unpushed surface at pre-push, plus diff --check and the DECISIONS.md rule on a wide change. The floor is marker-managed shims in .git/hooks/, so it runs for a person committing from an editor too. A missing gitleaks binary is a HARD FAIL at the hook — never a silent pass.

The commit message. The convention, the Receipt-Id trailer, and the override reason when one is active are checked before the commit lands.

The no-verify guard. Denies --no-verify and every other hook-skip, a core.hooksPath redirect away from the floor, and check silences (eslint-disable, @ts-ignore, noqa, nosec, NOLINT, allow-lists).

The self-protect guard. Denies writes against the governed files, against a spec.html whose sha256 is pinned in the lock, and against the canon skills.

The injection guard. Instruction-shaped text in what the agent is about to consume is denied before the model reads it; on a page already fetched, the block is containment and says so.

The spec runner. ai-eng spec run — a check that could not execute fails the run, so CI is never green by absence of an executor.

CI. Typecheck, lint, bun test, the architecture test (bun run arch), a live contract enforced with ai-eng spec run, and the scanners: gitleaks, a pinned semgrep, trivy at HIGH+CRITICAL, and bun audit --audit-level=high over the lockfile the repository actually has.

The only way past any of it is .ai-engineering/overrides.toml with a reason and an end date. An override lands in the receipt, is required in the commit footer, and shows in doctor until it expires.

INFORMS everything else — one line or silence

The loop guard. It denies a repeated identical call (loop_window = 6, loop_repeats = 3) and a failing signature streak (loop_failures = 5), and its message tells a person — not the agent — how to grant an exception.

Canon drift. doctor byte-compares the installed skills against the binary and reports drift, missing, stale and not-ours as WARN.

A newer version. One line at the tail of init, doctor and update, cached for a day, silent offline. Opt out with notices = false or AI_ENG_NO_UPDATE_NOTICES=1.

An active override. WARN until it expires, with the days left; expired entries are named with the fix, because a guard that is live again does not make dead config harmless.

Architecture in bootstrap mode. A project with no src/ yet is not lectured about layers — it is a WARN, not a failure.

Growth caps. max_files = 25 per NNN folder and receipts_ttl = "30d" in [gc] are WARN thresholds: growth is hygiene, not security.

What a person sees on a normal day

A tool call that passes produces nothing on screen: the verdict is written to a receipt, and the same physical call is never judged twice. Output appears in exactly four situations — a denial, a rewrite, a git-floor failure, and a run that ran long.

Prompt ──▶ tool call ──▶ the chain decides ├── allow — receipt written, nothing printed (only a decision past the 200 ms hot-path budget prints one warning) ├── rewrite — a test command becomes ai-eng wrap test -- <cmd> · the filtered output plus the receipt id ├── deny — the guard, the reason, and the way out: overrides.toml with reason + until └── git floor — gitleaks finding → BLOCKED · a clean commit lands with Receipt-Id
[ai-eng] loop: a person — not you — can grant an exception: .ai-engineering/overrides.toml
         [[guard.off]] with a written reason and an until date.

3 passed · 1 failed · 4.2s
[ai-eng] chain: hot path over 200 ms (231 ms)

A denial names the guard that fired and the action that unblocks it. A rewrite is the command the agent already asked for, with the noise removed. The git floor speaks only when it blocks. The only line about slowness is the one printed when a decision exceeds its own budget.

Observe → fix → block

The rule that keeps governance from getting in the way: the guard works underneath the developer, not above them. Three levels, and only the last one interrupts.

  • OBSERVE — never seen. The chain runs on every tool call and writes its receipt; doctor aggregates the latencies (p50 and p95) against the 50 ms ceiling it also applies to a live adversarial payload. Zero output.
  • FIX — one line, not a wall. wrap rewrites a test command to the filtered runner without asking, and the model tier for each kind of work is already a value in config.toml, so it is never renegotiated mid-run. The agent never learns there was a problem.
  • BLOCK — the last resort, and only for security and quality. It interrupts once, with the reason and the exit path attached.

The design test for any new guard is one question: if this guard is correct, does it pass unnoticed? A correct guard that speaks in the normal flow is badly designed — observe or fix, do not announce. And the asymmetry is the point: informing what cannot break you, and blocking what can.

The balance, in one line

You inform what cannot break you; you block what can. The inverse — blocking trivia and informing the dangerous — is the expensive direction, and it is why the two classes above are separated rather than tuned together.

11.4 · update

Re-installs the assets ai-eng owns from the binary already on the machine. Zero network requests: the payload is embedded in the binary, the same one init installs. It syncs both halves — the repo's files and the global canon when it has drifted.

  • --yes answers the two prompts: conflicts resolve to keep mine, and Apply is taken.
  • The sync plan is computed before anything is written and shown as four classes: current (byte-identical to ours or never ours), updates (the exact previous version), fresh (not on disk), conflicts (edited by the user and changed in the new binary).

11.5 · upgrade

12.2 · What the wrapper does

src/wrap/index.ts parses wrap test -- <command>, runs the real command through /bin/sh -c with no stdin, and paints what comes back. The command is not reimplemented and not sandboxed.

  • The runner is detected from the command text: vitest, jest, playwright, bun, or generic.
  • Vitest is the one runner whose JSON reporter is free to consume: unless the command already carries --reporter, the wrapper appends --reporter=json and parses counts and failures from the report. Every other runner is painted from its own text.
  • A runner that hangs must not hang the agent: the timeout is 10 minutes and surfaces as exit 124 with TIMEOUT in the receipt line.
  • Output is a sequence of failure blocks — the file, then its failing cases and their details — followed by one summary line: <passed> passed · <failed> failed · <seconds>s. When the summary cannot be parsed the counts print as ? and the failed count falls back to the bullets actually painted.
  • It always ends with its own line naming the runner, that the output was filtered, and the receipt id: the trace must not lie about which command ran. The exit status is the runner's, so the surface still sees a failing suite as a failure.

A failing suite still exits non-zero, so a surface that reads status sees the truth even when the output was reduced to three blocks.

13Enforced architecture: dynamic in layers, static in rules

ai-engineering imposes no architecture. ai-architect detects the shape of the project and proposes rules; a human approves them. The proposal is a diff of .ai-engineering/arch.rules.json in a pull request — the skill never writes that file. Enforcement has one source of truth, and it is projected into the arch test that CI runs.

13.1 · The contract: .ai-engineering/arch.rules.json

The schema is a free-form layer map plus a rule list. Any layer name maps to a glob, so the same JSON carries a clean-architecture split, a feature-based split, a monorepo split or no layers at all — only the globs change.

13.2 · The projection: one JSON, one executed check

tests/arch.spec.ts reads .ai-engineering/arch.rules.json and projects one archunit 2.4.0 check per mayNotImport target, so the JSON is the only place a rule is written. bun run arch runs that test, and the check job of CI calls it.

the enemy silent green

A typo in a layer glob — src/doamin/** instead of src/domain/** — matches zero files, finds zero violations and passes. The typo disables the protection without a word, and a guardrail that cannot fail is worse than no guardrail.

the answer empty-test protection

The same suite asserts that every directory under src/ is a declared layer and that every rule names declared layers. The typo'd glob matches nothing, the assertion fails, and the suite goes red — a rule that cannot be evaluated is a failure, never silence.

15.2 · The loop is the surface's native loop

Every supported surface ships its own goal loop, tuned to its own harness. ai-engineering does not implement a loop, and ai-goal is not a second engine: reimplementing one would be worse on every surface at once — a second planning layer for latency, two competing progress bars for the user, and a copy that every surface release breaks. ai-goal pins the contract; the surface runs the loop.

The native goal loop provides

The engine (iterating until the objective is exhausted), context managed by the harness, model switching, session economy (compaction, usage limits), suspension and resumption with its own state.

ai-goal provides

The exit contract: the loop is fed by plan.html, not by a free interpretation of the objective; every step ends at a gate of spec.html with a receipt (the harness saying "done" counts for nothing without proof); the three stops of §02 are exit conditions; and the session budget of config.toml is the hard ceiling — the binary does not meter it, the agent honours it at step boundaries. The guards run underneath in the tool layer, so a native loop cannot skip the floor it never sees.

Which mode applies is decided by the capability the surface declares. A surface with a native goal loop runs contract mode: the skill pins the contract and the loop executes it. A surface that declares none is not handed to a loop at all — ai-goal runs facilitator mode and walks plan.html one step at a time inside the session, with the same three stops and the same receipts, the human as the clock: one step, its receipt, then stop and wait. No timer, no unattended queue, no implicit approval. On the surfaces that carry no guards in the hot path, the human order of §15.1 remains the honest mode, and facilitator mode is how it is walked.

16.2 · Cleaning and concurrency: one slot per checkout, a worktree per agent

There is exactly one spec.html, plan.html, brainstorm.md and recap.html per repository: they are slots, not numbered files. Two questions follow — who cleans, and what happens when two agents want the slot at once.

Cleaning is a ritual with verbs

ai-eng spec open <milestone> claims the slot and refuses when a live contract already exists; ai-eng spec approve pins the approved spec's sha256 in the lock (STOP 1). ai-eng spec close is the only exit: it verifies that every gate has a receipt or an ABANDON with a reason, that no fired trigger was left without an artifact, archives spec/plan/brainstorm/recap to git, deletes them from the tree and frees the slot. Because human cleaning is forgotten, doctor audits it: a live spec.html whose milestone already has a tag is a FAIL; a brainstorm.md older than the last approval is a WARN with the deletion proposed; receipts past receipts_ttl are aggregated and deleted. The invariant: no file outlives what it documents, and a file that cannot name the live milestone it belongs to is dated rubbish.

Concurrency is a slot, not a shared file

Two agents writing the same spec.html on the same branch is the one forbidden configuration, and the lock makes it physical: the sha256 pinned at STOP 1 makes the second writer receive a DENY from the self-protect guard. The sanctioned pattern for parallel features is one git worktree per agent — each worktree is a governed checkout with its own .ai-engineering/, so it has its own slot, its own receipts, its own plan.html, and two milestones on two branches are two contracts that never touch. When they converge, a merge conflict in spec.html is the gate: git raises it, a human resolves it, ai-plan merges the contracts.

This adds no human verb and no dependency: open, approve, run and close are subcommands of the machine verb spec, and worktree is git. The binary never touches the remote (§04).

16.3 · Bounded growth: the policy of the NNN folders

research/, design/audits/, security/, reports/ and receipts/ are the only folders without a natural ceiling. Growth is not fought with human discipline — that is forgotten — nor with a second copy inside the repository, which duplicates the version control system. It is fought with one rule and one flag:

The rule

The working tree is the cache of the living; git is the archive. An NNN artifact belongs in the tree while (a) a live governing file cites it — DECISIONS.md, the milestone's spec/plan, arch.rules.json, NOTICE — or (b) it fits its folder's budget. Anything else has served its historical purpose and lives better in git log --follow .ai-engineering/research/<nnn>-<name>.html than in the directory. Deleting from the tree loses nothing: the commit that added it is the archive, and the gc message says so.

The mechanism: doctor --gc — a flag, not a new verb

doctor audits; --gc executes what the audit proposes, in one commit. (1) A deterministic citation check — the NNN references found in the live governing files; cited means immune, never touched. (2) Uncited and older than older_than and already tracked by git → deleted from the tree. (3) Receipts past receipts_ttl → aggregated into receipts/summary.json and deleted; doctor reports from the summary and the permanent signature is the Receipt-Id trailer. (4) In security/, the last keep_runs runs always stay live, because the known-findings ledger of a run reads the earlier ones. Without --gc it prints the WARN and the exact command. No new verbs: the six human verbs stay six.

The caps, in config.toml (thresholds, not mystery)

[gc]
max_files    = 25    # per NNN folder — exceeding it is a WARN
older_than   = "90d" # the minimum age to be a candidate
keep_runs    = 5     # security/: the last ones always live
receipts_ttl = "30d" # receipts: aggregate, then delete

The caps are WARN, not FAIL — growth is hygiene, not security (§09). An NNN is assigned as max+1 at write time; two worktrees that pick the same number collide at the merge, and the merge is the gate — the same rule as §16.2, no new machinery. gc never rewrites history: it only adds revertible deletion commits. The backup of the archive is your remote, which ai-eng never touches.

16.5 · BEHAVIOR.md: the process criterion, in someone else's format

The framework verifies the result (the gates of spec.html, the binaries, the merge gate) and the security of the process (the compiled guards). What has nowhere else to live is the criterion of behaviour: did the loop ask before spending? did it cite or remember? did it declare done without measuring the render? Those are trajectory questions — not binary, not blockable. The answer is the open braintrustdata/agentbehavior standard (Apache-2.0), adopted in its minimal form, without its platform.

What it is and where it lives

A BEHAVIOR.md is frontmatter (name = the folder, description) plus free Markdown describing the recurring expected conduct — suggested dimensions: Intent / Evidence / Decision / Execution / Recovery / Failure modes. It lives in .agents/behaviors/<name>/, at the repository root, not in .ai-engineering/: human reviewers, eval judges and other tools of the standard read it, and ai-eng only validates it. What the tool executes lives in the tool's house; what the ecosystem reads lives where the ecosystem looks.

The line that prevents slop: one file, one meaning

spec.html asks "was the milestone met?" (binary, CI). BEHAVIOR.md asks "did the agent behave well?" (scored, a trend, never a gate). A BEHAVIOR.md that is really a task checklist is a spec.html in disguise and dies in review. The standard draws the line for us: AGENTS.md is runtime instruction; BEHAVIOR.md is the standard evals measure against. Content is not migrated from AGENTS.md to behaviors — different audiences.

Three pieces carry the cost; the standard does the rest.

  • Validation: the frontmatter linter, not a new CLI. The shape agentbehavior requires (name = folder, description ≤1024, strict YAML, unknown fields ignored) is the shape doctor already lints for SKILL.md; the linter is extended to the .agents/behaviors/ path. Vendoring a third-party CLI to validate the same shape would be one more dependency for nothing.
  • Authoring: ai-writing-behavior, the standard's own skill, on demand. Apache-2.0 and self-contained (it carries the spec in references/, no network), with the method that cannot be improvised: decide what deserves a spec — a small, high-impact set, not an inventory of instructions — and calibrate against four trajectories: positive, negative, outside-scope and lucky-correct, the lucky ending that hides a wrong process, which is the kind of false green this framework exists to catch.
  • Consumption: one method sentence in ai-verify. The decide tier reads the repository's BEHAVIOR.md files as the answer key when scoring a trajectory, under the standard's own rule: in an observational eval the agent being judged is blind to the spec — showing it beforehand would measure obedience, not conduct.

The one dogfood spec is .agents/behaviors/ai-goal-loop/BEHAVIOR.md: the native loop under contract — it asks before spending (STOP 3), never declares done without a receipt, cites what it opens (the grounding duty, §08), and on the design lane never delivers without measuring the render. One spec per lane, once an eval consumes it; zero "just in case" specs. Nothing else touches .agents/: doctor validates and ai-verify judges.
