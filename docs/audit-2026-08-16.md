## The process-optimization commitments

The 2026-08-15 audit recorded 9 PROVEN, 5 FAILED, 12 other. Four of the five FAILED are
closed above; PO-16 carries its written exception. What has to be said beside that:

**this session's work ran outside the protocol it audits.** The block cadence — a block
boundary, an independent reviewer per block, one bounded re-review — governs implementation
blocks. What ran here after Block D was continuous-integration repair: fifteen commits, each
gated by `just check` and pushed, with no block boundary and no independent reviewer. That is
not a violation of a rule that covers it; it is work the protocol has no rule for, which is
the fourth gap this repository has now recorded in it. The others are a repair that
introduces a defect, a re-review that returns REJECT, and a checkpoint that turns a shipped
test red.

## What the audit found that nobody had asked for

Seven defects, none of them in scope, all of them the same shape — a control that reads
stronger than it is:

1. `actionlint` and `zizmor` ran after `just check` in the same job, so on a branch that had
   never been green they had never executed once. Their first run found a branch name pasted
   into a shell script.
2. `ai-eng doctor --ci` cannot exit 0 on any commit, and the gate took its exit code as a
   verdict.
3. `ai-eng audit verify` ran before anything had been sealed into the chain, so it could
   neither pass nor verify anything.
4. The fenced-block recogniser in the acceptance register required a bare newline, so a spec
   file written on Windows read as holding no acceptances — a PASS over an empty register.
5. `decide --accept` put command-line text into a glob pattern; `..` is a legal glob segment.
6. `authority_role` from the Intent was interpolated into the MADR header between bare
   quotes, so an edited Intent could forge `status` and `supersedes`.
7. The Codex hook entry used three key names Codex CLI does not define, so that guard could
   never have deserialised.

### `EP-051`: the artefact where flipping a byte proves nothing

Two artefacts already had a tamper fixture — one flipped byte of the scanner rules, and an
SBOM valid in every way that describes a different wheel. The row named the gap: no fixture
for the scanner binary itself.

A binary is the one artefact where flipping a byte proves nothing. It either still runs or it
does not, and a scanner that does not run is already caught. What has to be tampered with is
the *answer*. The version pin catches a scanner that is the wrong build; it cannot catch one
that reports the right version and finds nothing — a wrapper on `PATH`, a configuration that
disabled every rule, an ignore file somebody added upstream. From inside this process those
are indistinguishable from a clean tree, and "clean" is what the framework then publishes
about somebody's records.

So a clean scan is believed only after the same scanner, invoked the same way, has found a
secret planted where one certainly is. Three answers, three outcomes: found is PASS, not found
is INCOMPLETE naming the scanner rather than the bytes, and a canary that could not run is
INCOMPLETE saying so — which is a third answer and not either of the other two.

The first version of the canary used AWS's own published example key and came back False. The
scanner allowlists it, precisely because it is the string every tutorial contains. A canary
the scanner is entitled to ignore fails for a reason that is not the one it exists to detect,
and it would have turned this control into a permanent refusal on every clean run. That is
written into the source beside the constant, because the next person to change the planted
value needs to know why this one was chosen.

It also caught a stand-in. Two test fixtures modelled a scanner by answering "clean" to every
directory, which is exactly the tampered scanner this refuses — a stand-in for a working
scanner now has to behave like one.
