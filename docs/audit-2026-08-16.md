# What this audit withdrew, and what it cost to find out

`docs/requirements.toml` is the record. It holds every requirement, its verdict, and the
command that decides it — and `tests/ledger_run.py` runs those commands, so the verdicts
can be checked rather than read.

This file holds the one thing the ledger cannot: **the history of its own corrections**. A
verdict that was withdrawn, an overclaim a reviewer caught, a number that was published too
high. The ledger says what is true today; this says what it said yesterday and why that was
wrong, which is the only part of an audit that cannot be re-derived from the tree.

It used to be two files and 1,851 lines, most of it re-measurement that the ledger already
held in a form a command could execute. That duplication had a gate of its own — a test
whose only job was to check that a number printed here matched the number in the ledger —
and a gate that exists because one fact has two homes is a gate that should not exist.
Both are gone. What follows is the part that was never anywhere else.

## The structural gap
**Thirty-six requirements have no owning spec.** EP-062 through EP-097, except EP-081 —
the entire thesis and mission section, and the whole "Propuesta" column of the comparative
X-ray. That includes EP-066 (the corrected mission, measured INCOMPLETE against
`CONSTITUTION.md`: four of its nine verbs and its guardrails clause are unrecorded),
EP-084 (observability attribution), EP-090 (a JSON envelope with a schema — the current
one validates against nothing) and EP-095 (the stakeholder section).

Specs 011 through 015 own the five waves. Nothing owns the document's own thesis.

## The six proofs this audit withdrew

The previous audit granted these and the re-run would not.

- **EP-077, EP-079, EP-090** — each was credited to a mechanism that exists beside the
  requirement rather than under it: a file-home check for an adapter claim, a readable
  `audit verify` for an envelope claim, two pinned dependencies for a schema claim. There is
  still no envelope schema in `policy/` and `spec list --json` emits a `schema_version` with
  no `schema`.
- **EP-285** — `FLOOR = 89` exists in the justfile and no whole-tree mutation score does.
  The lane that would produce one has never completed on this branch: it hits its
  30-minute cap mid-run. A floor nothing has ever measured against is a number, not a gate.
- **EP-287** — closed above as a FAILED item and withdrawn as a P5 indicator, which is not a
  contradiction: the rule is now read and recorded, and no command publishes the number.
- **EP-308** — a closed fifteen-capability list is not a check that a sixteenth capability
  cannot be declared without governance.

## The block hand-offs

`specs/010/plan.md` requires a block to close with a hand-off carrying six things: the base,
the final HEAD, the commits reviewed, the related-suite output, the reviewer's disposition,
the repair commits and the gate output. The audit above found it written in no commit on this
branch, including the two block reviews that did happen. Here they are — E and F late, G on
the day.

They are late and say so. A hand-off written after the fact cannot prove the freeze it claims
— nobody can now show that writes stopped while the reviewer read — so what these record is
what is checkable from the tree: the range, the commits, the findings and the repairs. The
freeze is asserted and not proven, which is the honest half of writing this down at all.

### `PO-01`, `PO-06` and `PO-13`

The audit above recorded these three as the honest failure: the block cadence did not govern
requirement-closure work, and the protocol had no rule for it. Both halves have moved — and a
reader that was not this session graded the result **INCOMPLETE**, not closed. The correction
is below and it stands over what follows it.

The rule is `docs/adr/0011`, accepted by the repository owner on 2026-08-17. The execution is
Block G above: a boundary, one independent read-only reviewer given the requirement texts, one
ledger, one bounded repair pass, one gate run per repair, and a hand-off. And it paid on its
first use, which is what the record predicted it would and what it is fair to hold it to.

What is now checkable rather than asserted: `tests/test_record.py` reads this section and
requires every block named here to carry a reviewer disposition, a repair and a gate line. A
cadence whose evidence is prose is a cadence that lapses the first busy afternoon — which is
exactly how these three came to be open.

**And an independent reader graded that not enough, hours after it was written.** Its argument
is the one this section already concedes and then walks past: `gh run list` for the branch
carrying all of it returns zero rows. No continuous integration has run on it at all. So the
freeze holding, the reviewer being independent, and the gate being green after each repair are
this record's own prose about itself, with nothing outside it to check against. It also made
the smaller point that matters more: **one execution is not "governs"**. A rule accepted this
morning and run once this afternoon is a rule with one data point.

`docs/requirements.toml` therefore carries `PO-01`, `PO-06` and `PO-13` as INCOMPLETE, each
naming that gap, and this paragraph exists so the prose above cannot be read as claiming
otherwise. What closes them is not more writing: it is a pull request on this branch so a
gate result exists that nobody here authored, and a second and third block that run under the
rule without anybody deciding to.

### `PO-16`, and the audit grading the session that commissioned it

The same reader graded `PO-16` **CONTRADICTED**, and it is about this session's own commits.
The commitment is one primary home per commit. The exception the owner granted covers a commit
that moves a count or a ceiling another check forces it to move. The widest commit on this
branch touches twenty-one files: four source modules, nine test files, two workflows, a policy
table, a skill and a whole new specification.

That is not a commit moving a count. The rule says one home; the practice here is twenty-one,
exception included. It is recorded rather than argued, because the argument available — that a
block repair pass is one logical change — is one the exception does not make, and a session
that writes its own exemption into the record it is being judged by has learned nothing from
the eighty-six.

### The field all three hand-offs are missing

**No independent record of the gate run.** The receipts are gitignored and the workflow does
not trigger on a push to this branch, so "green after the repair" is this record's word in
every row above. That is the finding this audit already carries, and writing three hand-offs
does not close it. For Block G it is narrower and worth naming: the branch carrying these
repairs has no pull request, so no CI has run on it at all, and the only gate anybody can
point at is local.

### The twenty-six, measured like the three hundred and eighty-five

`docs/requirements.toml` now carries one row per process commitment, with the command that
decides it, held by `tests/test_requirements_ledger.py` to the same three rules as every
product requirement: a verdict from six words, a command on every row, and a reason on every
row that is not PROVEN.

**Fourteen of twenty-six are proven.** Seven are INCOMPLETE, three are NO-EVIDENCE and were
honestly reported as not reached, one is UNFALSIFIABLE, and one — `PO-16` — is CONTRADICTED.

Three of the seven INCOMPLETE (`PO-01`, `PO-06`, `PO-13`) and the one CONTRADICTED are
corrections to claims made in this repository earlier the same day. That is the entire reason
the pass was run by somebody else.

## Measured a fourth time, and the published number was 86 too high

`docs/requirements.toml` is what this section exists to introduce, and it is the first thing
in this repository that answers "which requirement is open" rather than "how many are".

Everything above this line publishes counts. The first pass listed every id, and the second
and third re-measured 196 of them in bulk and named only the notable movements — so from the
second pass onward the totals are real and the membership is not recorded anywhere. That was
not visible as a defect until somebody tried to use it: asked which requirements remained,
this document can produce a number and cannot produce a list.

So it was measured again on 2026-08-17, by four independent read-only auditors, one per range,
each told that a verdict must come from something executed and that a test whose name matches
a requirement is not evidence until you break it and watch it go red.

| verdict | count |
|---|---:|
| PROVEN | **180** |
| NO-EVIDENCE | 89 |
| INCOMPLETE | 82 |
| BLOCKED | 16 |
| UNFALSIFIABLE | 13 |
| CONTRADICTED | 5 |
| total | 385 |

**180 of 385** when it was measured, against 266 published. The gap is 86 and almost all of it
is one habit.

The first pass recorded its PROVEN set as compressed ranges — `EP-141–EP-150`, `EP-217–EP-238`
and a dozen more. Roughly sixty of the ids inside those ranges have no description in this
document, no test naming them, no spec row and no command anywhere in the tree. Two auditors
working on different ranges, neither able to see the other's work, reported the same thing in
almost the same words and both refused to inherit the verdict. They were right to.

And one of them is worse than unevidenced. `EP-147` sat inside `EP-141–EP-150` as PROVEN; a
reader checked it and found `deny_protocol` has no producer anywhere, the receipt schema
carries none of the fields the requirement names, and specification 011's own closing table
records it as INCOMPLETE. Not a missing proof — a false one, published, for weeks.

Nothing here says the work was not done. 180 requirements are proven by a command somebody
ran, and the pass also moved twelve rows *up* on evidence that landed after they were last
measured. What it says is that this project published a number it could not reconstruct, in
the one document whose subject is not publishing numbers you cannot reconstruct.

**186 of 385** as of this commit. Six closed within the hour of the ledger landing, and it is worth
saying how, because it is the argument for having built it: five clauses were sitting in
`ai-design` where nothing read them — deletable with the whole suite green — and the pass found
them because it asked every requirement the same question instead of re-reading the pin table.
The sixth, `PO-17`, had been asked for by the plan since it was written and run by nothing: a
staged hunk with a whitespace error or a conflict marker in it now stops the commit, which took
four lines in a hook that already existed.

`EP-254` was deliberately not closed with them, though its clause sits two lines from the five.
It asks that imagery lose its metadata and be scanned, which is a mechanical act and not an
instruction, and pinning prose to close it would be exactly the move this document spent the
day undoing.

The correction that matters is not the number. It is that `docs/requirements.toml` now holds
one row per requirement with the command that decides it, and
`tests/test_requirements_ledger.py` refuses a row that names none — which is exactly the
check that would have caught this, and which nothing did.

### Three things this day found that were not on any list

**`ai-eng spec new` could not run in this repository at all.** The Intent was active and
approved, and the verb refused because `authority_role` read `repository owner` while
`accountable_role` read `repository maintainer` — two names for one person, compared as
strings. The check is right and its message named none of the four conditions it enforces,
so the cause took reading the source. A control that is right and illegible gets worked
around rather than fixed.

**Two adapters landed together and one had no denial behind it**, which `D-011-02` forbids
in those words. The precedent had no reader until the requirement asking for one was closed,
and the first thing the new reader caught was the session that wrote it. The adapter was
removed rather than excepted: a rule you write yourself an exception to on the day it first
applies to you is not a rule.

**The mutation lane was a red nobody could clear.** It refused when a branch was wider than
it can measure, and refusing meant failing, so on a wide branch no commit could make it
green. It hands the question to the whole-tree run now and requires that run's receipt — and
the whole-tree run opens its own issue when it fails, because a nightly that blocks nothing
reaches nobody unless it goes and finds them.

## Four instalments against the mutation floor, and what each one cost

The owner's decision on 2026-08-17 was that the floor stays at 89 and the tests get better.
This is the arithmetic so far, module by module, because "we improved the tests" is the kind
of sentence this document exists to replace with a number.

| what | before | after | what moved it |
|---|---|---|---|
| `imagery` + `executor` | 77% | 86% | refusals pinned whole; one real defect found |
| `update` + `uninstall` | 75% | 78% | what the two verbs say when they refuse |
| `scan` + `spec` | 76% | 80% | the envelope, the numbering, the security report |
| whole tree | — | 72% | measured for the first time, 21,960 mutants |

**The technique is not transferable and that is the finding.** Pinning help blocks took
`update` and `uninstall` up three points and took `spec` up almost nothing — six mutants of
three hundred and ninety-five — because `spec`'s help was already reachable through other
cases. Measuring first is the only thing that could have said so, and the negative result is
in the commit rather than repeated.

What does transfer is the shape underneath it: **every survivor worth killing is a sentence
somebody reads, or a decision nobody watched being taken.** The five refusals in `spec.main`.
The three checks in a created spec's envelope, which are three distinct claims about what was
verified. The whole printed report of the security gate, in order, because one that says the
right things in the wrong order is one a person misreads. The number that names every
governed record, which must be one past the highest and never one past the count.

Three real defects came out of the four instalments rather than only coverage: a docstring
claiming a symlink refusal the code did not make, a runner that stopped being a command, and
a derived check that read the mutated tree. Each was invisible to the local gate.

**The gap is about 3,700 mutants at the whole-tree level.** At the rate above that is not one
session's work, and saying so is more useful than a plan that assumes otherwise.

## 18 August 2026 — the fifth pass: the answer key was never run

The four passes above measured the tree against two documents and wrote the verdicts down.
None of them ran the commands.

`docs/requirements.toml` names a command beside every requirement it calls proven, and until
today the only thing checking those commands was `test_every_row_names_the_command_that_
decides_it`, which asserts that each row names something at least eight characters long. That
is a check on the length of a sentence. `tests/ledger_run.py` executes them instead.

On the first honest run, **24 of the 222 proven rows did not hold**. None of them were wrong
about the tree; all of them were wrong as commands:

- Seven were absence claims — *no second values layer*, *no hand-set proven flag*, *no commit
  calls itself done* — whose command printed the absence and exited non-zero **precisely when
  the absence was true**.
- Five required a zero exit from `ai-eng report surfaces` and `ai-eng doctor --ci`, whose
  honest answer here is INCOMPLETE. Two of those five say in their own note that what is
  proven is that two readers *agree on an open failure*, so requiring success was requiring
  the opposite of the claim.
- Three passed `-k a or b` unquoted, so the shell handed pytest three arguments.
- Two used basic `grep` with `|` in the pattern, which is a literal pipe there, and had
  matched nothing since the day they were written.
- One named a function renamed days earlier. One was a heredoc with a prose parenthetical
  inside it and was never a command. One staged a file in the operator's own repository.

Running the key over the rows that are **not** marked proven found something larger. 130 of
155 passed, and almost all of it was one shape: `git grep -n 'EP-350' -- .` finds `EP-350`,
in this file, on the line asking the question. Sixty-six rows carried that command. Their
verdicts were honest — every one says NO-EVIDENCE — but a later reader running the key over
every row instead of only the proven ones would have flipped sixty-six verdicts to PROVEN on
a self-reference and read it as progress.

Excluding this ledger and this document fixed sixty-four. Two survived on a comment
discussing the range `EP-141–EP-150`, which is where the technique ends: no search for an
identifier distinguishes a mention of a requirement from an implementation of one. Those
sixty-four rows now say, in one fixed phrase, that there is nothing to run, and the test
refuses a command on such a row rather than demanding one. A shape check satisfiable by
theatre produces theatre.

The published total does not move: **205 of 385**. Not one verdict changed, because not one
of the twenty-four was wrong about the tree. What changed is that the document can now be
checked rather than read, and the check runs on the nightly lane before the mutation run —
before it, because a false verdict in the answer key makes every number measured after it a
number about the wrong tree.

One row is open as this is written, and it is the key working rather than failing. `PO-09`
asks GitHub for the check-runs at this exact HEAD, and GitHub has never seen this HEAD: six
commits sit on this machine and nowhere else. The row says the specification stays draft
until a candidate proves its own exact-HEAD receipts, and it is correctly reporting that this
candidate has not.

### `PO-12`, and three commits that proved nothing

`PO-12` asks that a commit's focal test fail before the change and pass after it. The note
under it said why nobody had checked: two checkouts and a targeted run per task, up to
fifty-three times. `tests/red_then_green.py` does it — the parent's `src` and `hooks` laid
under the commit's own new tests, each in its own worktree.

Over the 73 commits of this branch: 24 added no tests, 30 pin behaviour that did not change,
**16 are red at their parent, and 3 proved nothing**.

The three are real and one is worth naming. `09b15096` introduced `doctor.accessibility_floor`
— assertion 26, the accessibility gate — and added nine tests with it. Every one of the nine
passes against the source from before the commit, because all nine test `policy/accessibility.
toml` and the `ui` and `outcome` behaviour that already existed. The tests for the assertion
itself arrived in a later commit. Nothing was wrong with the assertion; what was wrong is that
the commit shipping it cited tests that would have passed without it.

The runner had to learn one distinction before it could say that. Its first version called
three of this session's own commits "proved nothing", and it was wrong: a commit that adds
tests over unchanged code is a characterisation commit, and its tests are *supposed* to pass
at the parent — what proves them is the mutation score. Drawing that line by reading the diff
failed too, because in a repository where the comments outnumber the code, a commit whose
entire product diff is the second and later lines of a docstring looks like a change. It is
drawn now by parsing both versions of every product file the commit touched and comparing
what is left once the prose and the ceiling are gone.

### What the mutation floor costs, measured rather than estimated

The floor is 89 and the instruction is that the tests get better, never that the number
comes down. This is what that costs at the rate actually observed, so the instruction is
given with its price rather than without one.

Over one day, 144 tests written specifically to kill surviving mutants killed **177** of
them: **1.23 mutants per test**. That figure is measured five times, per module, not
projected — `acceptance` 55 then 60 then 7, `cli` 38, `init` and `audit` together 17.

The gap from the whole-tree measurement of 2026-08-18 is **3,231 mutants**. At 1.23 per
test that is roughly **2,600 more tests**, against a suite that holds 1,901 today.

The rate is not constant and it does not improve. It falls inside every module as the cheap
half is taken first, and it does not transfer between them: in `acceptance` the first
twenty-one cases killed 55, the next forty killed 60, and the fifteen after that killed 7.
The same shape appeared in `madr`, where sixty-six cases bought six points and the next
twenty-eight bought one.

Two things follow, and neither is a proposal to move the floor.

The survivors are spread across every module rather than pooled in one, so no single
afternoon closes this and no single technique does either. And the honest way to spend
effort against it is the way it was spent today: pick the function with the largest pool,
write the cases its branches ask for, measure, and stop when the rate falls — which found
two real defects in the product on the way, both of the same kind. `--debug` in JSON mode
wrote its traceback into `/dev/null`, and `_safe_path` accepted a named pipe while the line
above it said it rejects special files. Neither would have been found by reading, and
neither was the mutant that led to it.

### The same rate, measured a second time over five different modules

The figure above — 1.23 mutants killed per test — was taken over `acceptance`, `cli`,
`init` and `audit`. A second pass covered `accept`, `report`, `decide`, `checkpoint` and
`intent`, none of which had been touched: **94 tests killed 97 mutants, 1.03 per test**.

Cumulatively over the day: **274 mutants killed by 238 tests, 1.15 per test**. The two
measurements agree to within a fifth of a mutant across nine modules, which is what makes
the projection worth stating rather than guessing: the gap to the floor is roughly **2,600
more tests** against a suite that now holds 2,016.

What the second pass adds is that the rate did not improve on fresh ground. It was not the
tail of `acceptance` dragging the number down — five untouched modules produced the same
figure, which means the shape of the remaining work is the same everywhere: the cheap half
of each module is gone, and what is left costs about one test per mutant regardless of
which module it is in.

The secondary yield is what makes the exercise worth its cost at that rate. Over the same
238 tests it produced two real defects in the product — `--debug` writing its traceback
into `/dev/null` in JSON mode, and `_safe_path` accepting a named pipe while the line above
it claimed to reject special files — plus one test that silenced every test that ran after
it, and three commits in the branch's history whose own tests would have passed without the
change they shipped with. None of those was the mutant that led to it.

### The whole tree at the close: 72% to 77%, and why the per-module figure understated it

Measured over 22,860 mutants: **17,516 killed, 5,185 survived — 77%**. Against 75% this
morning and 72% on 2026-08-17.

The interesting part is the rate. Per module, this session measured 1.15 mutants killed per
test across nine modules. Over the whole tree, the same work reads **1.35 per test** — 404
survivors killed by 299 tests between the two whole-tree runs.

The difference is not noise and it is not an error in either figure. A per-module run scopes
the mutants to one file, so a test written for `acceptance` that also happens to kill three
mutants in `issue` or `outcome` never appears in `acceptance`'s number. The whole-tree run
counts them. **The per-module measurement is the pessimistic one**, and the honest reading is
that it undercounts by about a fifth.

At the whole-tree rate the gap is **2,829 mutants, roughly 2,100 more tests** against a suite
that now holds 2,045 — down from the 2,600 projected this morning, and still measured in
weeks rather than in a session.

Where the survivors are now, in order: `spec_transaction` 389, `acceptance` 383, `init` 341,
`audit` 313, `madr` 266, `update` 259, `cli` 243, `decide` 242. Every module worked today is
still in that list, which is the same finding as before stated more precisely: the cheap half
of each is gone and the tail is long everywhere.
