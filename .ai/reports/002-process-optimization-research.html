Commit pequeño y probado. Review profunda por capacidad. Review final del sistema.

La review final deja de ser la primera búsqueda de defectos. Se concentra en integración, gobernanza, evidencia y release.

Explicado sin proceso interno

  1. Fabricamos varias piezas relacionadas. Cada pieza se prueba al crearla.
  2. No esperamos al inspector entre piezas. El writer mantiene el contexto y continúa.
  3. Montamos el módulo pequeño. Entonces un reviewer inspecciona las piezas y cómo trabajan juntas.
  4. Corregimos todo el módulo de una vez. Ejecutamos el gate completo una vez.
  5. Antes de terminar la máquina, hacemos una review final de integración.

Cómo queda el proceso

El ahorro viene de quitar esperas y gates completos entre Tasks. No viene de quitar TDD, commits atómicos, reviewer independiente, fail-closed ni el gate final.

Implementar una Task

Un writer, scope aprobado, rojo primero, implementación mínima y focal verde.

Crear checkpoint

Commit atómico y revertible. Se marca UNREVIEWED: no está aprobado, terminado, mergeable ni publicable.

Continuar el bloque

El writer implementa la siguiente Task relacionada sin esperar reviewer ni ejecutar just check completo.

Cerrar la capacidad

Se ejecuta la suite relacionada y se congela el bloque. Nada posterior depende del bloque hasta revisarlo.

Review consolidada

Un reviewer independiente inspecciona cada commit y el diff acumulado: scope, arquitectura, integración, seguridad, tests y rollback.

Corregir una vez

El writer recibe un ledger completo, corrige todos los findings y pasa una re-review acotada.

Gate del bloque

just check una vez; dos solo si el primero falla y se modifica el código. El bloque queda aprobado y puede alimentar al siguiente.

Review final

Al terminar P0: integración entre bloques, autoridad, hard renames, completeness, readiness, receipts y gate exacto del HEAD final.

Lo que eliminamos

  • Reviewer después de cada Task.
  • Espera writer → reviewer → writer por cada microcorrección.
  • just check después de cada Task y finding.
  • Reabrir una exploración completa por cada arreglo pequeño.
  • task-check, dashboards y telemetría como solución inmediata.

Lo que conservamos

  • TDD rojo primero y focal exacto.
  • Un commit atómico y rollback por Task.
  • Un solo writer antes de P3.
  • Reviewer independiente por bloque.
  • Fail-closed, adversarial, scanners y just check.
  • Hashes, autoridad humana, sin aliases, shims ni suppressions.

Qué hacemos en cada commit

No basta con comprobar secretos. Eso evitaría una fuga, pero todavía permitiría un commit que rompe su función, escribe fuera del repositorio, concede autoridad inexistente o no puede revertirse.

Control mínimo y barato

No hay review semántica ni gate completo. Solo las pruebas deterministas necesarias para que el commit sea un checkpoint seguro y comprensible.

Importante: el commit intermedio no se llama “done” ni “PASS”. Es trabajo probado localmente, pero todavía no revisado.

  • Scope autorizadoExactamente una Task, un primary home y tests/fixtures permitidos.
  • Focal rojo → verdeEl test exacto del plan falla antes del cambio y pasa después.
  • Suite inmediataTests baratos del módulo cuando existan; no el gate completo.
  • Diff limpiogit diff --check y commit revertible con git revert.
  • Higiene y privacidadSin secretos, PII, rutas de máquina, suppressions ni --no-verify.
  • Sin autoridad inventadaNada de publicar, instalar, aceptar riesgo o declarar el bloque aprobado.

Cuándo cerrar antes

Un bloque no se mide solo por número de Tasks. Se cierra cuando aparece una frontera que otras Tasks van a consumir.

  • Autoridad, aceptación de riesgo o outcome terminal.
  • Guard fail-closed, telemetry o dispatcher blocking.
  • Parser de input no confiable, Git history o filesystem.
  • Symlinks, concurrencia, transacciones o rollback.
  • Mutación global, uninstall, red, publishing o release.
  • CI, evidence, provenance o los propios gates.

El punto no es revisar “por calendario”. Es revisar antes de construir dependencias encima de una frontera todavía no inspeccionada.

Qué revisamos en el bloque y qué dejamos para el final

La review final sí aporta valor, pero como review de sistema. No debe ser la primera vez que alguien intenta encontrar un escape de path o un fallo de autoridad en miles de líneas.

Al cerrar cada bloque

  • Cada commit cumple su Task, scope y rollback.
  • El resultado integrado de la capacidad.
  • Fail-closed, autoridad y datos no confiables.
  • Filesystem, Git, concurrencia y transacciones aplicables.
  • KISS, DRY, YAGNI, SOLID y Clean Architecture.
  • Tests, adversariales cercanos y falsos positivos.
  • Ledger consolidado de findings y re-review.

En la review final de P0

  • Trazabilidad Spec 010 → bloques → implementación → tests.
  • Contratos y dependencias entre capacidades.
  • Hard renames y ausencia de homes/aliases antiguos.
  • Flujos completos de autoridad, outcomes y evidence.
  • Wheel instalado y surfaces.
  • CI, install matrix, readiness y release evidence.
  • Presupuesto exacto y receipts del mismo HEAD.

Qué dijo el LLM Council

Tres análisis independientes evaluaron la propuesta desde seguridad/gobernanza, delivery flow y el mejor caso posible de “review solo al final”.

Seguridad y gobernanza

Recomienda bloques de capacidad. Solo secretos no basta; el mínimo incluye focal, scope, privacidad, suppressions y rollback. Las fronteras de autoridad y fail-closed se revisan antes de ser consumidas.

Delivery y arquitectura

Recomienda commit por Task y review/gate por bloque. Reduce los costes fijos de handoff alrededor de 70–85% según el número de bloques, manteniendo diffs pequeños y reversibles. [estimación, no medición]

Abogado del final-only

Acepta que final-only maximiza continuidad del writer, pero lo rechaza para 37 Tasks y hasta 20.000 líneas previstas: los fallos fundacionales contaminarían consumidores y la review perdería profundidad.

Consenso: tu mecanismo principal es correcto —batching—, pero el punto seguro no es Task 53. Es el cierre de cada capacidad, más una review final transversal.
