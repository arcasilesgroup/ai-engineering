What obra/superpowers does that this repo does not

Research brief — github.com/obra/superpowers, branch main, accessed 2026-08. Everything below is from the repository's own files (primary source) or its public issues.

1. What it actually is

A "complete software development methodology for your coding agents", built from composable, trigger-based skills plus bootstrap instructions that make the agent consult them [1]. Distributed as a per-harness plugin shim; current version 6.3.0, MIT [2]. By Jesse Vincent and Prime Radiant ("obra" org).

No "workflow" entity type exists. A skill is a reference guide (technique / pattern / reference) with YAML frontmatter and a SKILL.md body; "workflow" is the ordered sequence of skills that fire automatically: brainstorming → using-git-worktrees → writing-plans → subagent-driven-development OR executing-plans → test-driven-development → requesting-code-review → finishing-a-development-branch [1][2]. Historically the workflow steps were slash-commands; those macro shims were removed and replaced with direct invocation via each harness's native Skill tool [4][5].

2. The delivery mechanism: a SessionStart hook, not installed files

The repo ships a hooks/session-start bash hook that reads the meta-skill and injects it as session-start additional context in each harness's shape (Cursor additional_context; Claude Code hookSpecificOutput.additionalContext; Copilot/SDK-standard top-level additionalContext) [6]. This is the whole distributed mechanism — very close to this repo's "no file lands in the project" idea, but keyed on a session-start hook straight into the agent's context.

3. The mandatory skill-check protocol (what "auto-trigger" means)

The using-superpowers meta-skill is deliberately aggressive: "if you think there is even a 1% chance a skill might apply, you MUST invoke it before any response or action" — including clarifying questions, exploring the codebase or checking files; then announce "Using [skill] to [purpose]". It ships a "Red Flags" table of rationalizations to stop on ("this is just a simple question", "let me explore the codebase first", "I remember this skill"…). Subagents dispatched to a task explicitly skip the protocol (<SUBAGENT-STOP>) so it does not recurse [7].

4. Skill authoring: TDD applied to documentation

The writing-skills skill is the most transferable piece: documentation is RED–GREEN–REFACTOR.

  • no skill without a failing test first — you must watch an agent fail without the skill (baseline), then verify it complies with it (GREEN), then close loopholes (REFACTOR). Writing before testing means delete and start over [8].
  • description states ONLY when to use, never what the skill does. A description that summarizes the workflow made agents follow the description instead of reading the body — measured in their head-to-head wording tests. "Use when executing implementation plans with independent tasks" (triggers only), not "dispatches subagent per task with review" (workflow) [8].
  • Match the form to the failure: prohibitions backfire on shaping problems (agents negotiate with "don't X"); positive recipes ("say what the output IS") work better for shape. No nuance clauses — "don't X unless it matters" reopens the negotiation [8].
  • Skill-discovery keywords mirror your problem's symptoms/errors ("flaky", "Hook timed out"), active voice names (creating-skills, condition-based-waiting), token budgets (frequently-loaded: <200 words; getting-started <150; others <500), heavy references split into separate files [8].

5. The subagent-driven development loop

The README's core: once a plan is approved, the agent works autonomously for "a couple of hours" without deviating from the plan. The subagent-driven-development skill dispatches a fresh subagent per task (clean context — no inherited reasoning), then a two-stage review (spec-compliance first, then code-quality), then the next task [9][10]. This is exactly the "IDE let the host decide how many agents" model you were describing, and it is why there is no "one writer" rule there: isolation is bought by per-task subagents, not by serializing the main thread [9].

6. Known criticisms and limits

Token cost is the dominant complaint.
Issue #190: all skills preloaded at startup consumed 22k+ tokens (~11% of context); dormant skills still cost "description rent" even when they never fire. Independent measure (Ken Imoto): 5 skills loaded, 3 never fired, skills ≈ 18% of bill over 7h [11][12][13]. (Their skills are large; their description discipline is the mitigation, ours is the framing.)
Heaviness / slow plan phase.
Issue #781: "approval process too cumbersome, plan formulation too long"; SDD's review loops turn minutes into hours for small tasks [14].
SoMe' no "braid" skill manager in 2026.
The task premise mentioned "braid"; the current tree has none — that was a historical, pre-plugin loader (late 2025). Today it's session-start hooks + the harness-native Skill tool [15][16].

7. The four ideas worth taking from here

  1. A session-start injection (`hooks/session-start`) instead of writing files. Your distribution already avoids writing into consumer repos, but it does it by landing seven files + guards registered in profiles; Superpowers instead injects a meta-skill into agent context at startup, keyed per-harness. That is a different distribution surface worth evaluating.
  2. The "using-superpowers" mandatory skill-check protocol — a meta-skill that forces "check skills before any action" and includes a rationalization Red-Flags table. This repo has no equivalent of a "always check the skill tree first" instruction; its rejections live in AGENTS.md and per-skill triggers.
  3. TDD for skills (WRITE skills like code, with a failing-test-first baseline) — namely: watch an agent fail without a skill before you ship it. This repo treats skills as prose (even with SKILL_FOG_CEILING); Superpowers treats skills as code and enforces a test-first rule.
  4. description discipline: "when to use" only, never the workflow. Their own measurement (agents follow the description instead of the body) is exactly the failure mode your "always-loaded budget" doctrine guards against, applied to skill description.

8. What is NOT transferable (and why)

  • No fail-closed guardrail in superpowers. There is no fail-closed belt-and-suspenders: the "1% rule" is a prompt injunction, not a check. A gate that is also a prompt is the failure this repo exists to fix — this repo has no fail-closed=red-gate equivalent to borrow; keep fail-closed machinery inside the framework.
  • Autonomy as a selling point — the "2 hours autonomous without deviating" is contrary to this repo's "green gate before done" + receipts. An autonomous mode built here would still need a receipt for every step.
  • Large skills. Superpowers skills are big (tokens). This repo caps skill readability (FOG) and always-loaded budget; its skills are meant to be small. The tuning difference matters more than the implementation.
