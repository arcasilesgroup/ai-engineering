State, gaps, and the research behind the next spec

What ai-engineering is today, the eight goals it must serve, and what primary sources say about each open decision. Every claim carries a number and a source, or says it could not be sourced. This report is the research input for the next spec and plan; the brainstorming half of that spec is the discovery step of /ai-spec, which this document feeds rather than replaces. [11]

One page

The framework already does most of what the eight goals ask. Sixteen skills under .agents/skills/ with a contract that measures descriptions, corpora and routing; four fail-closed guards plus two telemetry hooks, dispatched by hooks/chain.py on every surface; three git hooks shipped in the wheel and wired per repository through core.hooksPath; a ten-verb CLI whose init installs globally and, on request, per project; a hash-linked audit chain; a CycloneDX SBOM and release attestation; and a quality gate whose every promise is a command. [11]

The open decisions are smaller than they look. (1) Git hooks stay per-repository — that is what git's own documentation and pre-commit's both recommend; a global hook install is explicitly not recommended because of untrusted repositories, and the middle ground for new clones is init.templateDir. [1][2] (2) The per-project half of ai-eng init cannot be globalised — the seven files it writes are repository-scoped by nature — but it can become automatic: run inside a repository and it does global plus project; outside, global only. [11] (3) Skills are already ahead of the open Agent Skills standard, and the next step is a measurable catalog budget, not new fields. [5][6] (4) PII is the one genuine security gap: gitleaks finds secrets, not personal data, and the guard layer never reads document bodies — the fix is a scanning lane, not a new guard. unsourced

And one committed inconsistency to decide: the project is English-first, yet docs/tools.md, the generated docs/solution-intent.html and reports 001–005 are in Spanish. The rule and the record disagree; a spec should close it. [11]

This report ends with three cited directions worth taking; the spec weighs them against the options below.

What is proven, and what is not

  • proven Guards are fail-closed and their class is asserted. A test reads the dispatcher table and turns CI red if a hook on a blocking event is not a guard; a guard that crashes denies. Telemetry is the only thing that may fail open.
  • unproven No surface reads as proven. The README is explicit: not one surface has a receipted denial, so every surface that can deny reads unproven — including Claude Code. CI proves the dispatcher's deny path, not a surface.
  • measured Skills are measured, not described. contract.audit_one checks the six portable fields plus exactly three extensions, requires a Not for X — use /ai-Y clause, caps descriptions at 1,000 characters, bans jargon, scores prose with a Gunning-fog ceiling (11.03), and requires a corpus with ## Routes here and ## Refuses sections. just skilleval routes the corpus against a baseline in policy/pilot-register.toml.
  • proven The git floor exists and is verified. pre-commit runs git diff --cached --check and gitleaks over staged hunks; pre-push blocks protected branches, gitleaks on outgoing commits, and expired risk acceptances; commit-msg enforces <type>(<scope>): subject and writes the run-receipt trailer. ai-eng doctor asserts git_hook_fires.
  • one gap Supply chain is real but has one open verifier. sbom.py writes a CycloneDX document naming the exact sha256 uv build produced; the release job attests dist/* and the SBOM as one subject list; CI pins every scanner version and checksum. What nobody has done is fetch a published artefact from the index and check it against the attestation (EP-047/EP-280, per policy/threat-model.toml).
  • written down The doctrine is written down. The twelve rules in AGENTS.md include rule 10 (KISS, YAGNI, DRY, SOLID, TDD, Clean Code, Clean Architecture) and rule 11 (monitoring and observability before a URL). The templates init writes carry the same rules into every new repository.

Research findings

5.1 Git hooks: the scope decision (goal 5, and the floor of goal 1)

Git's own documentation frames core.hooksPath as the mechanism for “centrally configure your Git hooks”, and it can be set at any config scope. The same manual explains that system, global and command scopes are protected configuration — scopes git trusts because they are controlled by the user or a trusted administrator. That trust is precisely the risk: a hook that runs everywhere runs in repositories the user did not choose to govern. [1]

pre-commit, the most widely used hook framework, installs per repository (.git/hooks/pre-commit). Its documentation is explicit about the global form:

a global install “not recommended as it can lead to accidentally running hooks when interacting with an untrusted repository” [2]

pre-commit's supported middle ground is init-templatedir set into git config --global init.templateDir: hooks land in newly created or cloned repositories via the template, while existing foreign forks are untouched, and hooks pass cleanly when the repository never opted into the config (--skip-on-missing-config). [2]

The ai-engineering repo already chose the per-repository model and wrote down why in wiring.wire_git: “a global core.hooksPath would impose our commit convention on every foreign clone on the machine, forks included.” [11] The research agrees with that decision. The genuinely new option is init.templateDir so the floor exists on day one of a new clone.

5.2 Skills: the open standard, and where the repo is already ahead (goals 2 and 4)

The open Agent Skills specification (originally Anthropic's, now an open standard) defines name (1–64 lowercase/hyphenated chars, must match the folder), a description of 1–1,024 characters that must say what and when, and optional license, compatibility (1–500), metadata and allowed-tools (experimental). Loading is progressive: ~100 tokens of metadata at startup, the body on activation (keep under 500 lines), references one level deep. [5]

Anthropic's authoring guidance is sharp about the description: it is the field Claude matches against when deciding whether to trigger the skill, it should be third-person, name specific triggers, and be tested with evaluations before volume. [3][4] The repo's corpus discipline — a Not for X — use /ai-Y clause, a corpus.md of routing and refusal cases, and just skilleval against a baseline — is precisely the “evaluations first” practice the guidance asks for, enforced as code. [11]

Zed adds a constraint the repo should measure: the total size of all skill names and descriptions is capped at 50 KB per catalog, and skills that do not fit are “dropped from the catalog with a warning”. None of the 16 current descriptions is close to 1,000 chars, so sixteen skills sit far below the budget; the guardrail keeps it true. [6] Zed also confirms the repo's global root (~/.agents/skills/), project-local trust gating, and support for disable-model-invocation, which the repo already uses on the critics. [11]

One deliberate divergence is worth recording in the spec: contract.py allows the six portable fields plus exactly three extensions and rejects everything else, including the spec's optional metadata. That is a portability choice, written down; keep it, and say so in the record rather than relitigating it silently. [11]

5.3 Security and quality: OWASP GenAI, PII, supply chain (goals 1 and 8)

The OWASP GenAI LLM Top 10 2026 (published 4 August 2026, successor of the LLM Top 10 v1.1) keeps the categories that map to this product's guards: [7]

OWASP categoryExisting control in ai-engineering
Prompt injectionhooks/injection_guard.py on Read/WebFetch/Fetch/WebSearch/MCP + adversarial suite
Sensitive information disclosuregitleaks at the git floor; closed 9-field issue.py payload; _otlp.py redact=strict; constitution “never record secrets or personal data”
Supply chain vulnerabilitiesSBOM from the wheel; release attestation; pinned+checksummed scanners in CI; dependency gates (trivy, pip-audit, snyk)
Excessive agencyfail-closed guards; loop_guard; no_verify_guard; keyboard-only exception
Insecure plugin / skill designcontract.py audits every skill; self_protect denies writes into guards and settings

The genuine gap is PII, and it is a scanning problem, not a guard problem. gitleaks detects secrets (credentials, keys, tokens); it is not a personal-data classifier. unsourced Most personal data never reaches the guard layer at all (guards read tool names, paths and payloads, not document bodies), so the control that matters is a PII lane in the git floor and in issue reporting — regex/entity scanning over staged hunks and over the closed issue payload — plus keeping the existing “never record personal data” rule. This is additive: a pre-push/pre-commit lane, not a fifth guard. [11]

Supply chain is the strongest pillar and has exactly one open verifier. The repo builds a CycloneDX SBOM naming the wheel's sha256, runs it inside just check, attests dist/* and the SBOM in release, and pins every scanner. Sigstore's model — keyless signing with OIDC identity and a transparency log — is what the GitHub-native attestation used by the release workflow implements. [8][9] SLSA gives the levels for stating what provenance that buys (v1.2 is current; the repo's threat model already bounds its claim to a named subset of CycloneDX 1.6). What remains, per threat-model.toml, is EP-047/EP-280: nobody has fetched a published wheel from the index and verified the attestation + SBOM against it. That needs the network and a published release; the report marks it as the one supply-chain item no local work can close. [11]

5.4 One-shot CLI and project scaffolding (goals 6, 7, 8)

The Command Line Interface Guidelines the repo already follows cover all three goals: make the default the right thing for most users; never require a prompt; confirm before changing state; --dry-run; tell the user what changed; keep a repair path; and make it easy to uninstall. [10] ai-eng init already does the last five. The simplification that remains is detection: if init runs inside a repository it offers the project half; if not, it does the global half and says so. “Run once, configured” then reads: uv tool install ai-engineering + ai-eng init, with --dry-run first for the cautious. [10][11]

For goal 8 the repo already ships the bones: write-once doctrine files with rules 10 and 11 baked in, a per-stack justfile with lint/test/build per detected language, a security recipe (trivy + gitleaks) and a check workflow. The two honest gaps are that SAST rule sets are explicitly “add your own” per language, and the observability stanza defaults to an empty provider. The spec decision is whether the per-stack SLA becomes init --stack or a sibling verb; the doctrine says: prefer the smallest control that proves the outcome, and a new verb home costs a capability row, not just a file. [11]

5.5 Language: English always (goal 3)

The project states the rule (this session: “the project is always in English because it is open source”) and the tree mostly obeys it. The exceptions are committed and reviewed: docs/tools.md (a command cheat-sheet), the generated docs/solution-intent.html, and reports 001–005 under .ai/reports/. Fixing the generated page is a change in src/ai_engineering/solution_intent.py plus a regeneration; the others are translations or a deliberate archival note. This report is written in English to conform, and any spec/plan it feeds should be too. [11]

Decision-ready options for the spec

Five options the next spec should weigh. Each says what it is, what it gives, what it costs, what it rules out, and what the research points to.

Option 1 · Hooks: keep the per-repo floor, add init.templateDir

What: Keep core.hooksPath + ai.managed per repository; add an opt-in git init.templateDir so new clones are wired automatically; never set a global core.hooksPath.

Gives: the floor exists on day one of a new repo; foreign forks stay untouched; matches git's documentation and pre-commit's explicit warning.

Costs: one more init step (writes the template dir once, machine scope); new repos run gitleaks before a human has decided to govern that repo — which is exactly the “untrusted repository” case, so the template hook must pass cleanly when the repo never opted in.

Rules out: a true global hook floor, and everything that implies for forks. recommended [1][2][11]

Option 2 · CLI: init becomes context-aware (repo → global+project)

What: ai-eng init detects whether it is inside a repository; inside, it offers the project half after the global half; outside, global only. Flags (--global/--project/--dry-run) stay for scripts.

Gives: one command, one mental model; the per-project half stays (it cannot be globalised), but nobody has to remember the split.

Costs: a detection step and a new test for “inside vs outside a repo”; the will table (SCOPE) gains a conditional.

Rules out: a global-only install, which would silently not govern any repository. recommended [10][11]

Option 3 · Scaffolding: per-stack CI/CD + SAST + observability wiring

What: Extend the project half so the generated justfile/check.yml carries a per-stack security lane (SAST rule set + dependency scan + gitleaks) and an observability stanza with a named provider slot. Either inside init --stack or a sibling verb; the spec decides the home.

Gives: goal 8 in full: doctrine + monitoring + CI/CD quality and security for every detected project type, each step a command.

Costs: real maintenance weight per stack; the language-specific rules age and must be pinned like everything else in this repo; a capability row changes.

Rules out: leaving “add your own” as the per-language answer. recommended [7][10][11]

Option 4 · Skills: keep the six fields, add a measurable catalog budget

What: Keep contract.py's six portable fields + three extensions and the corpus discipline; add a check that the sum of every skill's name + description stays under the smallest documented catalog budget (Zed's 50 KB), so a future new skill cannot silently drop off a surface.

Gives: the “not one word over” guarantee becomes measurable per surface instead of per file; no new fields to maintain.

Costs: one constant and one assertion; the description cap stays at 1,000 internally vs the open standard's 1,024 (deliberate; keep and record why).

Rules out: adopting metadata or other upstream fields the contract currently refuses. recommended [5][6][4][11]

Option 5 · PII: a scanning lane, not a fifth guard

What: Add a PII scan to the git floor (staged hunks, on the same path gitleaks uses) and to the closed issue payload; keep it additive and fail-closed when the lane cannot run; leave the guards themselves unchanged.

Gives: the missing OWASP “sensitive information disclosure” coverage without widening guard authority or reading document bodies.

Costs: a scanner choice and its pin; PII detection is heuristic and must refuse to over-block (the repo's own threshold discipline applies).

Rules out: treating PII as a guard concern. The guard layer decides tool calls; PII is data that should never be written, and the floor is where that is caught. unsourced [7]

Explicitly not doing

  • No ai-brainstorm skill. The normative disposition (spec 010) absorbed brainstorming into the discovery step of the /ai-spec; this report is that step's research input for the next spec. Adding a skill would be a second home for a decision the record already made. [11]
  • No global core.hooksPath. Both git's protected-configuration model and pre-commit's warning oppose it; per-repo wiring plus init.templateDir covers the need.
  • No new CLI verbs without a capability row. Every verb change touches the will table and the capability manifest; the report prefers extending init over adding new homes.

What would change, depending on each answer

D1Hooks: per-repo + init.templateDir → new clones governed on day one; forks never touched. A global floor would change nothing for the better.
D2CLI context-aware → init outside a repo does global only. The alternative (drop the project half) would silently stop governing repositories.
D3Per-stack SLA → every generated project gets the security/quality lane; the cost is a pinned rule set per language that CI must test like any other scanner.
D4Catalog budget → the “not one word over” goal becomes measurable across the corpus, not just per file.
D5PII lane → closes the one OWASP gap without changing guard authority. Supply-chain verifier (EP-047/280) stays open until a release exists to fetch.

Three cited directions worth taking

1. Adopt the hybrid hook model and wire new clones. Keep the per-repository core.hooksPath floor exactly as wiring.py builds it, and add an opt-in init.templateDir so a new clone runs the floor from its first commit — while passing cleanly on any repository that never opted in. Git documents the mechanism, and pre-commit's maintainers explicitly warn that a global hook install misfires on untrusted repositories. [1][2]

2. Make skill precision measurable across the corpus. Keep the six-field contract, the Not for clause and the corpora that skilleval already routes, and add the catalog-budget assertion the surface docs actually impose (50 KB of metadata on Zed) so “not one word over” is a gate and not a description. [5][6][4]

3. Close the supply-chain verifier gap the threat model names. Ship the fetch-and-verify step for the published wheel — attestation + SBOM against the index bytes — the half EP-047/EP-280 mark as unreachable from local work, using the model the release workflow already implements. And fix the English-first inconsistency (translate tools.md, regenerate the page) in the same block so the record and the rule stop disagreeing. [8][9][11]
