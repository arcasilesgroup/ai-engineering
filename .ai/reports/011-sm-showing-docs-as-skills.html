R-011 · «Why does sm (skill-map) show so many "skills" in this repo, when those files are really specs, plans and corpus?»

Date: 2026-08-25 · tool verified: sm 1.12.2 · provider lens: agent-skills · repo: ai-engineering

Short answer

sm does not misclassify your specs, plans, ADRs or corpus as skills. Its own graph proves it: of the 161 nodes it mapped before any fix, exactly 16 are kind=skill — the sixteen real .agents/skills/<name>/SKILL.md files — and every spec/plan/ADR/corpus/AGENTS/CHANGELOG file is kind=markdown [5]. What makes the map look like a wall of "skills" is that the scan had been admitting garbage it should ignore: 37 of the 161 nodes (23%) came from .venv/…/site-packages/ai_engineering/skills/** (an extra copy of the skills tree that this repo's own wheel installs into its venv) plus .pytest_cache/README.md, because scan.respectGitignore was false [5]. ai-engineering is not badly made: its one-skill-tree design maps 1:1 onto skill-map's model. The repo's own spec 026 already adopts sm as its reference-integrity gate. The defect was a scan configuration, and it is fixed by one command.

What I did to answer it (verified, not assumed)

Everything below I ran on this machine against this repo, so it is first-hand, not a blog [5]:

  • Read sm config list → activeProvider: agent-skills, scan.respectGitignore: false.
  • Queried the scan store .skill-map/skill-map.db (table scan_nodes): ('markdown', 145), ('skill', 16).
  • Bucketed the 145 markdown nodes → 36 from .venv/.../ai_skills/**, 1 from .pytest_cache/README.md; the rest are real tree files (specs/, ADRs/, corpus/, top-level docs).
  • Ran the fix sm config set scan.respectGitignore true, then sm scan, then re-queried: nodes dropped 161 → 124; skill still exactly 16; .venv/.pytest_cache nodes now 0.

Why the map shows "so many" nodes at all

skill-map is a graph of every markdown file under the active provider lens, each tagged with a programmatic kind [1][2]. Under the agent-skills provider a skill node is only a <…/skills/<name>/SKILL.md — the same SKILL.md convention the repo itself uses. Everything else (corpus.md, references/, specs/, docs/adr/, AGENTS.md, CONSTITUTION.md, intent.md, README.md) is classified markdown [2][1]. The UI simply lists all of those node kinds together, so a wide node board reads as "todos son skills" when the dashboard/per-kind filter would show exactly 16 of them tagged skill.

And the cluster had been inflated by files that should never be in the map. scan.respectGitignore: false makes the walker descend into .venv and .pytest_cache even though they are gitignored [3]. Inside .venv/lib/python /site-packages/ai_engineering/skills/ sits a second, installed copy of that skill tree (the wheel's packaged skills/ sidecar — packaging residue, not a source-tree mirror), so `sm` double-counted roughly one extra file per skill [verified by my own scan, 5]. That is the concrete mechanic behind "muestra tantos".

Is ai-engineering wrongly made, or sm wrongly used?

Neither framework is wrong. The repo's structure matches skill-map's model exactly: one canonical skill tree .agents/skills/, everything else intentionally outside it, and the repo's own AGENTS.md rule "no mirror, no sync" (the wheels in .venv is packaging, not a mirror). spec 026 (draft, dated 2026-08-25) belongs to this repo and definitively answers "how is sm supposed to be used here": as a reference-integrity instrument — just map runs sm scan && sm check --json and fails the gate on a real missing-target finding, with the NNN-slug demo holes excluded as a data file. So sm is "fine", and the repo is not misconfigured at the directory level. The only misconfiguration was in the engine-local .skill-map/settings.json scan (gitignore not respected), which has no effect on the repo's own contract.

How to configure / use it well (with the commands I proved)

# 1. Stop the map admitting .venv / caches / node_modules
sm config set scan.respectGitignore true
#    (or pin the scan to just the skill tree: add roots/ignore inside .skill-map/settings.json)

# 2. Re-emit the graph so the counter reflects only real content
sm scan

# 3. Use it as the repo's own spec 026 prescribes for the gate
just map    # runs sm scan && sm check --json -> non-zero exit on a real broken ref

Result after the fix: the 37 junk nodes are gone, skill is still exactly 16, and the map now reflects only files actually present in this repo — your instinct was right: those weren't 160 skills, but the repo itself is sound; only the scan config was loose [5].
