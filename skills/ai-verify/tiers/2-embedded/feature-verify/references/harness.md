## What the script detects, and how it guesses

- **Package manager** — from the lockfile (`pnpm-lock.yaml`, `yarn.lock`, `bun.lockb`, else npm).
  This also picks the `dlx` form used to install the browser (`pnpm dlx`, `yarn dlx`, `bunx`,
  `npx -y`).
- **Dev command** — `scripts.dev`, falling back to `start`, then `serve`.
- **Port** — an explicit `-p`/`--port` in that script wins; otherwise by framework (Next/Remix/Nuxt/CRA
  → 3000, Vite/SvelteKit/Astro → 5173); otherwise 3000.

Every guess is visible in the summary the script prints. If a value looks wrong, re-run with an
override rather than editing the generated files — they're regenerated on each run.

## Overriding command and port

```bash
bash scripts/setup_harness.sh /path/to/repo --port 4321 --cmd "pnpm dev --host"
```

## What the run directory contains

```
.feature-verify/
  config.json     baseURL, chrome-headless-shell path, artifacts dir, detected dev command
  harness.mjs     browser lifecycle, check(), the polling assertions, shot()
  specs/          your throwaway *.test.mjs files
  artifacts/      screenshots, DOM dumps, error logs — the evidence
```

`harness.mjs` is ordinary JavaScript; edit it directly for anything the flags don't cover (a
different default timeout, extra Chrome flags, a different default viewport). It's regenerated by
the next `setup_harness.sh` run, so don't put anything there you need to keep.

Two settings worth knowing:

| Setting | Where | Why |
|---|---|---|
| `DEFAULT_TIMEOUT` | `harness.mjs` | 10s ceiling for every polling assertion |
| `headless: 'shell'` | `harness.mjs` launch | required — the shell binary rejects Chrome's `--headless=new` |
| `deviceScaleFactor: 1` | `check()` viewport | agent verification shots; raise only for human deliverables |

## The dev server

The script probes the port and reports, but never starts a server — a backgrounded process spawned
from a setup script outlives it and gets orphaned. You start it, as a background command, and you
kill it during cleanup.

Reusing a server the user already has running is usually what you want: it's faster and it tests the
same process they're looking at. Two caveats during triage:

- A stale server running pre-change code produces a confusing "the feature isn't there" failure.
  If the feature's UI is missing entirely, check that the dev server picked up the change before
  reporting a defect.
- If the port is occupied by a *different* project, everything fails at once. The control route
  from Step 2 catches this.

## Environment variables

The dev server inherits the environment of whatever shell you start it in:

```bash
FEATURE_FLAG=on <pm> run dev
```

If the feature is behind a flag, verifying with the flag off silently tests nothing. Confirm which
state you're in and say so in the report.

Never hardcode secrets — read them from the ambient environment. If a required variable is missing,
stop and tell the user which one; don't invent a value.

## The browser binary

`chrome-headless-shell` is installed once per machine into `~/.cache/puppeteer` and shared by every
repo. Full Chrome and Canary are not substitutes here: the shell is 3.7x faster on a real page and
9x on a local one, with byte-identical output.

```bash
npx -y @puppeteer/browsers install chrome-headless-shell@stable --path "$HOME/.cache/puppeteer"
```

It prints `chrome-headless-shell@<version> <absolute path>` whether it downloaded anything or not,
which is how the setup script resolves the path into `config.json`. If a run fails with a spawn
error, re-run that command — the cache may have been cleared. The path is per-machine, so a
`config.json` copied between machines is worthless; re-run the setup script instead.

`puppeteer-core` is installed as a dev dependency of the repo (never `puppeteer`, which would drag
in a full Chrome download). Say in the report if the script added it.

## Auth

The harness shares one browser — and therefore one cookie jar — across all checks in a spec file, so
logging in once in a lazily-invoked helper is enough. See the Auth section of
`puppeteer-patterns.md` for the pattern.

Credentials come from env (`E2E_EMAIL` / `E2E_PASSWORD` or whatever the project already uses). If
there are none and the app is gated, the honest outcome is a report saying authenticated flows were
not verified — not a fabricated user.

To persist auth across spec *files*, dump and reload cookies:

```js
const cookies = await page.cookies();
fs.writeFileSync(`${ARTIFACTS}/cookies.json`, JSON.stringify(cookies));
// in the other file:
await page.setCookie(...JSON.parse(fs.readFileSync(`${ARTIFACTS}/cookies.json`, 'utf8')));
```

## Seeded data

Specs asserting on specific records need those records to exist. In order of preference:

1. **Run the project's existing seed script** (whatever `db:seed` / `seed` / a `Makefile` target is called here) before the suite, if it's safe and
   idempotent. Ask first if it touches a shared database — this skill doesn't mutate state the user
   didn't sanction.
2. **Create what you need through the UI** in the first `check()`, then assert against it. Slower
   but self-contained and it exercises real code paths.
3. **Stub the API** with request interception so the data is deterministic. Note the stubbing in the
   report.

Assert on shapes rather than exact values when data isn't controlled — a count greater than zero, or
a regex on a heading, beats hardcoding "3 rows" against a database you don't own. (`count()` wants an
exact number; use `poll()` for "more than none".)

## Monorepos

Run the setup script with the app package as `<repo>` so `puppeteer-core` resolves and the port
detection matches, and start the dev server from there:

```bash
bash scripts/setup_harness.sh /abs/path/to/repo/apps/web --cmd "pnpm --filter web dev"
```

`blast_radius.py` should run from a root that contains both the app and any shared packages,
otherwise it can't see the import edges from `packages/ui` into `apps/web`. Say in the report which
apps you verified and which you didn't.

## Build-then-serve instead of dev

Occasionally the dev server hides a problem the production build has (or vice versa — dev-only
overlays, different env handling). When the change touches build config, static generation, or
server components, verifying against the built output is more faithful:

```bash
<pm> run build && <pm> run start   # then point the harness at that port
```

This is slower; use it when the change warrants it, and note which mode you verified in.

## When it still won't start

Run the dev command in the foreground and read the output. The usual causes: a port already bound, a
missing `.env`, a failed install, or a build error that Step 3's gates should have caught first.

If the app genuinely can't run in this environment, stop and report that. A verification run that
never loaded the app must not produce a PASS.

## Cleanup rules

The run directory is disposable; the evidence inside it is not.

- **All green** — remove `<repo>/.feature-verify/` entirely.
- **Any failure** — remove `specs/`, keep `artifacts/`, and give the user the absolute path.
- **Kill any dev server you started.** Leave the user's own running.
- **Keep** `~/.cache/puppeteer` — it's shared across repos and runs, and re-downloading it is exactly
  the cost this setup avoids.
- **Never** touch files outside `.feature-verify/`, including the project's own tests. The two
  exceptions are the `.gitignore` line and the `puppeteer-core` devDependency the setup script adds,
  both of which it reports when it does.
